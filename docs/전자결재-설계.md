# 전자결재 설계

> mes-v6 · 수주 · 발주 · 작업지시 · 외주발주 · 출하지시의 결재
> 작성일: 2026-08-28 · 상태: 확정 (미결은 §9)
> 상위 문서: [개발범위-및-MVP.md](./개발범위-및-MVP.md) · 관련: [정책-설정-설계.md](./정책-설정-설계.md)

---

## 1. 결정

> **자체 구현.** 순차 · 병렬 · 합의 · 참조 · 전결 · 전결 규정까지 다룹니다.
> 그룹웨어 연동은 **어댑터 자리만** 만들고 구현하지 않습니다.

---

## 2. 왜 자체 구현인가

**결재 대상이 MES 데이터입니다.** 작업지시서 · 발주서는 MES 안에서 만들어지고,
승인 결과가 곧 그 문서의 상태를 바꿉니다.

| 그룹웨어 연동의 문제 | |
|---|---|
| 데이터 복제 | 문서 내용을 그룹웨어로 보내고, 승인 결과를 되받아 상태를 바꿔야 합니다 |
| **왕복 실패** | 승인은 됐는데 콜백을 놓치면 MES는 계속 대기 상태입니다 |
| 표준 불가 | 업체마다 그룹웨어가 다릅니다 — 더존 · 영림원 · 자체 개발 |
| 승인 전 차단 | 외부 응답을 기다리는 구조에서 업무를 막는 것은 취약합니다 |

**패키지 제품에서 업체마다 다른 외부 시스템에 의존하면 매 계약이 커스텀 개발이 됩니다.**

다만 대기업 협력사는 그룹웨어 결재를 강제받는 경우가 있으므로, **어댑터 인터페이스만 정의**해두고
실제 구현은 그런 요구가 왔을 때 합니다(§8).

---

## 3. 범위와 결재 방식

| 만든다 | 만들지 않는다 |
|---|---|
| **순차 · 병렬** 결재 | 조건식 엔진 (스크립트 · 수식) |
| **합의** · 참조 | 자유 양식 빌더 |
| **전결** · **전결 규정** | 위임 · 부재중 대리 (**Phase 3**) |
| 상신 → 승인 / 반려 → 재상신 | 결재 문서 자체의 버전 관리 |
| 문서 유형별 고정 양식 + 자유 텍스트 | 조직도 연동 |
| 첨부파일 · 결재 이력 | |

### 단계 유형 셋

| 유형 | 동작 | 반려 가능 |
|---|---|---|
| **`APPROVAL`** 결재 | 승인해야 다음 단계로 | O |
| **`AGREEMENT`** 합의 | 관련 부서의 동의. 승인 흐름을 **막음** | O |
| **`REFERENCE`** 참조 | **통보만.** 흐름을 막지 않고 즉시 통과 | X |

실무 순서는 보통 `기안 → 합의(관련 부서) → 결재 → 참조`입니다.
합의와 결재를 나누는 이유는 **책임의 성격이 다르기 때문**입니다 —
합의는 *"우리 부서는 이의 없음"* 이고 결재는 *"내가 승인한다"* 입니다.

### 병렬 — 같은 단계에 여러 명

같은 `seq`에 결재자가 여럿이면 **동시에** 진행합니다.

| `parallel_rule` | 다음 단계로 넘어가는 조건 |
|---|---|
| **`ALL`** *(기본)* | 그 단계 **전원**이 승인 |
| `ANY` | **한 명이라도** 승인 |

`ANY`는 *"팀장 셋 중 아무나"* 같은 경우입니다. 한 명이 승인하면 나머지는 `SKIPPED`가 됩니다.

**병렬 단계에서 한 명이라도 반려하면 문서 전체가 반려**됩니다. `ANY`여도 마찬가지입니다 —
반대 의견이 나왔는데 다른 사람 승인으로 통과시킬 수는 없습니다.

### 전결 — 그 선에서 종결

결재자에게 **전결 권한**(`can_final`)이 있으면, 승인할 때 *"전결"* 을 선택해
**이후 단계를 건너뛰고 문서를 확정**할 수 있습니다.

```
1. 팀장   ─ 승인
2. 부장   ─ 전결 승인  ←  여기서 종결
3. 이사   ─ SKIPPED
   문서 → APPROVED
```

- 건너뛴 단계는 삭제하지 않고 **`SKIPPED`로 기록**합니다. 누가 전결했는지 이력에 남습니다
- 전결은 **권한이 있는 사람만** 선택할 수 있습니다. 없으면 일반 승인만 보입니다
### 전결 규정 — 결재선을 자동으로 고른다

전결에는 두 층이 있습니다. **둘 다 필요하고, 하는 일이 다릅니다.**

| | 무엇을 정하는가 | 누가 |
|---|---|---|
| **전결 규정** | 조건에 따라 **어느 결재선을 탈 것인가** | 시스템이 자동 |
| **전결 권한** (`can_final`) | 그 결재선 안에서 **조기 종결** | 사람이 판단 |

규정으로 짧은 결재선이 잡히면 마지막 결재자가 곧 최종 승인자가 됩니다.
그 안에서도 상황에 따라 상급자가 앞당겨 끝내야 할 때 `can_final`이 쓰입니다.

#### 조건식을 쓰지 않는다

전결 규정은 대부분 **금액 구간**입니다 — *"1천만원 이하 부장, 1억 이하 이사, 초과 대표"*.
여기에 문서 유형과 부서가 곁들여지는 정도입니다.

스크립트나 수식 엔진을 넣으면 유연해지지만 **업체 담당자가 쓸 수 없고 디버깅이 어렵습니다.**
조건 컬럼을 명시적으로 두고 **우선순위로 매칭**합니다.

```
approval_rule
  doc_type    SALES_ORDER     필수
  dept_id     NULL            NULL = 모든 부서
  amount_min  NULL            NULL = 하한 없음
  amount_max  10,000,000      이하
  line_def_id → "부장 전결선"
  priority    10              낮을수록 먼저 평가
```

#### 매칭 순서

```
1. doc_type · dept · amount 로 approval_rule 조회
2. priority 오름차순 첫 번째 규칙의 결재선 사용
3. 매칭되는 규칙이 없으면 → 그 doc_type 의 is_default 결재선
```

- **규정으로 선택된 결재선은 상신자가 바꿀 수 없습니다.** 규정이니까요
- 매칭되는 규칙이 없어 기본 결재선이 잡힌 경우에만 상신자가 고를 수 있습니다
- 상신 **전에** 문서 금액이 바뀌면 결재선을 다시 평가합니다.
  상신 **후에** 바뀌면 **재상신**해야 합니다 — 금액이 달라졌는데 같은 결재선으로 통과시킬 수 없습니다

#### 금액이 없는 문서

작업지시서처럼 금액이 없는 문서는 `amount`가 `NULL`이고, 금액 조건이 있는 규칙에는 매칭되지 않습니다.
`doc_type`과 `dept_id`만으로 규칙을 만들면 됩니다.

`approval_doc.amount`는 문서를 만들 때 채웁니다 — 수주 금액 · 발주 금액 · 출하 금액 · 외주 금액.

## 4. 문서 유형 5종

원문에 명시된 연동 지점 그대로입니다.

| 유형 | 대상 | 승인 전 막히는 것 |
|---|---|---|
| `SALES_ORDER` | 수주 | 생산계획 · 작업지시 |
| `PURCHASE_ORDER` | 발주서 | 발주 전송 · 입고 |
| `WORK_ORDER` | 작업지시서 | 작업지시 배포 · 라우트시트 발행 |
| `SUBCONTRACT_ORDER` | 외주발주 | 외주 출고 |
| `SHIPMENT_ORDER` | 출하지시서 | 출하 처리 |

각 업무 테이블에 이미 자리를 잡아둔 필드를 씁니다
([개발범위-및-MVP.md](./개발범위-및-MVP.md) §6 — *"빼되 설계는 미리"*).

```sql
approval_status   VARCHAR(12)  -- NONE | DRAFT | PENDING | APPROVED | REJECTED
approval_doc_id   BIGINT NULL
```

## 5. 승인 전에는 진행하지 않는다

**결재는 차단이 맞는 몇 안 되는 경우입니다.** 승인 전에 발주가 나가거나 출하가 되면 되돌릴 수 없습니다.

소급 입력이나 공정 순서와 다릅니다 — 그쪽은 *"이미 현장에서 일어난 일"* 이라 막으면 안 되지만,
결재는 *"아직 일어나서는 안 되는 일"* 입니다.
([재고-수불-설계.md](./재고-수불-설계.md) §5.2의 구분과 같은 논리)

**`feature.approval`이 꺼져 있으면 결재 자체가 없습니다.** `approval_status`는 `NONE`이고 아무것도 막지 않습니다.
결재를 쓰지 않는 업체가 다수일 것이므로 기본값은 꺼짐입니다.

## 6. 스키마

**단계(stage)와 결재자(member)를 분리합니다.** 병렬이면 한 단계에 결재자가 여럿이기 때문입니다.

```sql
-- 문서 유형별 양식 정의 (제품이 제공, 공용 DB)
CREATE TABLE approval_form_def (
  doc_type   VARCHAR(20)  NOT NULL,   -- SALES_ORDER | PURCHASE_ORDER | ...
  title_ko   VARCHAR(60)  NOT NULL,
  field_spec TEXT         NULL,       -- 유형별 고정 항목 정의
  PRIMARY KEY (doc_type)
) ENGINE=InnoDB;

-- 결재선 템플릿 (업체가 등록)
CREATE TABLE approval_line_def (
  id         BIGINT      NOT NULL AUTO_INCREMENT,
  tenant_id  INT         NOT NULL,
  doc_type   VARCHAR(20) NOT NULL,
  name       VARCHAR(60) NOT NULL,
  is_default BOOLEAN     NOT NULL DEFAULT FALSE,
  is_active  BOOLEAN     NOT NULL DEFAULT TRUE,
  PRIMARY KEY (id),
  KEY ix_type (tenant_id, doc_type, is_active)
) ENGINE=InnoDB;

-- 단계
CREATE TABLE approval_line_stage (
  line_def_id   BIGINT      NOT NULL,
  seq           SMALLINT    NOT NULL,
  step_type     VARCHAR(10) NOT NULL,            -- APPROVAL | AGREEMENT | REFERENCE
  parallel_rule VARCHAR(4)  NOT NULL DEFAULT 'ALL',  -- ALL | ANY
  PRIMARY KEY (line_def_id, seq)
) ENGINE=InnoDB;

-- 단계별 결재자 (병렬이면 여러 행)
CREATE TABLE approval_line_member (
  line_def_id BIGINT   NOT NULL,
  seq         SMALLINT NOT NULL,
  approver_id BIGINT   NOT NULL,
  can_final   BOOLEAN  NOT NULL DEFAULT FALSE,   -- 전결 권한
  deputy_id   BIGINT   NULL,                     -- 대리자 자리 (Phase 3)
  PRIMARY KEY (line_def_id, seq, approver_id)
) ENGINE=InnoDB;

-- 전결 규정 (업체가 등록)
CREATE TABLE approval_rule (
  id          BIGINT        NOT NULL AUTO_INCREMENT,
  tenant_id   INT           NOT NULL,
  doc_type    VARCHAR(20)   NOT NULL,
  dept_id     BIGINT        NULL,          -- NULL = 모든 부서 (부서는 1단계 평면 — 상위 상속 없음)
  amount_min  DECIMAL(18,2) NULL,          -- NULL = 하한 없음
  amount_max  DECIMAL(18,2) NULL,          -- NULL = 상한 없음
  line_def_id BIGINT        NOT NULL,      -- 적용할 결재선
  priority    SMALLINT      NOT NULL,      -- 낮을수록 먼저 평가
  is_active   BOOLEAN       NOT NULL DEFAULT TRUE,
  PRIMARY KEY (id),
  KEY ix_match (tenant_id, doc_type, is_active, priority),
  CONSTRAINT fk_rule_line FOREIGN KEY (line_def_id) REFERENCES approval_line_def(id)
) ENGINE=InnoDB;

-- 상신된 문서
CREATE TABLE approval_doc (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id     INT          NOT NULL,
  doc_type      VARCHAR(20)  NOT NULL,
  ref_id        BIGINT       NOT NULL,   -- 수주 · 발주 … 원본 ID
  doc_no        VARCHAR(30)  NOT NULL,
  title         VARCHAR(120) NOT NULL,
  body          TEXT         NULL,       -- 양식 항목 값 + 의견
  amount        DECIMAL(18,2) NULL,      -- 전결 규정 매칭용. 금액 없는 문서는 NULL
  line_def_id   BIGINT       NOT NULL,   -- 적용된 결재선
  rule_id       BIGINT       NULL,       -- 매칭된 전결 규정 (없으면 기본 결재선)
  status        VARCHAR(12)  NOT NULL,   -- PENDING | APPROVED | REJECTED | CANCELED
  final_by      BIGINT       NULL,       -- 전결로 종결한 사람
  drafted_by    BIGINT       NOT NULL,
  drafted_at    DATETIME(6)  NOT NULL,
  closed_at     DATETIME(6)  NULL,
  reject_reason VARCHAR(500) NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_no  (tenant_id, doc_no),
  KEY ix_ref  (tenant_id, doc_type, ref_id),
  KEY ix_wait (tenant_id, status, drafted_at)
) ENGINE=InnoDB;

-- 진행 중인 단계
CREATE TABLE approval_stage (
  doc_id        BIGINT      NOT NULL,
  seq           SMALLINT    NOT NULL,
  step_type     VARCHAR(10) NOT NULL,
  parallel_rule VARCHAR(4)  NOT NULL,
  status        VARCHAR(10) NOT NULL,   -- WAITING | DONE | REJECTED | SKIPPED
  PRIMARY KEY (doc_id, seq)
) ENGINE=InnoDB;

-- 결재자별 행위
CREATE TABLE approval_action (
  doc_id      BIGINT       NOT NULL,
  seq         SMALLINT     NOT NULL,
  approver_id BIGINT       NOT NULL,
  status      VARCHAR(10)  NOT NULL,   -- WAITING | APPROVED | AGREED | REJECTED | SKIPPED | NOTIFIED
  is_final    BOOLEAN      NOT NULL DEFAULT FALSE,  -- 전결로 승인
  acted_at    DATETIME(6)  NULL,
  comment     VARCHAR(500) NULL,
  PRIMARY KEY (doc_id, seq, approver_id),
  KEY ix_my (approver_id, status)       -- 내 결재함
) ENGINE=InnoDB;
```

`approval_form_def`는 **공용 DB**, 나머지는 테넌트 DB입니다 —
양식은 제품이 정하고 결재선은 업체가 정하기 때문입니다
([멀티테넌시-설계.md](./멀티테넌시-설계.md) §3).

## 7. 상태 흐름

```
        상신                       마지막 단계 완료
DRAFT ────────▶ PENDING ─────────────────────────▶ APPROVED
                   │  ▲                    ▲
                   │  │ 재상신              │ 전결 승인 (이후 단계 SKIPPED)
                   ▼  │
                REJECTED
```

### 단계 진행 규칙

| 단계 유형 | 완료 조건 |
|---|---|
| `APPROVAL` · `AGREEMENT` | `parallel_rule`에 따라 **전원** 또는 **한 명** 승인 · 동의 |
| `REFERENCE` | **즉시 완료.** 알림만 보내고 흐름을 막지 않음 |

- 한 단계가 완료되어야 다음 단계가 열립니다
- **`ANY` 단계에서 한 명이 승인하면 나머지는 `SKIPPED`** 가 됩니다
- **어느 단계든 한 명이라도 반려하면 문서 전체가 `REJECTED`** 입니다.
  `ANY`여도 반대 의견을 다른 승인으로 덮지 않습니다
- **전결 승인이면 이후 단계 전체가 `SKIPPED`** 되고 문서가 `APPROVED`로 종결됩니다.
  누가 전결했는지는 `approval_doc.final_by`에 남습니다

### 재상신 · 회수

- 재상신은 **새 문서를 만들지 않고** 같은 문서의 단계를 초기화합니다.
  이전 시도의 `approval_action` 이력은 그대로 두고 회차를 구분해 누적합니다
- 상신자는 진행 중인 문서를 **회수**할 수 있습니다 (`CANCELED`)

## 8. 외부 연동 자리

그룹웨어 결재를 요구하는 고객이 나오면 **인터페이스 하나만 갈아끼웁니다.**

```
ApprovalGateway
  submit(doc)        상신 → 결재 시스템으로
  cancel(doc)        회수
  onResult(docId, result)   승인 · 반려 결과 수신
```

- 기본 구현: **내부 결재** (§6 스키마 사용)
- 외부 구현: 그룹웨어 API 호출 + 콜백 수신
- 업무 코드는 `approval_status`만 봅니다. **어느 쪽이 처리했는지 알 필요가 없습니다**

정책 키는 만들지 않습니다. 외부 연동은 **배포 설정**(어댑터 구현 선택)이지 업체가 화면에서 켜는 값이 아닙니다.

## 9. Phase

| Phase | 내용 |
|---|---|
| **Phase 1** | `approval_status` · `approval_doc_id` **필드만.** 값은 항상 `NONE` |
| **Phase 2** | 내부 결재 전체 — 결재선 템플릿 · 상신 · 승인 · 반려 · 재상신 · 내 결재함 |
| **Phase 3** | 위임 · 부재중 대리. 필요 시 외부 어댑터 구현 |

## 10. 미결

| # | 항목 | 확인 필요 |
|---|---|---|
| 1 | **양식 항목** | 문서 유형 5종 각각에 어떤 항목이 들어가는지(`approval_form_def.field_spec`). **화면정의서 단계에서 자연스럽게 정해집니다** — 설계를 막지 않습니다 |

> 해결됨 — *규정 조건 항목*: **`doc_type` · `dept_id` · `amount` 셋으로 확정.** 더 늘리지 않습니다.

## 부록 · 결정 요약

| 결정 | 값 |
|---|---|
| 구현 | **자체 구현.** 그룹웨어 연동은 어댑터 자리만 |
| 범위 | **순차 · 병렬 · 합의 · 참조 · 전결 · 전결 규정.** 위임 · 부재중 대리는 Phase 3 |
| 단계 유형 | `APPROVAL`(결재) · `AGREEMENT`(합의, 흐름 막음) · `REFERENCE`(참조, 안 막음) |
| 병렬 | 같은 `seq`에 결재자 여럿. `ALL`(전원) / `ANY`(한 명). **반려는 언제나 전체 반려** |
| 전결 | `can_final` 권한자가 전결 승인 시 **이후 단계 `SKIPPED`** 후 종결. 이력 보존 |
| **전결 규정** | `approval_rule` — **`doc_type` · `dept_id` · `amount` 세 조건 확정** + 우선순위로 **결재선 자동 선택**. 조건식 엔진 없음 |
| 결재선 변경 | 규정이 매칭되면 **상신자가 못 바꿈.** 기본 결재선일 때만 선택 가능 |
| 금액 변경 | 상신 전이면 재평가, 상신 후면 **재상신** |
| 스키마 | **단계와 결재자를 분리** — 병렬이면 한 단계에 여러 명 |
| 양식 | 문서 유형별 **고정 항목 + 자유 텍스트.** 양식 빌더 아님 |
| 문서 유형 | 5종 — 수주 · 발주서 · 작업지시서 · 외주발주 · 출하지시서 |
| 승인 전 | **차단.** *"아직 일어나서는 안 되는 일"* 이므로 |
| 기본값 | `feature.approval` **꺼짐** |
| 배치 | `approval_form_def`는 공용 DB, 나머지는 테넌트 DB |
| Phase | 필드만 Phase 1 · 본체 Phase 2 · 위임/외부연동 Phase 3 |

### Nuxt는 SPA 모드로 씁니다

```ts
// nuxt.config.ts
export default defineNuxtConfig({ ssr: false })
```

**사내 업무 시스템에 SSR은 이득이 없습니다.** SEO도, 첫 화면 속도도 관심사가 아니고,
SSR을 켜면 **Node 서버가 하나 더** 늘어납니다 — 온프레미스에서 프로세스 하나가 그냥 비용입니다.

그럼 Nuxt를 왜 쓰냐면, **화면이 57개**이기 때문입니다.

| Nuxt가 주는 것 | 왜 필요한가 |
|---|---|
| **파일 기반 라우팅** | 57개 화면의 라우트를 손으로 등록하지 않습니다 |
| **자동 임포트** | 공통 컴포넌트 4개를 매 파일에서 `import` 하지 않습니다 |
| **레이아웃** | 메뉴 · 헤더 · 인증 가드를 한 번만 씁니다 |
| **컴포저블 규약** | `useXxx()` 자리가 정해져 있어 팀이 헤매지 않습니다 |

빌드 결과는 **정적 파일**이라 Nginx가 그대로 서빙합니다.

**프로세스가 넷입니다** — Nginx · PHP-FPM · Reverb · 스케줄러.
PHP는 상주하지 않으므로 웹소켓과 배치를 앱 안에 넣을 수 없습니다.
**설치를 패키지로 감싸는 이유**가 이것입니다(§13).

### 디렉터리

```
app/
  Http/         Controllers · Requests · Resources · Middleware
  Services/     업무 규칙 (트랜잭션 경계)
  Models/       Eloquent 모델
  Domain/
    Stock/      원장 · 잔고 · 스냅샷
    Calc/       수식 파서 · 평가기
    Policy/     정책 해석 (스코프 계층)
  Support/
    Tenancy/    커넥션 교체 · 마이그레이션 순회
    Notify/     알림 발행 (한 곳)
    Files/      파일 저장소 (로컬 / S3)
```

**`Services`가 트랜잭션 경계입니다.** 컨트롤러는 요청을 받아 넘기기만 하고,
모델에 업무 규칙을 넣지 않습니다 — 규칙이 흩어지면 어디서 재고가 깎이는지 못 찾습니다.

## 4. 멀티테넌시 런타임

### 4.1 요청마다 커넥션을 바꾼다

```php
// Middleware
$tenant = $request->user()->tenant;          // 토큰 → 사용자 → 테넌트
config(['database.connections.tenant.database' => $tenant->db_name]);
DB::purge('tenant');
DB::reconnect('tenant');
TenantContext::set($tenant);
```

| 규칙 | 내용 |
|---|---|
| 테넌트 결정 | **클라이언트가 보내지 않습니다.** 토큰의 사용자에서 서버가 찾습니다 |
| 커넥션 이름 | `common`(고정) · `tenant`(교체). 모델마다 `$connection`을 명시 |
| 컨텍스트 정리 | 미들웨어 `terminate`에서 반드시. **안 하면 다음 요청이 남의 DB를 봅니다** |
| 큐 · 배치 | 컨텍스트가 안 따라갑니다. **작업에 `tenant_id`를 담아 넘기고** 실행 시 다시 세웁니다 |

> `stancl/tenancy` 같은 패키지를 쓰지 않습니다.
> **테넌트 수십 규모**에서 필요한 것은 위 다섯 줄이고,
> 패키지를 넣으면 **온프레미스 단일 테넌트**에서 오히려 걸리적거립니다.

### 4.2 마이그레이션은 순회한다

```bash
php artisan migrate --database=common --path=database/migrations/common
php artisan mes:migrate-tenants          # 자체 명령 — tenant 목록 순회
```

| 규칙 | 내용 |
|---|---|
| 순서 | 공용 DB 먼저. 테넌트 스크립트가 공용 카탈로그를 참조합니다 |
| 실패 | **그 테넌트만 잠급니다.** 나머지는 정상 기동 |
| 롤백 | **하지 않습니다.** `down()`을 쓰지 않고 되돌리는 마이그레이션을 새로 씁니다 |
| 기록 | `migration_state`(공용 DB)에 테넌트별 버전 |

### 4.3 `tenant_id`는 남습니다

커넥션으로 이미 격리된 뒤에도 컬럼이 있습니다 — **오배치 탐지용**입니다.

```php
// 모델 부트에서
static::saving(function ($m) {
    if ($m->tenant_id !== TenantContext::id()) {
        throw new TenantMismatchException($m);   // 조용히 넘어가면 나중에 못 찾습니다
    }
});
```

## 5. 데이터 접근 — Eloquent와 Query Builder를 나눈다

| | 쓰는 곳 | 이유 |
|---|---|---|
| **Eloquent** | 마스터 CRUD · 단건 저장 | 관계 · 이벤트 · 검증이 그대로 필요합니다 |
| **Query Builder** | **목록 · 집계 · 리포트** | 조인이 많고 **N+1이 곧 사고**입니다 |

```
품목 저장          Eloquent        모델 하나
LOT 재고현황       Query Builder   잔고 + LOT + 라벨 조인 + 커스텀 슬롯
부족 시점 조회     Query Builder   수불 예정 집계
공정실적 목록      Query Builder
원장 기록          Eloquent        한 건씩 정확하게
```

> **원장(`stock_ledger`)은 Eloquent로 쓰고 Query Builder로 읽습니다.**
> 쓰기는 한 건씩 정확하게, 읽기는 뭉쳐서 빠르게 — 성격이 다릅니다.

**목록 화면에서 Eloquent 컬렉션을 쓰지 않습니다.** 50줄 그리드에 관계가 3개 붙으면
쿼리가 150개가 됩니다. 목록은 **한 쿼리로** 가져옵니다.

### 커스텀 컬럼

슬롯은 **사전 생성된 실제 컬럼**이라 그냥 `select`됩니다
([커스텀 컬럼 §4](./커스텀-컬럼-설계.md)). 동적 DDL도, 동적 SQL도 없습니다.
화면이 `custom_field_def`를 읽어 **어느 슬롯이 무슨 이름인지** 매핑합니다.

## 6. API 규약

**REST + JSON.** 온프레미스에서 문제가 생기면 **브라우저 네트워크 탭만으로 원인을 봐야** 합니다.

```
GET    /api/items                 목록 (페이징 · 정렬 · 검색)
POST   /api/items                 생성
PUT    /api/items/{id}            수정
POST   /api/work-orders/{id}/ops/{seq}/scan     동작은 동사로
```

| 규칙 | 내용 |
|---|---|
| 경로 | **복수형 소문자 케밥** — `work-orders` |
| 검증 | **FormRequest**에서. 컨트롤러에서 `if`로 검사하지 않습니다 |
| 응답 | **API Resource**로 변환. 모델을 그대로 내보내지 않습니다 |
| 페이징 | `?page=1&per_page=50&sort=item_cd&order=asc` |
| 날짜 | `yyyy-MM-dd` / `yyyy-MM-dd HH:mm:ss` |
| 숫자 | 수량 · 금액은 **문자열이 아니라 숫자**. `DECIMAL(18,6)` 정밀도 유지 |

### 응답 봉투

```json
{ "data": { }, "meta": { "total": 128, "page": 1 } }
{ "error": { "code": "E_STOCK_NEGATIVE", "message": "…", "field": "qty" } }
```

**Laravel 기본 검증 응답(`errors` 객체)도 이 봉투로 감쌉니다** — 예외 핸들러 한 곳에서.
프런트가 두 가지 형식을 다루게 하지 않습니다.

### 6.1 실행 결과 알림 — 공용 인터페이스

**저장했다 · 음수로 남았다 · 자동 출고했다.** 이런 문구를 화면마다 하드코딩하면
같은 처리가 화면에 따라 다르게 말합니다.

> **문구는 서버가 정합니다.** 응답 봉투에 `notice`를 얹어 내려보내고,
> 프런트 공용 컴포저블이 **자동으로 띄웁니다.**

```ts
interface ApiNotice {
  level: 'success' | 'info' | 'warn' | 'error'
  message: string          // 한 줄 — 토스트 제목
  detail?: string          // 여러 줄 — 펼쳐 보기
  code?: string            // E_ / W_
  sticky?: boolean         // 자동으로 안 닫힘 (경고 · 오류 기본값)
}

interface ApiResponse<T> {
  data: T
  meta?: { total: number; page: number; perPage: number }
  notice?: ApiNotice       // 있으면 띄웁니다. 없으면 조용히 지나갑니다
}
```

```json
// 자재를 투입했는데 재고가 없어 음수로 남은 경우 — 성공입니다
{
  "data": { "consumed": 3 },
  "notice": {
    "level": "warn",
    "code": "W_STOCK_NEGATIVE",
    "message": "자재를 투입했습니다. 와셔 6이 음수 재고로 남았습니다",
    "detail": "MT-WSH-06 · -400 EA · 음수재고 미결(INV-08)에서 해소하세요",
    "sticky": true
  }
}
```

#### 경고는 성공에 실려 옵니다

**이것이 이 시스템의 핵심입니다.** 음수 재고 · 소급 · 자재 부족 · 기준 초과는
**전부 성공하고 경고합니다**([§11 에러 코드](#11-시간--에러--로깅)).

| 상황 | HTTP | 봉투 |
|---|---|---|
| 그냥 성공 | `200` | `data` — `notice` 없음 |
| **성공 + 경고** | **`200`** | `data` + **`notice.level = warn`** |
| 검증 실패 | `422` | `error` + `notice.level = error` |
| 막힘 (`E_`) | `409` | `error` + `notice.level = error` |

**`W_`를 4xx로 내려보내지 않습니다.** 저장은 됐으니까요 —
프런트가 실패로 처리하면 화면이 롤백되고 사용자는 다시 입력합니다.

#### 프런트는 한 줄로 씁니다

```ts
// composables/useApi.ts — notice 를 자동으로 띄웁니다
const { data } = await api.post('/api/work-orders/14/materials/consume')
// 토스트는 이미 떠 있습니다. 화면 코드에 try/catch 가 없습니다
```

| 규칙 | 내용 |
|---|---|
| **문구** | **서버가 정합니다.** 프런트가 "저장되었습니다"를 하드코딩하지 않습니다 |
| **자동** | `useApi()`가 `notice`를 보고 띄웁니다. 화면마다 토스트를 부르지 않습니다 |
| **끄기** | 직접 제어할 때만 `api.post(url, body, { silent: true })` |
| **오류** | `error` 응답은 **언제나** 띄웁니다. 조용히 실패하지 않습니다 |
| **표시** | `CMP-05 MesToast` — 성공 3초 · 경고·오류 **수동 닫기** |

**서버가 말하게 하는 이유** — 같은 API를 여러 화면이 부릅니다.
자재 투입은 `PRD-06`에서도 `INV-03`에서도 일어나는데,
**둘이 다르게 말하면 같은 일인지 사용자가 모릅니다.**

| 현장 로그인 | **개인 QR 스캔**(§7.1). 비밀번호를 대체하지 않고 **지름길**로 씁니다 |

### 7.1 QR 로그인 — 현장 단말

**장갑 낀 손으로 아이디와 비밀번호를 치게 할 수 없습니다.**
로그인 화면에서 **[QR 로그인]** 버튼을 누르고 **개인 QR을 찍으면** 들어갑니다.

```
로그인 화면 → [QR 로그인] → 스캔 대기 → U-7f3a9c21…  → 로그인
                             (CMP-04 그대로 씁니다)
```

#### QR에 무엇이 들어가는가

```
U-7f3a9c21b8e4…      불투명한 랜덤 토큰 32바이트
```

| 규칙 | 내용 |
|---|---|
| 내용 | **랜덤 토큰뿐.** 아이디 · 비밀번호 · 사번을 넣지 않습니다 |
| 저장 | 서버는 **SHA-256 해시만** 보관합니다. 평문은 **발급 시 한 번** 인쇄하고 버립니다 |
| 접두 | **`U-`** — 작업지시(`W-`) · 자재 LOT과 형식으로 갈립니다 |
| 유효 범위 | **로그인 화면에서만.** 로그인 뒤 화면에서 `U-`를 읽으면 무시합니다 |
| 대상 | **`qr_login_enabled` 가 켜진 계정만.** 꺼져 있으면 읽어도 거부합니다 |
| 재발급 | **재인증을 거쳐야** 발급됩니다. 발급 순간 **이전 QR은 즉시 무효**입니다(§7.1-1) |

#### 켠 사람만 씁니다 — opt-in

**QR 로그인은 기본이 꺼져 있습니다.** 쓰겠다고 한 사람만 켭니다.

```
마이페이지 · 로그인 설정
  [ ] QR 로그인 사용        ← 켜야 발급 버튼이 살아납니다
```

```sql
-- user_account 에 추가
--   qr_login_enabled  BOOLEAN NOT NULL DEFAULT FALSE
```

| 규칙 | 내용 |
|---|---|
| 기본값 | **꺼짐.** 전원에게 발급해 두지 않습니다 |
| 켜는 사람 | **본인**(마이페이지 `SYS-10`). 관리자도 대신 켤 수 있습니다 |
| 발급 | **켜져 있어야** 발급 버튼이 활성됩니다 |
| 로그인 | **켜져 있어야** QR이 먹힙니다. 꺼진 계정의 QR은 **읽어도 거부**됩니다 |
| 끄면 | **기존 QR이 즉시 무효.** 끄는 것이 곧 폐기입니다 |
| 관리자 | 시스템관리자 · 업체관리자는 **켤 수 없습니다**(§아래) |

> **전원 발급해 두면 안 쓰는 카드가 서랍에 방치됩니다.** 그게 유출 경로입니다 —
> 쓰지 않는 사람의 자격증명이 세상에 존재하지 않는 것이 가장 안전합니다.

테넌트 정책이 `auth.qr_login = OFF`면 **이 체크박스 자체가 보이지 않습니다.**

#### QR은 복사되는 자격증명입니다

**사진 한 장이면 끝납니다.** 이 사실을 전제로 경계를 잡습니다.

| 경계 | 값 |
|---|---|
| **관리자 금지** | 시스템관리자 · 업체관리자는 **QR 로그인 불가.** 현장 작업자 계정만 |
| **유휴 타임아웃** | 무동작 **10분**이면 자동 로그아웃(`auth.qr_idle_minutes`) |
| **PIN 병행** | 필요하면 QR + 4자리 PIN(`auth.qr_login = QR_PIN`) |
| **비밀번호 대체 아님** | 비밀번호 로그인은 그대로 남습니다. QR은 **현장 단말용 지름길** |

> **유휴 타임아웃이 핵심입니다.** 현장 단말은 **공용**입니다 —
> 한 사람이 로그인하고 안 나가면 **다음 사람 실적이 그 사람 이름으로 남습니다.**
> 누가 만들었는지가 틀리면 불량 추적이 무너집니다.

#### 스키마

```sql
-- user_account (공용 DB) 에 추가
--   qr_login_enabled    BOOLEAN      NOT NULL DEFAULT FALSE   -- 본인이 켠 사람만
--   login_qr_hash       CHAR(64)     NULL   -- SHA-256. 평문은 저장하지 않습니다
--   login_qr_issued_at  DATETIME(6)  NULL
--   login_qr_issued_by  BIGINT       NULL   -- 본인 또는 관리자
--   login_qr_reason     VARCHAR(10)  NULL   -- FIRST | LOST | DAMAGED
--   login_pin_hash      VARCHAR(255) NULL   -- QR_PIN 모드일 때만
```

#### 분실하면 재인증하고 다시 발급합니다

**카드를 잃어버리는 일은 정상적으로 일어납니다.** 재발급 경로를 둘 둡니다.

| 경로 | 화면 | 재인증 |
|---|---|---|
| **본인** | 마이페이지 `SYS-10` | **자기 비밀번호 재입력** |
| **관리자** | 사용자관리 `SYS-02` | **관리자 비밀번호 재입력** |

> **로그인된 세션만으로는 재발급되지 않습니다.** 비밀번호를 다시 받습니다 —
> 켜 둔 태블릿을 남이 집어 자기 QR을 뽑아 가는 것을 막습니다.

```
분실 신고 → 재인증(비밀번호) → 새 토큰 발급 → 인쇄
                                    │
                                    └─ 이전 QR 즉시 무효
```

| 규칙 | 내용 |
|---|---|
| 폐기 시점 | **발급하는 순간.** 이전 카드는 그때부터 안 먹힙니다 |
| 유예 | **없습니다.** 잃어버린 카드를 며칠 더 살려 둘 이유가 없습니다 |
| 사유 | `최초` · `분실` · `훼손` 중 하나를 **반드시** 고릅니다 |
| 기록 | **누가 · 언제 · 왜 · 누구에게** 발급했는지 감사 기록에 남깁니다 |
| 폐기만 | 재발급 없이 **폐기만**도 됩니다 — 퇴사자 · 장기 휴직 |
| 끄기 = 폐기 | **`qr_login_enabled`를 끄면 기존 QR이 그 순간 무효**입니다 |

#### 카드에는 이름을 인쇄합니다

**QR 코드 안에는 토큰만 들어가고, 카드 표면에는 사람 이름이 보입니다.**
둘은 다른 얘기입니다.

```
┌─────────────────────────┐
│   ███ ▚▚ ███ ▚ ███      │   ← QR : 토큰만 (U-7f3a9c21…)
│   ▚ ███ ▚▚ ███ ▚▚       │
│   ███ ▚ ███ ▚▚ ███      │
│                         │
│   김작업                 │   ← 표면 : 이름
│   가공1팀 · 2026-09-02   │   ← 부서 · 발급일
└─────────────────────────┘
```

| 인쇄 | 내용 |
|---|---|
| **QR 데이터** | **토큰뿐.** 이름도 아이디도 사번도 들어가지 않습니다 |
| **카드 표면** | **이름 · 부서 · 발급일.** 로그인 아이디는 인쇄하지 않습니다 |

**이름이 없으면 카드가 섞였을 때 누구 것인지 모릅니다.**
발급할 때도, 주웠을 때도, 반납받을 때도 육안으로 확인할 게 있어야 합니다.

인쇄는 **라벨 템플릿**을 그대로 씁니다([ERD](./ERD.md) §10) — 규격이 업체마다 다릅니다.

#### 정책

| 키 | 값 | 기본 | 편집 |
|---|---|---|---|
| `auth.qr_login` | `OFF` · `QR_ONLY` · `QR_PIN` | **`QR_ONLY`** | **시스템관리자** |
| `auth.qr_idle_minutes` | INT | **10** | 업체관리자 |

**기본을 `QR_ONLY`로 둡니다.** 찍으면 바로 들어가는 것이 요구이고,
위험은 **관리자 금지 + 유휴 타임아웃**으로 낮춥니다 —
PIN을 강제하면 장갑을 벗어야 하고, 그러면 현장이 **한 사람 계정으로 돌려 씁니다.**

### 7.3 로그인 사용자는 언제나 보인다

**공용 단말에서는 "지금 누구로 로그인되어 있는가"가 가장 중요한 정보입니다.**
레이아웃 **상단 오른쪽에 항상** 띄웁니다 — 화면을 옮겨도 사라지지 않습니다.

```
┌──────────────────────────────────────────────────────┐
│  mes-v6      공정실적관리          김작업 · 가공1팀  ⏻ │
└──────────────────────────────────────────────────────┘
                                     └ 이름 · 부서 · 로그아웃
```

| 규칙 | 내용 |
|---|---|
| 위치 | **모든 화면 상단.** 레이아웃에 한 번만 두고 화면이 관여하지 않습니다 |
| 내용 | **이름 · 부서.** 아이디가 아니라 **사람이 알아보는 이름** |
| 로그아웃 | 바로 옆에. **한 번에 닿아야** 다음 사람이 자기로 바꿉니다 |
| 유휴 경고 | 자동 로그아웃 **1분 전**에 남은 시간을 여기에 표시합니다 |

### 7.4 작업자는 로그인 사용자가 기본값이다

실적을 남길 때 **작업자 칸은 로그인한 사람으로 미리 채웁니다.**
**바꿀 수 있습니다** — 한 사람이 단말을 잡고 여러 사람 실적을 대신 넣는 일이 실제로 있습니다.

```
공정실적 · 수량 입력
  작업자   [ 김작업          ▾ ]   ← 로그인 사용자로 채워져 있음
  수량     [ 20 ]
```

#### 입력한 사람과 작업한 사람을 나눕니다

| 컬럼 | 뜻 | 바꿀 수 있나 |
|---|---|---|
| `created_by` | **입력한 사람** — 로그인 사용자 | **못 바꿉니다.** 서버가 씁니다 |
| `operator_id` · `inspector_id` | **작업 · 검사한 사람** | **바꿉니다.** 기본값이 로그인 사용자 |

> **둘이 다르면 "대신 입력"입니다.** 이걸 한 칸으로 합치면
> 대신 넣은 실적이 **누가 넣었는지 사라지고**, 나중에 물어볼 사람이 없습니다.

| 규칙 | 내용 |
|---|---|
| 기본값 | **로그인 사용자.** 대부분 본인이 자기 실적을 넣습니다 |
| 선택 범위 | **같은 부서 사용자**부터 보여 주고 검색으로 넓힙니다 |
| 스캔 | 상대 QR을 찍어 작업자를 **바꿀 수도** 있습니다 — 대신 입력이 잦은 현장 |
| 감사 | `created_by ≠ operator_id`면 **목록에서 표시**합니다 (`대신 입력` 배지) |

**이것이 QR 로그인의 위험을 실제로 낮춥니다.** 남이 로그인해 둔 단말에서 찍어도
작업자 칸이 **그 사람 이름으로 채워져 있는 것이 보이므로** 바꾸게 됩니다
— 자동 로그아웃(§7.1)과 함께 쓰는 두 번째 방어선입니다.

### 7.5 권한은 서버가 검사한다

```php
Route::middleware(['auth:sanctum', 'menu:BAS-02,write'])
     ->put('/api/items/{id}', [ItemController::class, 'update']);
```

| 층 | 검사 |
|---|---|
| 화면 | 읽기 권한 없으면 **메뉴에서 사라집니다** |
| API | **메뉴 코드 단위** read / write 미들웨어 |
| 데이터 | 테넌트 격리는 **커넥션**이 이미 함 |

**화면 ID가 곧 권한 단위입니다**(`BAS-02` · `INV-03`).
메뉴를 숨기는 것은 편의이고, **막는 것은 서버**입니다.

## 9. 배치 · 큐

PHP는 상주하지 않습니다. **스케줄러를 상주 프로세스로 띄웁니다.**

```bash
php artisan schedule:work     # supervisor 또는 systemd 로 상주
```

`crontab`을 고객사 서버에 넣지 않습니다 — 아무도 관리하지 않고, 서버를 옮기면 사라집니다.

| 작업 | 주기 | 내용 |
|---|---|---|
| 재고 스냅샷 | 정책 주기 | 스냅샷 생성 · 더티 재계산 |
| 관측 지표 | 매일 02:00 | `ops_metric_daily` 한 줄 |
| 알림 정리 | 매일 03:00 | 90일 지난 알림 삭제 |
| 정기수주 회차 | 매일 06:00 | 예정 회차 생성 (Phase 2) |

| 규칙 | 내용 |
|---|---|
| 테넌트 순회 | 작업마다 컨텍스트를 **명시적으로 설정**하고 실행 |
| 실패 격리 | 한 테넌트가 실패해도 **나머지는 계속** |
| 중복 방지 | `onOneServer()` — 인스턴스가 여러 대여도 한 번만 |
| 수동 실행 | 시스템관리자 화면에서 **다시 돌릴 수 있어야** 합니다 |

**큐는 Phase 1에서 최소로 씁니다.** 라벨 대량 발행 · 엑셀 대용량 내보내기만
`queue:work`로 넘기고, 나머지는 동기 처리합니다 — 프로세스를 더 늘리지 않기 위해서입니다.

## 11. 시간 · 에러 · 로깅

| 항목 | 값 |
|---|---|
| 저장 | `DATETIME(6)` — **테넌트 로컬 시각.** UTC 변환 안 함 |
| Laravel | `config('app.timezone') = 'Asia/Seoul'` |
| 이중 시간축 | `occurred_at`(물리) · `recorded_at`(전산). **섞지 않습니다** |

**Eloquent의 `created_at`은 `recorded_at`이 아닙니다.** 원장은 두 컬럼을 명시적으로 갖습니다.

### 에러 코드

```
E_  막습니다        E_STOCK_NEGATIVE_BLOCKED · E_CALC_SYNTAX · E_PERM_DENIED
W_  경고만 합니다    W_STOCK_NEGATIVE · W_BACKDATE_LATE · W_MATERIAL_SHORT
```

**이 시스템은 대부분 `W_`입니다.** 음수 재고 · 소급 · 자재 부족 · 기준 초과 —
전부 경고하고 진행합니다. `E_`는 **되돌릴 수 없는 것**에만 씁니다.

### 로깅

```
[2026-09-02 14:20:11] production.INFO: material.issue
  {"tenant":"t3","user":42,"menu":"INV-03","wo":"W-2609-014","items":3,"ms":88}
```

`tenant`를 **모든 줄에** 붙입니다 — 없으면 어느 고객 문제인지 못 찾습니다.
원장 · 조정 · 정책 변경은 **DB에 별도 기록**하고 로그 파일에만 두지 않습니다.

> **코드만 있는 PR은 반려**합니다 — 부품의 겉모습은 그 문서가 계약입니다.

### 12.2 그리드 타입은 인터페이스로 고정한다

**같은 목록 데이터를 그리드만 쓰는 게 아닙니다.** 엑셀 내보내기 · 인쇄 · 모달 선택기 ·
다른 화면이 같은 데이터를 씁니다. **그리드 전용 타입으로 내려받으면 나머지가 전부 오염됩니다.**

> **서버 응답은 도메인 형태로 두고, 그리드에 넣을 때만 마지막에 덧씌웁니다.**

```ts
// 1 ─ 서버 응답 : 도메인. 그리드를 모릅니다
interface StockRow {
  lotId: number
  itemCd: string
  lotNo: string
  qty: number
  looseQty: number
  ext: Record<string, string | number | null>   // 커스텀 슬롯
}

// 2 ─ 목록 봉투 : 모든 목록 API가 같은 모양
interface GridResult<T> {
  rows: T[]
  total: number
  page: number
  perPage: number
}

// 3 ─ 컬럼 정의 : 우리 타입. tui-grid 옵션이 아닙니다
interface MesColumn<T> {
  key: (keyof T & string) | `ext.${string}`
  header: string
  width?: number
  align?: 'left' | 'right' | 'center'
  format?: (row: T) => string
  render?: (row: T) => VNode
  tree?: boolean
}

// 4 ─ 어댑터 : 여기서만 tui-grid 를 압니다
// components/mes/MesGrid.vue
```

| 규칙 | 내용 |
|---|---|
| **서버 응답** | 그리드를 모릅니다. 폼 · 계산 · 다른 화면이 **같은 타입**을 씁니다 |
| **봉투** | `GridResult<T>` **하나로 고정.** 목록 API가 전부 같은 모양입니다 |
| **컬럼** | `MesColumn<T>` — 우리 타입. 화면이 tui-grid 옵션을 **직접 쓰지 않습니다** |
| **import** | **`tui-grid`를 `import` 하는 파일은 `MesGrid.vue` 하나** |

```
                    ┌─ 그리드      MesGrid 가 MesColumn 으로 씌움
GridResult<StockRow>├─ 엑셀        같은 rows 를 그대로
                    ├─ 인쇄        같은 rows 를 그대로
                    └─ 모달 선택기  같은 rows 를 그대로
```

**이렇게 두면 세 가지가 따라옵니다.**

- 같은 목록 데이터를 **엑셀 · 인쇄 · 선택기가 그대로** 씁니다 — 변환이 없습니다
- **그리드를 바꿔도 화면 코드가 안 바뀝니다** — `MesGrid.vue` 하나만 고칩니다
- 커스텀 컬럼이 `ext.*` 키로 **런타임에 컬럼을 추가**해도 타입이 안 깨집니다

> `tui-grid`가 화면 파일에 `import` 되는 순간 이 구조가 무너집니다.
> **린트 규칙으로 막습니다** — `MesGrid.vue` 외의 `tui-grid` import 금지.

### 12.3 화면은 페이지와 모달 둘 다로 열린다

**같은 화면이 두 가지로 열립니다.**

```
품목등록을 메뉴에서      →  /master/items/new         페이지
수주등록에서 새 품목을   →  모달                       같은 내용
```

이걸 두 번 만들면 **검증 규칙이 갈라집니다.** 한 번만 만들고 껍데기를 바꿉니다.

```
components/features/item/
  ItemForm.vue          ← 내용. 이것만 있으면 됩니다
pages/master/items/
  [id].vue              ← ItemForm 을 페이지로 감쌉니다
composables/
  useItemModal.ts       ← ItemForm 을 모달로 엽니다
```

#### 본체가 지켜야 할 것

```vue
<!-- ItemForm.vue -->
<script setup lang="ts">
const props = defineProps<{ id?: number }>()
const emit  = defineEmits<{ saved:[Item]; cancel:[] }>()
// ❌ useRouter() 를 여기서 부르지 않습니다 — 모달에서 깨집니다
// ❌ 저장 후 이동을 여기서 하지 않습니다 — 감싼 쪽이 정합니다
</script>
```

| 규칙 | 내용 |
|---|---|
| **라우터를 모릅니다** | 본체 안에서 `useRouter()` · `navigateTo()` 금지 |
| **끝을 알립니다** | `saved` · `cancel` **이벤트만** 냅니다 |
| **닫기를 모릅니다** | 모달을 닫는 것은 감싼 쪽의 일입니다 |
| **제목을 모릅니다** | 페이지 헤더 · 모달 타이틀은 감싼 쪽이 답니다 |

#### 감싸는 쪽

```vue
<!-- pages/master/items/[id].vue -->
<ItemForm :id="id" @saved="navigateTo('/master/items')" @cancel="back()" />
```

```ts
// useItemModal.ts
const item = await openModal(ItemForm, { id })   // saved 페이로드를 돌려줍니다
```

**모달은 값을 돌려줍니다.** 수주등록에서 품목을 만들면 그 품목이 그대로
선택 상태가 됩니다 — 저장하고 목록을 다시 불러 찾게 하지 않습니다.

> [화면목록 §5](./screens/00-화면목록.md)의 **단건은 팝업, 다건은 이동**이
> 이 구조로 구현됩니다. 팝업은 **전용 화면의 폼을 그대로 빌려 씁니다** —
> 같은 처리를 두 곳에 구현하면 검증 규칙이 갈라집니다.

장갑 낀 손으로 목록을 뒤지다 그냥 종이에 적습니다.

### 12.5 브라우저는 Chrome · Edge만

**둘만 지원합니다.** Firefox · Safari · IE는 대상이 아닙니다.

| | 값 |
|---|---|
| 지원 | **Chrome** · **Edge** — 최근 2개 메이저 버전 |
| 빌드 타깃 | 그에 맞춰 잡습니다. **레거시 폴리필을 넣지 않습니다** |

**둘 다 Chromium이라 사실상 한 엔진입니다.** 렌더링 차이를 다루는 비용이 없어지고,
번들이 가벼워지며, **바코드 스캐너 · 인쇄 · 웹소켓을 한 곳에서만 검증**하면 됩니다.

| 이 결정이 지우는 것 | |

> 진짜 문제는 **IE 전용 사내 시스템과 같은 PC를 쓰는 경우**이고, 그건 탭을 나눠 씁니다.

## 13. 빌드 · 배포

### 13.1 산출물

```
mes/
  app/ … vendor/          Laravel (composer install --no-dev)
  public/                 Nuxt 빌드 결과 (정적)
  .env                    환경 설정
docker-compose.yml        온프레미스 설치 패키지
```

**Nuxt 빌드 결과를 `public/`에 넣습니다.** 웹서버를 따로 세우지 않습니다.

### 13.2 배포는 Docker입니다 — 확정

**Nginx · PHP-FPM · Reverb · 스케줄러** 넷이 돕니다.
고객사 담당자에게 넷을 각각 관리하게 할 수 없습니다.

```yaml
# docker-compose.yml — 온프레미스 표준 설치
services:
  app:        # php-fpm + nginx
  reverb:     # php artisan reverb:start
  scheduler:  # php artisan schedule:work
  db:         # mariadb (고객사 DB를 쓰면 뺍니다)
```

```bash
docker compose up -d        # 설치 · 기동
docker compose restart app  # 담당자가 할 수 있는 유일한 조치
```

#### Docker를 설치 요구사항에 넣습니다

**supervisor · NSSM 같은 대안 구성을 만들지 않습니다.**
넷을 각각 서비스로 등록하는 절차는 고객사마다 달라지고,
장애가 나면 **어느 프로세스가 죽었는지부터** 찾아야 합니다.

| 항목 | 요구사항 |
|---|---|
| OS | **Linux** — Ubuntu 22.04 LTS 이상 · **Windows** — Server 2022 이상 또는 11 Pro |
| 런타임 | **Docker Engine 24 이상** · Compose v2 |
| 자원 | 2 vCPU · 4GB RAM · 50GB (테넌트 1개 기준) |
| 네트워크 | 사내망만으로 동작. **외부 연결이 없어도 됩니다** |
| DB | 컨테이너로 띄우거나 **고객사 MariaDB에 연결** |

> **Docker를 못 쓰는 고객사는 계약 전에 걸러집니다.**
> 나중에 supervisor 구성을 급조하는 것보다 낫습니다 —
> 그렇게 만든 설치본은 **우리도 재현하지 못하고**, 장애 대응이 매번 처음이 됩니다.

**담당자가 아는 명령은 셋이면 충분합니다.**

```bash
docker compose up -d          # 설치 · 기동
docker compose restart app    # 이상하면 이것부터
docker compose logs -f app    # 그래도 안 되면 이걸 보내 주세요
```

### 13.3 Windows 서버 — WSL2 + Docker Engine

**국내 제조 현장은 Windows 서버가 흔합니다.** 1급 지원 대상으로 잡습니다.

| 항목 | 값 |
|---|---|
| 최소 버전 | **Windows Server 2022** 또는 **Windows 11 Pro** — WSL2가 정식 지원되는 선 |
| 설치 방식 | **WSL2 + Docker Engine** (Ubuntu 배포판 안에 직접) |
| **Docker Desktop** | **쓰지 않습니다** — 규모에 따라 **유료**이고, GUI가 서버에 필요 없습니다 |

```powershell
wsl --install -d Ubuntu-22.04          # WSL2 + Ubuntu
# Ubuntu 안에서
curl -fsSL https://get.docker.com | sh  # Docker Engine
```

#### 볼륨은 WSL2 안에 둡니다 — 여기서 사고가 납니다

**Windows 파일시스템(`/mnt/c/...`)에 볼륨을 두면 DB가 몇 배 느려집니다.**
9p 프로토콜을 거치기 때문이고, 처음엔 돌아가다가 데이터가 쌓이면 드러납니다.

```yaml
volumes:
  db:    # ✅ 이름 있는 볼륨 — WSL2 내부 ext4
  files:
# ❌ - /mnt/c/mes/db:/var/lib/mysql     이렇게 쓰지 않습니다
```

| 대상 | 위치 |
|---|---|
| DB 데이터 | **이름 있는 볼륨**(WSL2 내부) |
| 첨부 파일 | **이름 있는 볼륨**(WSL2 내부) |
| 백업 산출물 | **`/mnt/c/...`로 내보냅니다** — 여기만 Windows 쪽 |

#### 재부팅해도 스스로 떠야 합니다

고객사 서버는 **정전과 윈도우 업데이트로 재부팅됩니다.**
담당자가 매번 WSL에 들어가 명령을 치게 할 수 없습니다.

```yaml
services:
  app:
    restart: unless-stopped     # 모든 서비스에
```

```powershell
# 작업 스케줄러 — 시스템 시작 시
wsl -d Ubuntu-22.04 -u root -e sh -c "service docker start && cd /srv/mes && docker compose up -d"
```

WSL2는 **접속이 없으면 종료**되므로, 위처럼 부팅 시 한 번 깨워 줘야 합니다.

#### 백업은 Windows 폴더로 내보냅니다

```bash
docker compose exec -T db mariadb-dump --all-databases \
  > /mnt/c/mes-backup/$(date +%F).sql
```

**고객사 백업 정책이 Windows 폴더를 대상으로** 돌아가는 경우가 대부분입니다.
WSL2 안의 볼륨은 그 대상에 안 잡히므로 **내보내는 단계가 반드시 필요합니다.**

#### 이미 MariaDB가 깔려 있으면

```yaml
# db 서비스를 빼고
DB_HOST=host.docker.internal
```

Windows에 이미 MariaDB가 돌고 있으면 **컨테이너를 하나 덜 띄웁니다.**
백업 · 모니터링이 이미 그쪽에 걸려 있는 경우가 많습니다.

### 13.4 설치는 타입을 골라 시작하고, 고른 값을 남깁니다

**Linux와 Windows는 달라지는 것이 몇 개뿐입니다.** 그 몇 개를 오버레이로 분리하고,
**고른 타입을 설정에 적어** 이후 동작이 그걸 보게 합니다.

```
docker-compose.yml            공통 — 서비스 정의
docker-compose.linux.yml      Linux 오버레이
docker-compose.windows.yml    Windows 오버레이
install.sh  /  install.ps1    타입을 고르고 .env 를 씁니다
```

#### 설치

```bash
./install.sh              # Linux
```
```powershell
.\install.ps1            # Windows — WSL2 안에서
```

설치 스크립트가 하는 일은 셋뿐입니다.

1. **호스트 타입 확인** — 자동 감지하고 화면에 보여 준 뒤 확정을 받습니다
2. **`.env` 작성** — 타입과 그에 딸린 경로를 씁니다
3. **기동** — `docker compose up -d`

#### 고른 값은 `.env`에 남습니다

```ini
# .env — 설치 스크립트가 씁니다
MES_HOST_OS=WINDOWS                 # LINUX | WINDOWS
MES_BACKUP_PATH=/mnt/c/mes-backup
COMPOSE_FILE=docker-compose.yml:docker-compose.windows.yml
```

**`COMPOSE_FILE`을 `.env`에 두는 것이 핵심입니다.**
이후 담당자는 오버레이를 몰라도 됩니다 — 명령이 그대로입니다.

```bash
docker compose up -d          # 오버레이가 자동으로 붙습니다
docker compose restart app
docker compose logs -f app
```

#### 무엇이 달라지는가

| | Linux | Windows |
|---|---|---|
| 백업 경로 | `/var/backups/mes` | **`/mnt/c/mes-backup`** — 고객사 백업이 도는 곳 |
| 호스트 DB 접근 | `extra_hosts: host-gateway` **필요** | 기본 제공 |
| 자동 시작 | **systemd** 유닛 | **작업 스케줄러** + `wsl` 기동 |
| 타임존 | `/etc/localtime` 바인드 | `TZ` 환경변수 |

**볼륨은 양쪽 다 이름 있는 볼륨입니다.** 여기는 안 갈립니다 —
Windows에서 바인드 마운트를 쓰면 느려지는 문제(§13.3)를 **애초에 못 쓰게** 둡니다.

#### 앱이 이 값을 압니다

```yaml
mes:
  deployment: ONPREMISE        # CENTRAL | ONPREMISE
  host-os: ${MES_HOST_OS}      # LINUX   | WINDOWS
```

| 쓰는 곳 | 내용 |
|---|---|
| **로그** | 모든 줄에 `host_os`. 지원 요청이 오면 **어느 환경인지 먼저** 압니다 |
| **운영 지표**(`TRC-02`) | 호스트 타입 · Docker 버전 · 볼륨 종류를 표시합니다 |
| **백업 안내** | 화면 문구가 그 환경의 실제 경로를 말합니다 |
| **부팅 자가진단** | `WINDOWS`인데 DB 볼륨이 **바인드 마운트면 경고 로그** — §13.3의 사고를 막습니다 |

> **환경을 짐작하지 않습니다.** 온프레미스 지원은 *"거기 서버가 뭐예요"* 부터 묻다가
> 반나절이 갑니다. **설정에 적혀 있으면 로그 한 줄로 끝납니다.**

### 13.5 배포 형태

| | 중앙 `CENTRAL` | 온프레미스 `ONPREMISE` |
|---|---|---|
| 실행 | **docker compose** | **docker compose** — 같습니다 |
| 파일 | S3 호환 | 로컬 볼륨 |
| 업데이트 | CI 배포 | **이미지 교체 + `up -d`** |
| 관리 서버 | 항상 연결 | **선택** — 없어도 동작 |

```bash
docker compose up -d db        # MariaDB
php artisan serve              # :8000
pnpm dev                       # :3000 (프록시)
php artisan reverb:start       # 웹소켓
```

> **E2E를 넓게 깔지 않습니다.** *"수주 1건이 자재 입고 → 작업지시 → 스캔 실적 →
> 검사 → 출하까지 완결"* 을 **한 개의 시나리오로** 자동화하고,
> 그것만 항상 녹색으로 유지합니다.

## 16. 미결

| # | 항목 | 확인 필요 |
|---|---|---|
| 1 | **인증 연동** | 자체 로그인 + QR만인지, 고객사 AD · SSO 요구가 있는지 |
| 2 | **동시 접속 규모** | 테넌트당 동시 사용자 수 — **PHP-FPM 워커 수와 Reverb 세션 수**를 여기서 잡습니다 |

> 해결됨 — *브라우저*: **Chrome · Edge 최근 2개 메이저**만. 둘 다 Chromium이라 **폴리필 · 렌더링 분기 · 인쇄 CSS 분기가 전부 사라집니다**(§12.5).
> 해결됨 — *배포 방식*: **Docker 확정.** `docker compose` 하나로 갑니다.
> **Docker를 설치 요구사항에 넣고**, 못 쓰는 고객사는 계약 전에 거릅니다 —
> supervisor · NSSM 대안 구성을 만들지 않습니다(§13.2).
> 해결됨 — *그리드*: **TUI Grid**. 트리 데이터가 기본이라 `SAL-01` 수주 트리가 해소됩니다.
> 해결됨 — *페이지 · 모달 병행*: **본체 컴포넌트 + 껍데기** 구조(§12.2). 본체는 라우터를 모릅니다.

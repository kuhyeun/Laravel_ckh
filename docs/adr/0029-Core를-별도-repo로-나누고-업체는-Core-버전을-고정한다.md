# ADR 0029. Core 를 별도 repo 로 나누고, 업체는 Core 버전을 고정한다

- 상태: 제안 ( 2026-10-28 정리 · **아직 실행하지 않음** — 분리는 두 번째 업체 착수 직전 )
- 날짜: 2026-10-28
- 관련: ADR 0028 ( Core 와 업체의 경계 · 바꿔 끼우는 방법 ) · ADR 0027 ( 업체별 설치 ) · ADR 0018 ( docker-compose 배포 ) · `repo_분리_가이드.txt`

## 배경

ADR 0028 은 **무엇을 Core 에 두고 업체가 어떻게 바꿔 끼우나**를 정했다. 이 문서는 **repo 를 어떻게 나누고 Core 변경을 업체에 어떻게 반영하나**를 정한다.

지금은 한 repo 안에 `packages/mes-core`( Core ) 와 `src/`( 업체 1곳 ) 가 있고, Composer path repository 로 연결돼 있다.

2026-10-28 회의 결과 :
- 설계 문서대로 전부 만들면 기간이 길고 처음부터 기능이 많아 가이드를 잡기 어렵다 → **Core 는 기본 기능만, 업체별 필요는 업체 repo 에서 추가**
- 예상 업체 **약 3곳**
- 업체별 주 담당자는 다를 수 있지만 **같은 팀**이 개발
- 업데이트는 정기 배포가 아니라 **요청이 오면 수정해 주는 방식** → **업체마다 업데이트 시점이 다르다**

## 검토한 대안

| 대안 | 구조 | 버린 이유 |
|---|---|---|
| A. 업체마다 통째로 복사( fork ) | 업체마다 프로젝트 전체 사본 | Core 버그 수정 · 보안 패치를 업체 수만큼 병합해야 한다. 업체가 늘수록 사실상 별개 제품 |
| C. 한 repo 에 Core + 업체 폴더 여러 개 | `packages/mes-core` + `companies/a` · `companies/b` · `companies/c` | 같은 팀 · 3곳 규모에는 가장 가볍지만, **업체마다 Core 시점을 다르게 둘 수 없다**. 업체 A 요청으로 Core 를 고치면 B · C 도 다음 배포 때 요청하지 않은 변경을 받는다. A 만 예전 상태로 두려면 예전 커밋에서 갈래를 따야 해 금방 꼬인다 |

## 결정

### 1. 구조 — Core repo 하나 + 업체 repo 업체마다

**Core repo ( `mes-core` )** = 제품
```
src/                  업무 로직 ( 서비스 · 컨트롤러 · 모델 )
routes/               API
resources/js/         화면 · 공통 컴포넌트
resources/excel/      기본 엑셀 양식
database/migrations/  Core 테이블
config/               menus.php · system_config.php 기본값
CHANGELOG.md          버전별 변경
```

**업체 repo ( `mes-업체명` )** = 얇게
```
composer.json             "mes-core": "^1.4"  ← 이 업체가 쓰는 Core 버전
config/mes.php            켤 모듈 · 계산식 변수
config/menus.php          ( 있으면 ) 업체 메뉴 추가
database/migrations/      업체 전용 테이블 · 칸만
database/seeders/         업체 초기 데이터
app/Modules/              업체 전용 기능 · 바꿔 끼운 서비스 ( ADR 0028 의 3 · 5 단계 )
resources/js/Pages/       바꿔 끼운 화면 ( ADR 0028 의 4 단계 )
resources/excel/          업체 엑셀 양식
docker-compose · .env     설치 설정
CUSTOM.md                 이 업체에서 Core 를 바꿔 끼운 목록 ( Core 를 올릴 때 확인할 곳 )
```

- 저장소는 **비공개 GitHub repo** 로 충분하다. Composer 가 비공개 repo 의 태그를 직접 가져온다 ( Packagist 불필요 )

### 2. 업데이트 흐름

| 요청 | 처리 |
|---|---|
| 업체 전용 수정 | 그 업체 repo 만 고치고 배포. Core · 다른 업체는 그대로 |
| Core 수정이 필요 | Core 수정 → 새 버전 태그 → **그 업체만** 새 버전으로 올려 배포. 다른 업체는 자기 요청이 올 때 올린다 |

업체를 올릴 때 : `composer update mes-core` → `CHANGELOG.md` · 업체 `CUSTOM.md` 확인 → `migrate` → 필요한 시더만( `--class` ) → 배포

### 3. 운영 규칙

1. **옛 버전은 고쳐 주지 않는다** — 업체 요청에 Core 수정이 필요하면 그 업체를 **최신 Core 로 올리면서** 반영한다. 버전마다 따로 고치면 Core 갈래가 업체 수만큼 생긴다. **긴급 장애만 예외** ( 그 버전에 수정 태그 `1.2.1` )
2. **버전 번호**
   - 기존 동작이 바뀜 · 업체 쪽 수정이 필요함 → `1.x` → `2.0`
   - 기능 추가 → `1.4` → `1.5`
   - 버그 수정 → `1.5.0` → `1.5.1`
3. **CHANGELOG** — 버전마다 바뀐 것 · 업체가 할 일( 시더 실행 · 설정 확인 등 )을 적는다
4. **Core 마이그레이션은 추가만** — 칸 삭제 · 이름 변경 · 타입 축소를 하지 않는다. 그래야 업체를 몇 버전 건너뛰어 올려도 안전하다. 꼭 바꿔야 하면 새 칸을 추가하고 옛 칸은 남긴 채 메이저 버전에서 정리
5. **업체 마이그레이션은 Core 다음** — 업체 테이블은 Core 테이블을 참조할 수 있지만 Core 테이블을 직접 고치지 않는다 ( 칸이 필요하면 예비 칸 또는 업체 테이블 1:1 )
6. **개발은 path, 배포는 태그** — 업체 repo 에서 Core 를 같이 고칠 때는 로컬 경로로 연결( 지금 방식 ), 배포 설정만 버전 태그를 가리킨다
7. **Core 는 업체 코드( `App\` )를 참조하지 않는다** ( ADR 0028 )

### 4. 분리 시점

- **두 번째 업체 착수 직전**. 업체가 하나일 때는 버전을 고정할 이유가 없고, Core 를 크게 고치는 시기라 절차만 늘어난다
- 그 전까지는 지금처럼 한 repo 로 두되, 위 규칙( 특히 5 · 7 )은 지금부터 지킨다

## 결과

- 업체마다 자기 요청이 올 때만 Core 변경을 받는다. 요청하지 않은 업체에 테스트하지 않은 변경이 들어가지 않는다
- 업체 전용 수정은 Core 를 건드리지 않고 그 업체 repo 에서 끝난다
- 대신 **버전 태그 · CHANGELOG · 업체 올리기 절차**라는 운영 비용이 생긴다. 3곳 · 같은 팀이면 감당할 수준
- 업체마다 Core 버전이 달라, 오래 안 올린 업체는 한 번에 여러 버전을 건너뛰게 된다 → 마이그레이션 "추가만" 규칙과 CHANGELOG 로 대비
- 옛 버전 백포트를 하지 않으므로, 요청이 오면 그 업체는 사이의 Core 변경도 함께 받는다 ( 업체 확인 범위가 넓어질 수 있음 )

# ADR 0027. 업체 DB에 tenant_id를 두지 않는다

- 상태: 채택
- 날짜: 2026-10-08
- 관련: `docs/멀티테넌시-설계.md` §4 · §5 · ADR 0002 ( `tenant_id` 부분을 대체 )

## 배경

ADR 0002 는 업체마다 DB 를 나누면서도 `tenant_id` 컬럼을 모든 업체 테이블에 남기기로 했다.
기준정보 11개 화면을 만드는 동안 `tenant_id` 없이 진행했고, 업무 테이블은 수가 많아
넣을 거면 업무 모듈 전에 정해야 했다.

배포는 **업체별 설치가 주력**이고, SaaS( 한 서버 여러 업체 )는 나중에 붙일 수 있으면 된다.

## 검토한 대안

| 대안 | 문제 |
|---|---|
| 설계대로 모든 테이블에 `tenant_id` + 저장 시 컨텍스트와 대조 | 새 행의 값도 같은 컨텍스트에서 채우므로 **연결을 잘못 바꾼 상황에서는 값이 일치해 잡지 못한다**. 모든 테이블 · 유니크 키 · 모델 · 시더에 비용이 들고 기준정보 소급도 필요 |
| 로그인 계정을 공용 DB 로 올려 업체를 판단 ( 설계 §5 ) | 로그인 · 권한 · 메뉴 코드를 공용 / 업체 두 연결로 나눠야 한다. 업체별 설치에서는 얻는 것이 없다 |

## 결정

- 업체 테이블에 **`tenant_id` 를 두지 않는다**
- 잘못된 DB 탐지는 **업체 DB 마다 자기 식별 1행**을 두고 **연결할 때 한 번 대조**한다 ( SaaS 미들웨어를 만들 때 함께 )
- SaaS 에서 업체는 **접속 주소( 서브도메인 )나 로그인 때 회사 코드**로 정한다. 계정 · 메뉴 · 권한 · 정책은 지금처럼 **업체 DB 에 그대로** 둔다. 공용 쪽에는 업체 목록 정도만 둔다
- 지금은 연결 교체 없이 "설치 하나 = 업체 DB 하나"로 돈다. 업무 코드는 아래 규칙을 지켜 나중에 미들웨어만 끼우면 되게 한다
  - DB 이름 · 연결 이름을 코드에 쓰지 않는다
  - 캐시 키에 DB 이름을 넣는다
  - 파일 저장 경로에 업체 구분 폴더를 둔다
  - 큐 · 배치 작업에는 업체 정보를 담아 넘긴다

## 결과

- 업무 테이블 · 기준정보 테이블에 컬럼 · 인덱스 · 저장 검사가 붙지 않는다
- SaaS 전환 작업이 **업체 목록 + 연결 교체 미들웨어 + 업체 순회 마이그레이션**으로 좁혀진다. 업무 코드는 고치지 않는다
- 행 단위로 합치는 길은 닫힌다 ( ADR 0002 가 이미 버린 길 )
- DB 를 옮기거나 집계할 때 출처는 행이 아니라 **DB 단위**로 붙여야 한다
- 같은 로그인 아이디가 업체마다 있을 수 있으므로, SaaS 로그인은 업체를 먼저 정해야 한다

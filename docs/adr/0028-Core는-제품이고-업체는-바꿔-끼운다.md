# ADR 0028. Core 는 제품이고, 업체는 바꿔 끼운다

- 상태: 제안 ( 2026-10-27 정리 · **아직 실행하지 않음** — 아래 "할 일"은 두 번째 업체 요구가 오거나 필요할 때 진행 )
- 날짜: 2026-10-27
- 관련: `packages/mes-core` · `src/` · `src/config/mes.php` · ADR 0013 ( 정책 ) · ADR 0027 ( 업체별 설치 ) · `docs/커스텀-컬럼-설계.md` · **ADR 0029 ( repo 구조 · 버전 운영 — 할 일 5번 "repo 분리"를 이어받음 )**

## 배경

처음에는 Core( `packages/mes-core` ) 에 **플랫폼**( Auth · Menu · Basic )만 두고,
업무 모듈은 업체 프로젝트( `src/app/Modules` )에서 만들 생각이었다.

실제로 개발해 보니 수주 · 구매 · 재고 · 생산 · 품질이 **모두 Core 에** 들어갔고,
`src/app/Modules` 6개는 빈 폴더( `.gitkeep` · TODO 라우트 )로 남았다 ( 2026-10-27 기준 Core 약 2MB · 업체 `src/app` 약 42KB ).
업체마다 다른 부분은 코드가 아니라 **설정**( 정책 · 모듈 켜고 끄기 · 엑셀 양식 덮어쓰기 · 커스텀 컬럼 · 수식 · LOT 규칙 )으로 흡수해 왔다.

repo 를 나누려던 원래 의도는 이것이었다 :
> 기본 기능은 그대로 가져가되, 업체별 수정 사항이 있으면 **업체 repo 만 고쳐서** 따로 가져간다.
> 예 ) 다른 업체가 수주 등록을 지금과 다르게 해야 하는 경우

그래서 "어디까지가 Core 인가"와 "업체가 Core 기능을 어떻게 바꾸나"를 정해 둔다.

## 검토한 대안

| 대안 | 문제 |
|---|---|
| Core = 플랫폼만, 업무는 업체 repo ( 처음 계획 ) | 두 번째 업체부터 수주 · 재고 · 생산을 **복사**하게 된다. 버그 수정 · 보안 패치를 업체 수만큼 반복 |
| 업체마다 Core 를 포크 | Core 업데이트를 업체마다 병합해야 한다. 업체가 늘수록 사실상 별개 제품 |
| 업체 차이를 전부 설정으로만 | 구조가 다른 요구( 수주 흐름 자체가 다름 )는 설정으로 담을 수 없다 |

## 결정

### 1. Core 는 "제품 그 자체"다

판단 기준 : **다른 업체에서도 쓸 수 있으면 Core, 그 업체에서만 의미가 있으면 업체 repo**

| Core ( `packages/mes-core` ) | 업체 repo ( `src/` ) |
|---|---|
| 모든 표준 기능 — 기준정보 · 업무 모듈 · 공통 컴포넌트 | `config/mes.php` — 켤 모듈 · 계산식 변수 연결 |
| 스키마( 마이그레이션 ) · 정책 카탈로그 · 내장 계산식 | 메뉴 구성( `config/menus.php` ) · 업체 초기 데이터( 시더 ) |
| 기본 엑셀 양식 | 업체 엑셀 양식 ( 같은 이름이면 업체가 이김 ) |
| 업체가 끼울 수 있는 확장 지점 | `.env` · docker · nginx 등 설치 설정 |
| | **그 업체에만 있는 기능 · Core 기능을 바꿔 끼운 것** |

규칙 : **Core 는 업체 코드( `App\` )를 참조하지 않는다** ( 2026-10-27 확인 — 참조 없음 ). 이 규칙만 지키면 나중에 `packages/mes-core` 를 그대로 떼어 별도 repo · Composer 패키지로 만들 수 있다.

### 2. 업체 수정은 Core 를 고치지 않고 "바꿔 끼운다" — 가벼운 단계부터

| 단계 | 방법 | 예 ( 수주 등록이 다른 업체 ) | Core 업데이트 |
|---|---|---|---|
| 1 | **설정** — 정책 · 커스텀 컬럼 · 엑셀 양식 | 단가 기본값 규칙, 칸 추가 | 그대로 받음 |
| 2 | **확장 지점** — 이벤트 · 훅 | 저장 전 검증 추가, 저장 후 알림 | 그대로 받음 |
| 3 | **서비스 교체** — 상속해서 일부 메서드만 | `SalesOrderService` 의 저장 규칙만 변경 | 바꾼 메서드만 직접 따라감 |
| 4 | **화면 교체** | 수주 등록 화면만 업체용으로 | 그 화면은 Core 수정을 못 받음 |
| 5 | **모듈 통째로 교체** | 수주를 업체가 새로 구현 | 해당 모듈은 별개 제품이 됨 |

위에서부터 시도하고, 안 될 때만 아래로 내려간다. 4 · 5 단계는 업체 요구가 **구조부터 다를 때만**.
업체 요구가 다른 업체에도 쓸 만하면 바꿔 끼우지 말고 **Core 에 옵션( 1 · 2 단계 )으로 올린다**.

### 3. 바꿔 끼우는 방법 ( 2026-10-27 코드 확인 )

| 대상 | 방법 | 현재 상태 |
|---|---|---|
| 서비스 | 업체 `AppServiceProvider` 에서 `$this->app->bind(SalesOrderService::class, 업체SalesOrderService::class)` | ✅ 가능 — Core 서비스는 컨테이너 주입 ( `new` 로 만드는 곳은 `CoreServiceProvider` 의 등록부뿐 ) |
| 라우트 | `src/app/Modules/{모듈}/routes.php` 에 같은 주소로 등록 → 나중에 등록된 업체 것이 우선 | ✅ 가능 — 단 암묵적이라 규칙으로 명시 필요 |
| 화면 | `src/resources/js/Pages/` 에 Core 와 같은 경로 · 이름으로 두면 업체 것이 뜬다 | ✅ 가능 ( 2026-10-28 `app.js` 페이지 합치기 순서 수정 — 이전엔 Core 가 업체를 덮어씀 ) |
| 확장 지점 | Core 서비스에서 이벤트 발생 | ❌ 없음 — 미리 만들지 않고 실제 요구가 온 자리에 추가 |
| DB 칸 | 예비 칸, 없으면 업체 쪽 1:1 확장 테이블 `cx_{Core 테이블}_ext` ( Core 테이블은 고치지 않음 ) | ✅ 규칙 확정 — `src/database/migrations/README.md` |

## 할 일 ( 미착수 — 필요할 때 )

1. ~~`src/resources/js/app.js` 페이지 합치기 순서 변경~~ — 완료 ( 2026-10-28 )
2. ~~모듈 이름 맞추기~~ — 완료 ( 2026-10-28 ) : 이름을 바꾸지 않고 **대응표로 정리**. 모듈 코드( `mes.php` · 메뉴 `module_code` · `app/Modules/{코드}` )는 그대로, Core 폴더와의 대응은 `CoreServiceProvider::MODULE_ROUTES` 한 곳에
3. `src/app/Modules` 빈 폴더 6개 정리 → "업체 전용 · 바꿔 끼운 기능만 여기" 안내만 남김
4. 수주 서비스 교체 예시 하나로 실제 덮어쓰기 검증 ( 서비스 · 라우트 · 화면 )
5. 실제 repo 분리는 **두 번째 업체가 생길 때**

## 결과

- 표준 기능은 한 곳에서 고치면 모든 업체에 간다
- 업체 차이는 대부분 설정으로 흡수하고, 구조가 다른 요구만 업체 repo 에서 바꿔 끼운다
- 3 ~ 5 단계로 바꿔 끼운 부분은 Core 업데이트를 **직접 따라가야 한다** — 업체별로 바꿔 끼운 목록을 업체 repo 에 남겨 둔다
- Core 가 커지는 것은 감수한다. 쓰지 않는 모듈은 `config/mes.php` 로 끈다

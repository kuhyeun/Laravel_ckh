# ADR 0024. BOM 변경 승인은 기록이지 관문이 아니다

- 상태: 채택
- 날짜: 2026-09-02
- 관련: `docs/ERD.md` §6, `docs/screens/20-기준정보.md` BAS-03

## 배경

*"이 BOM 누가 언제 승인했나"*는 **품질 감사에서 반드시 나온다.**
그런데 `feature.approval`(전자결재)은 Phase 2이고, 대부분의 업체는
**종이로 결재한 뒤 시스템에 옮겨 적는다.**

공통 컬럼의 `updated_at`으로 갈음하려 했으나 그것은 **행을 마지막으로 손댄 시각**이다.
오타 하나만 고쳐도 바뀐다. 설계변경일이 그렇게 움직이면 안 된다.

## 검토한 대안

| 대안 | 문제 |
|---|---|
| `updated_at`으로 갈음 | 행 수정 시각이다. **설계변경일과 다른 것**이다 |
| 별도 `bom_change_history` 테이블 | BOM은 이미 **버전**이 있다. 변경 한 번이 버전 하나이므로 이력이 두 벌이 된다 |
| 승인 없으면 활성 전환 차단 | **현장이 멈춘다.** 종이 결재가 먼저 끝나 있는데 시스템이 막는다 |
| 승인 여부를 정책으로 | 정책이 하나 더 는다. ADR 0013에서 더 늘리지 않기로 했다 |
| **컬럼 셋 + 경고** | 채택 |

## 결정

`bom`에 세 컬럼을 더한다.

```sql
changed_at   DATE         NULL   -- 설계변경 발효일 (업체가 적는다)
approved_at  DATETIME(6)  NULL   -- 변경 승인일
approved_by  BIGINT       NULL   -- 변경 승인자
```

**날짜 축을 분리한다.**

| 컬럼 | 무엇 | 누가 넣나 |
|---|---|---|
| `changed_at` | **설계변경 발효일** | **업체가 적는다.** 미래 날짜도 허용 |
| `approved_at` | 변경 승인일 | 승인 처리 시각 |
| `activated_at` | 활성으로 돌린 시각 | 시스템 |
| `updated_at` | 행을 마지막으로 손댄 시각 | 시스템(공통 컬럼) |

`changed_at`과 `activated_at`의 관계는 **발생 시각과 기록 시각**의 관계와 같다
(ADR 0004). 도면 개정은 지난주에 났고 시스템에는 오늘 넣는다.

**승인 없이도 활성 전환은 된다.** `W_BOM_NO_APPROVAL`로 경고만 한다.
`feature.approval`이 켜지는 Phase 2에 전자결재가 앞에 붙으면 그때 관문이 된다.

**승인 후 라인을 고치면 승인이 풀린다.** 승인한 내용과 다른 것이 되기 때문이다.

## 결과

- **별도 이력 테이블이 없다.** 버전 목록이 곧 변경 이력이다
- 정책을 늘리지 않았다. 경고는 항상 뜨고, 안 쓰는 업체는 무시하면 된다
- 승인을 강제하지 않으므로 **빈 채로 운영되는 업체가 있을 수 있다.**
  감사 대응이 필요한 업체는 Phase 2 전자결재로 올라간다
- `changed_at`이 미래일 수 있다. 조회·집계가 이 날짜를 기준으로 삼을 때
  **아직 오지 않은 변경**을 걸러야 한다

# ADR 0023. 공통 부품은 대장에 기록하고, 그 문서를 계약으로 삼는다

- 상태: 채택
- 날짜: 2026-09-02
- 관련: `docs/screens/01-공통컴포넌트.md`

## 배경

59개 화면이 같은 부품을 쓴다. 부품을 만든 사람과 쓰는 사람이 다르고,
목록이 없으면 **같은 부품을 두 번 만들거나** 쓸 때마다 `.vue`를 열어 props를 읽는다.
고칠 때 어디가 깨지는지도 모른다.

## 검토한 대안

| 대안 | 문제 |
|---|---|
| 코드가 곧 문서 | props를 읽으려면 파일을 연다. **쓰는 화면 목록이 없다** |
| Storybook | 도구 유지 비용이 든다. 온프레미스 배포에 불필요한 의존이 는다 |
| **마크다운 대장** | 채택 |

## 결정

`docs/screens/01-공통컴포넌트.md`에 부품마다 한 항목.
**props · emits · slots · 타입 · 쓰는 곳 · 예시 · `안 하는 것` · 이력**을 적는다.

- **새 부품 PR에 항목 추가가 없으면 반려한다**
- 계약(props·emits·slots)이 바뀌면 항목 수정 + 이력 한 줄. 내부 구현만 바뀌면 적지 않는다
- 부품이 되는 기준: **화면 3개 이상 / 업무 규칙 포함 / 바깥 라이브러리 감쌈** 중 둘 이상

## 결과

- 부품의 겉모습은 **코드가 아니라 문서가 계약**이다. 문서에 없는 것은 보장하지 않는다
- `쓰는 곳` 목록이 **변경 영향 범위**가 된다
- 문서와 코드가 어긋날 수 있다. 그래서 PR 규칙으로 묶는다
- `안 하는 것`을 적는 이유는 *"이것도 해 주면 편할 텐데"*를 멈추기 위해서다

# 정기수주 설계

> mes-v6 · 반복 수주와 분할 납품
> 작성일: 2026-08-28 · 상태: 확정 (미결은 §9)
> 상위 문서: [개발범위-및-MVP.md](./개발범위-및-MVP.md)

---

## 1. "정기수주"에는 두 가지 뜻이 있다

원문:

> *"특정 프로젝트(품목, 모델 등 고정적이지 않음)에 대한 반복적 수주가 있음"*
> *"정기수주로 명칭, **스케줄을 정하거나 상시**로 일정을 정할 수 있음"*
> *"해당 일정마다 **생산계획을 잡거나, 작업지시를 내릴 수 있음**"*

| | **유형 A · 반복 수주** | **유형 B · 분할 납품** |
|---|---|---|
| 무엇이 반복되나 | **수주 자체**가 반복해서 발생 | **납품**이 반복. 수주는 1건 |
| 총 수량 | 회차마다 새로 정함 | **수주 시점에 확정** (예: 12,000개) |
| 회차 수량 | 템플릿 수량 (조정 가능) | **납품 방법으로 정의** — 균등 · 사전지정 · 미정 |
| 만드는 것 | **새 수주** | 기존 수주의 **납품 회차** |
| 실무 이름 | 정기 발주 | **포괄수주 · 연간계약** |

**둘 다 필요합니다.** 하나로 합치면 오히려 헷갈립니다 —
A는 *"수주가 또 온다"* 이고 B는 *"온 수주를 나눠서 낸다"* 입니다.

---

## 2. 유형 A — 반복 수주

같은 고객에게 같은 품목을 반복 납품하는 경우입니다.
매번 수주를 처음부터 입력하지 않도록 **템플릿 + 일정**으로 만듭니다.

```
recurring_order          정기수주 (명칭 · 고객사 · 상태)
   ├ recurring_order_line   반복될 품목 · 수량
   └ recurring_schedule     언제 발생하는가
          ↓ 예정일 도래
      recurring_occurrence  회차 — 예정 목록에 뜸
          ↓ 사용자가 확정
      수주 / 생산계획 / 작업지시
```

**회차를 별도 테이블로 두는 것이 핵심입니다.**
예정 · 확정 · 건너뜀 · 취소 상태가 회차마다 다르고, 이력이 남아야 하기 때문입니다.

### 자동으로 만들지 않는다

> 일정이 도래하면 **예정 목록에 올리고, 사용자가 확정해야** 실제 문서가 생깁니다.

수주는 **고객 발주가 근거**입니다. 정기라도 이번 달 수량이 다를 수 있고, 고객이 건너뛸 수도 있습니다.
시스템이 임의로 수주를 만들면 실제 발주와 어긋납니다.

`recurring_order.auto_confirm`을 켜면 예정일에 바로 생성됩니다 —
수량이 항상 같고 고객이 확정적인 경우에만 씁니다.

### 무엇을 만드는가

원문 *"생산계획을 잡거나, 작업지시를 내릴 수 있음"* — **수주를 거치지 않을 수도 있습니다.**

| `output_type` | 만드는 것 | 쓰는 경우 |
|---|---|---|
| `SALES_ORDER` *(기본)* | 수주 | 고객 발주가 실제로 오는 경우 |
| `PRODUCTION_PLAN` | 생산계획 | 재고 보충 생산 |
| `WORK_ORDER` | 작업지시 | 계획 없이 바로 지시 |

## 3. 유형 B — 분할 납품

**수주는 1건입니다.** 총 수량이 확정되어 있고, 납품만 여러 번 나눠서 합니다.

```
수주 라인    커버 조립체 A   총 12,000개   매월 납품
   │
   ├ 회차 1   2026-09-25    800개    출하 완료
   ├ 회차 2   2026-10-25  1,200개    확정
   ├ 회차 3   2026-11-25       ?     예정 (수량 미정)
   │
   잔여      10,000개
```

### 기간 동안 어떻게 나눌지를 정의한다

**총 수량과 기간은 확정**되어 있고, 그 안에서 **어떻게 나눠 낼지**를 계약에 따라 정합니다.
방식이 하나가 아니므로 `delivery_method`로 고릅니다.

| `delivery_method` | 회차 수량 | 쓰는 경우 |
|---|---|---|
| **`EQUAL`** 균등 분할 | **총량 ÷ 회차 수** — 시스템이 계산 | *"12,000개를 12개월 매월 균등"* |
| **`PRESET`** 사전 지정 | **회차별로 미리 입력** | *"1월 500, 2월 1,500, 3월 …"* 계약서에 표가 있는 경우 |
| **`OPEN`** 미정 *(기본)* | **비어 있음** — 그때그때 | *"연간 12,000개, 요청 시 납품"* |

기간과 주기로 **회차 수가 정해집니다.**

```
start_date 2026-09-01 · end_date 2027-08-31 · MONTHLY 25일
   → 회차 12개
   EQUAL 이면  12,000 ÷ 12 = 1,000개씩
```

- 나누어떨어지지 않으면 **마지막 회차에 나머지**를 붙입니다
- `EQUAL` · `PRESET`이어도 **회차 확정 시 수량을 고칠 수 있습니다.** 계획일 뿐입니다
- `ON_DEMAND`(상시)는 회차 수가 정해지지 않으므로 **`OPEN`만 가능**합니다

### 회차 흐름

```
배치가 예정일 도래분 회차 생성
   EQUAL   qty = 계산값        status = PLANNED
   PRESET  qty = 지정값        status = PLANNED
   OPEN    qty = NULL          status = PLANNED
        ↓
사용자가 수량 확인 · 수정 · 확정   status = CONFIRMED
        ↓
생산계획 / 작업지시 생성
        ↓
출하                              status = SHIPPED
```

### 잔여 수량

```
잔여 = 수주 라인 qty − 확정된 회차 qty 합계
```

- **잔여를 넘는 회차는 경고**합니다. 차단하지 않습니다 — 고객이 추가 요청하는 경우가 있습니다
- 잔여가 0이 되면 그 라인은 `COMPLETED`
- 회차를 취소하면 잔여가 되돌아옵니다

### 유형 A와 구조가 닮았지만 다르다

| | `recurring_occurrence` | `sales_order_delivery` |
|---|---|---|
| 근거 | 템플릿 | **실제 수주 라인** |
| 총량 제한 | 없음 | **수주 라인 수량** |
| 산출물 | 수주 · 계획 · 지시 | 계획 · 지시 (수주는 이미 있음) |
| 수량 | 템플릿 값에서 시작 | **처음부터 비어 있음** |

## 4. 주기 표현 — 두 유형이 공유한다

cron 문법은 표현력이 과하고 현장 사용자가 읽지 못합니다.

| `cycle` | 추가 항목 | 예 |
|---|---|---|
| `MONTHLY` | `day_of_month` (1~31, 32=말일) | 매월 25일 |
| `WEEKLY` | `day_of_week` | 매주 화요일 |
| `DAILY` | — | 매일 |
| `INTERVAL` | `interval_days` | 10일마다 |
| **`ON_DEMAND`** | — | **상시** — 주기 없음, 필요할 때 발행 |

- `MONTHLY`에서 그 달에 없는 날짜(2월 31일)는 **말일**로 처리합니다
- 유효 기간(`start_date` · `end_date`)을 둡니다. `end_date`가 없으면 무기한

### 리드타임 역산

예정일이 곧 **납기일**이므로 그 전에 준비할 시간이 필요합니다.

```
목록 노출일 = 납기 예정일 − lead_days
```

제조리드타임 마스터에서 기본값을 가져오되 사용자가 조정할 수 있게 합니다 —
품목이 여러 개면 하나로 계산되지 않습니다.

## 5. 중지 · 건너뛰기 · 취소

셋을 구분합니다. 실무에서 자주 헷갈리는 지점입니다.

| 동작 | 대상 | 결과 |
|---|---|---|
| **중지** | 정기수주 / 수주 라인 | 이후 회차가 **생성되지 않음.** 이미 만들어진 문서는 그대로 |
| **건너뛰기** | 특정 회차 | 그 회차만 `SKIPPED`. 다음 회차는 정상 진행 |
| **취소** | 이미 확정된 회차 | 회차는 `CANCELED`. **생성된 문서는 별도로 취소**해야 함 |

> **회차 취소가 수주 · 작업지시를 자동으로 취소하지 않습니다.** 이미 생산이 들어갔을 수 있습니다.
> 취소 화면에서 연결된 문서를 보여주고 사용자가 판단합니다.

분할 납품에서 **회차를 취소하면 잔여 수량이 되돌아옵니다.**

## 6. 스키마

### 유형 A — 반복 수주

```sql
CREATE TABLE recurring_order (
  id           BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id    INT          NOT NULL,
  name         VARCHAR(100) NOT NULL,      -- 정기수주 명칭 (프로젝트명)
  partner_id   BIGINT       NOT NULL,      -- 고객사
  output_type  VARCHAR(16)  NOT NULL,      -- SALES_ORDER | PRODUCTION_PLAN | WORK_ORDER
  auto_confirm BOOLEAN      NOT NULL DEFAULT FALSE,
  lead_days    SMALLINT     NOT NULL DEFAULT 0,
  is_active    BOOLEAN      NOT NULL DEFAULT TRUE,
  PRIMARY KEY (id),
  KEY ix_active (tenant_id, is_active)
) ENGINE=InnoDB;

CREATE TABLE recurring_order_line (
  recurring_id BIGINT        NOT NULL,
  seq          SMALLINT      NOT NULL,
  item_id      BIGINT        NOT NULL,
  qty          DECIMAL(18,6) NOT NULL,
  PRIMARY KEY (recurring_id, seq)
) ENGINE=InnoDB;

CREATE TABLE recurring_schedule (
  recurring_id  BIGINT      NOT NULL,
  cycle         VARCHAR(12) NOT NULL,
  day_of_month  TINYINT     NULL,
  day_of_week   TINYINT     NULL,
  interval_days SMALLINT    NULL,
  start_date    DATE        NOT NULL,
  end_date      DATE        NULL,
  PRIMARY KEY (recurring_id)
) ENGINE=InnoDB;

CREATE TABLE recurring_occurrence (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  tenant_id      INT         NOT NULL,
  recurring_id   BIGINT      NOT NULL,
  due_date       DATE        NOT NULL,
  show_from      DATE        NOT NULL,   -- due_date − lead_days
  status         VARCHAR(12) NOT NULL,   -- PLANNED | CONFIRMED | SKIPPED | CANCELED
  created_ref_id BIGINT      NULL,
  confirmed_at   DATETIME(6) NULL,
  confirmed_by   BIGINT      NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_due (recurring_id, due_date),
  KEY ix_todo (tenant_id, status, show_from)
) ENGINE=InnoDB;
```

### 유형 B — 분할 납품

```sql
-- sales_order_line 에 추가되는 컬럼
--   delivery_type   VARCHAR(8)    ONCE | SPLIT
--   delivered_qty   DECIMAL(18,6) 확정된 회차 수량 합계

CREATE TABLE sales_order_line_schedule (
  order_id        BIGINT      NOT NULL,
  line_seq        SMALLINT    NOT NULL,
  cycle           VARCHAR(12) NOT NULL,   -- MONTHLY | WEEKLY | DAILY | INTERVAL | ON_DEMAND
  day_of_month    TINYINT     NULL,
  day_of_week     TINYINT     NULL,
  interval_days   SMALLINT    NULL,
  start_date      DATE        NOT NULL,
  end_date        DATE        NULL,       -- 기간. 회차 수를 결정
  delivery_method VARCHAR(8)  NOT NULL,   -- EQUAL | PRESET | OPEN
  lead_days       SMALLINT    NOT NULL DEFAULT 0,
  PRIMARY KEY (order_id, line_seq)
) ENGINE=InnoDB;

-- PRESET 일 때만. 회차별 수량을 미리 지정
CREATE TABLE sales_order_line_plan (
  order_id  BIGINT        NOT NULL,
  line_seq  SMALLINT      NOT NULL,
  seq       SMALLINT      NOT NULL,   -- 회차 번호
  due_date  DATE          NOT NULL,
  qty       DECIMAL(18,6) NOT NULL,
  PRIMARY KEY (order_id, line_seq, seq)
) ENGINE=InnoDB;

CREATE TABLE sales_order_delivery (
  id             BIGINT        NOT NULL AUTO_INCREMENT,
  tenant_id      INT           NOT NULL,
  order_id       BIGINT        NOT NULL,
  line_seq       SMALLINT      NOT NULL,
  seq            SMALLINT      NOT NULL,   -- 회차 번호
  due_date       DATE          NOT NULL,
  show_from      DATE          NOT NULL,
  qty            DECIMAL(18,6) NULL,       -- 확정 전에는 NULL
  status         VARCHAR(12)   NOT NULL,   -- PLANNED | CONFIRMED | SHIPPED | SKIPPED | CANCELED
  created_ref_id BIGINT        NULL,       -- 생산계획 · 작업지시
  shipment_id    BIGINT        NULL,
  confirmed_at   DATETIME(6)   NULL,
  confirmed_by   BIGINT        NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_due (order_id, line_seq, due_date),
  KEY ix_todo (tenant_id, status, show_from)
) ENGINE=InnoDB;
```

`uk_due`가 **중복 생성을 막습니다.** 배치가 두 번 돌아도 회차는 하나입니다.

`delivered_qty`는 잔여 계산을 빠르게 하기 위한 **파생 컬럼**입니다.
회차 확정 · 취소 시 같은 트랜잭션에서 갱신하고, 진실은 `sales_order_delivery` 합계입니다 —
재고 잔고와 원장의 관계와 같습니다.

## 7. 회차 생성 배치

```
매일 1회:
  [유형 A] 활성 정기수주 순회
     cycle 로 다음 예정일 계산
     due_date − lead_days <= 오늘  이고  회차 없으면
        recurring_occurrence 생성 (PLANNED)
        auto_confirm 이면 즉시 확정 → 문서 생성

  [유형 B] delivery_type = SPLIT 이고 잔여 > 0 인 수주 라인 순회
     cycle 로 다음 예정일 계산
     due_date − lead_days <= 오늘  이고  회차 없으면
        sales_order_delivery 생성 (PLANNED)
          EQUAL   qty = 총량 ÷ 회차 수 (마지막 회차에 나머지)
          PRESET  qty = sales_order_line_plan 에서 조회
          OPEN    qty = NULL
```

- `ON_DEMAND`는 배치 대상이 아닙니다. 사용자가 화면에서 직접 발행합니다
- 배치가 며칠 멈춰도 **누락되지 않습니다** — 지난 예정일도 조건에 걸립니다
- 유형 B는 **`auto_confirm`이 없습니다.** `EQUAL` · `PRESET`이어도 수량은 계획일 뿐이라 사람이 확인합니다

## 8. Phase

| Phase | 내용 |
|---|---|
| **Phase 1** | `sales_order_line.delivery_type` · `delivered_qty` **컬럼만.** 값은 `ONCE` |
| **Phase 2** | 유형 A · 유형 B 전체 |

분할 납품이 유형 A보다 **먼저 필요할 수 있습니다** — 포괄수주는 계약 형태라
첫 고객부터 나올 수 있기 때문입니다. Phase 2 안에서 순서를 조정합니다.

## 9. 미결

| # | 항목 | 확인 필요 |
|---|---|---|
| 1 | **유형 A의 품목 가변 범위** | 원문 *"품목, 모델 등 고정적이지 않음"* — 회차마다 품목이 바뀌는지, 수량만 바뀌는지. 품목까지 바뀐다면 템플릿은 **기본값** 역할만 합니다 |
| 2 | **템플릿 변경의 소급** | 정기수주 수량을 바꿨을 때 이미 만들어진 `PLANNED` 회차에 반영할지, 다음 회차부터 적용할지 |
| 3 | **분할 납품의 잔여 초과** | 지금은 **경고 후 허용**입니다. 계약 수량을 넘는 납품이 실제로 허용되는지 |
| 4 | **기간 변경 시 회차 재계산** | `EQUAL`에서 기간이나 총량이 바뀌면 **아직 확정 안 된 회차**를 다시 계산할지, 그대로 둘지 |

## 부록 · 결정 요약

| 결정 | 값 |
|---|---|
| 두 유형 | **A 반복 수주**(수주가 반복) · **B 분할 납품**(수주 1건을 나눠 납품). 합치지 않음 |
| 공통 구조 | 템플릿/수주 + 일정 + **회차**. 회차를 별도 테이블로 |
| 주기 | `MONTHLY` · `WEEKLY` · `DAILY` · `INTERVAL` · **`ON_DEMAND`(상시)**. cron 안 씀 |
| 유형 A 생성 | **자동 생성하지 않음.** 예정 목록 → 사용자 확정. `auto_confirm`은 옵션 |
| 유형 B 생성 | 예정일에 회차를 띄움. 수량은 `delivery_method`에 따라 계산 · 지정 · 비움. **자동 확정 없음** |
| 납품 방법 | `EQUAL`(균등 분할) · `PRESET`(회차별 사전 지정) · `OPEN`(미정, 기본). 기간 + 주기가 **회차 수**를 결정 |

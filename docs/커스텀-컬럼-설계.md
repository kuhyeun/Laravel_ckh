# 커스텀 컬럼 설계

> mes-v6 · 품목 · 발주 · 수주 · 출하의 사용자 정의 컬럼
> 작성일: 2026-08-27 · 상태: 확정 (미결은 §8)
> 상위 문서: [개발범위-및-MVP.md](./개발범위-및-MVP.md) · 관련: [정책-설정-설계.md](./정책-설정-설계.md)

---

## 1. 제약

> **운영 중 DDL 실행 금지.** 커스텀 컬럼을 추가할 때 `ALTER TABLE`이 돌면 안 됩니다.

이 제약이 선택지를 결정합니다.

| 방식 | DDL 필요 | 판정 |
|---|---|---|
| JSON 컬럼 + generated column 인덱스 | **검색 컬럼마다 DDL** | **탈락** |
| 예비 컬럼(슬롯) 사전 생성 | 없음 | 후보 |
| `extra_field` 테이블 (EAV) | 없음 | 후보 |

MariaDB의 `JSON`은 `LONGTEXT` + CHECK이라 직접 인덱싱이 안 됩니다. 검색 가능하게 만들려면
필드마다 generated column을 만들고 인덱스를 걸어야 하는데, 그게 곧 DDL입니다. 제약과 충돌합니다.

---

## 2. 단독으로는 둘 다 깨진다

**예비 컬럼만 쓰면** — 개수 상한이 곧 제품의 한계가 됩니다. 슬롯을 10개 잡아두면
업체가 15개를 요구할 때 답이 없습니다. 그렇다고 50개를 잡으면 대부분 NULL인 컬럼과
인덱스가 모든 테넌트의 쓰기 성능을 갉아먹습니다.

**EAV만 쓰면** — **목록 정렬과 검색이 죽습니다.** 커스텀 컬럼으로 정렬하려면 JOIN 후 `ORDER BY`인데
인덱스를 타기 어렵고, 조건 두 개를 AND로 걸면 self-join이 반복됩니다.
요구사항이 "통합검색, 상세검색"을 명시하고 있어서 이건 치명적입니다.

---

## 3. 결정 — 검색 여부로 갈라 저장한다

요구사항이 이미 힌트를 줬습니다.

> *"커스텀 컬럼은 **특정 기능을 위한 컬럼**과 **일반 텍스트 컬럼**으로 분류 됨"*

그리고 실무에서 **검색·정렬이 필요한 컬럼은 소수**입니다. 나머지는 목록에 보이고 엑셀로 떨어지면 충분합니다.

```
custom_field_def  ─ 정의는 언제나 여기 (메타데이터)
      │
      ├─ is_indexed = true  ──→  본 테이블의 예비 슬롯 컬럼   (검색 · 정렬 O, 개수 제한)
      └─ is_indexed = false ──→  custom_field_value (EAV)     (표시 · 엑셀만, 개수 무제한)
```

| | 슬롯 방식 | EAV 방식 |
|---|---|---|
| 검색 | 인덱스 사용 | 불가 (통합검색만 부분 지원) |
| 정렬 | 가능 | **불가** — UI에서 정렬 버튼 비활성 |
| 개수 | 엔티티별 상한 | 무제한 |
| DDL | **없음** (사전 생성) | 없음 |

**"검색 가능한 컬럼은 최대 N개"** 라는 한 문장으로 설명되는 제약입니다. 나머지는 개수 제한이 없습니다.

## 4. 슬롯 배치

행 수와 쓰기 빈도가 달라서 엔티티별로 다르게 잡습니다.

| 엔티티 | 성격 | 텍스트 | 숫자 | 날짜 | 계 |
|---|---|---|---|---|---|
| `item` (품목) | 마스터 · 행 적음 · 검색 많음 | 5 | 3 | 2 | **10** |
| `purchase` (발주) | 트랜잭션 | 3 | 2 | 2 | **7** |
| `sales_order` (수주) | 트랜잭션 | 3 | 2 | 2 | **7** |
| `shipment` (출하) | 트랜잭션 | 3 | 2 | 2 | **7** |

슬롯 컬럼과 인덱스는 **초기 스키마에 전부 생성**합니다. 운영 중에는 할당만 바뀝니다.

```sql
-- 품목 예시
ALTER TABLE item
  ADD COLUMN ext_c01 VARCHAR(200)   NULL,  -- ... ext_c05
  ADD COLUMN ext_n01 DECIMAL(18,6)  NULL,  -- ... ext_n03
  ADD COLUMN ext_d01 DATE           NULL;  -- ... ext_d02

CREATE INDEX ix_item_ec01 ON item (tenant_id, ext_c01);
-- 슬롯마다 하나씩
```

> 슬롯 수와 인덱스 개수는 **유연성과 쓰기 성능의 트레이드오프**입니다.
> 실제 사용률은 `ops_metric_daily`([수불설계 §11](./재고-수불-설계.md))와 같은 방식으로
> 관측한 뒤 조정합니다. 지금 숫자는 출발점입니다.

## 5. 스키마

```sql
-- 정의 : 슬롯이든 EAV든 정의는 언제나 여기
CREATE TABLE custom_field_def (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id     INT          NOT NULL,
  entity_type   VARCHAR(15)  NOT NULL,   -- ITEM | PURCHASE | SALES_ORDER | SHIPMENT
  field_key     VARCHAR(40)  NOT NULL,   -- 코드성 키 (엑셀 헤더, API)
  label         VARCHAR(60)  NOT NULL,   -- 화면 표시명
  kind          VARCHAR(12)  NOT NULL,   -- PLAIN | FUNCTIONAL   ← 원문의 두 분류
  var_name      VARCHAR(20)  NULL,       -- FUNCTIONAL일 때 계산식이 참조할 변수명
  data_type     VARCHAR(10)  NOT NULL,   -- TEXT | NUMBER | DATE | SELECT | BOOL
  select_values VARCHAR(1000) NULL,      -- SELECT일 때 후보
  is_indexed    BOOLEAN      NOT NULL DEFAULT FALSE,  -- 검색·정렬 대상 여부
  slot_col      VARCHAR(12)  NULL,       -- 'ext_c01' (is_indexed=true일 때만)
  is_required   BOOLEAN      NOT NULL DEFAULT FALSE,
  display_order SMALLINT     NOT NULL DEFAULT 0,
  is_active     BOOLEAN      NOT NULL DEFAULT TRUE,
  created_at    DATETIME(6)  NOT NULL,
  created_by    BIGINT       NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_key  (tenant_id, entity_type, field_key),
  UNIQUE KEY uk_slot (tenant_id, entity_type, slot_col),  -- 슬롯 중복 할당 방지
  UNIQUE KEY uk_var  (tenant_id, var_name)                -- 변수명은 테넌트 안에서 유일
) ENGINE=InnoDB;

-- 비색인 값 : 개수 무제한
CREATE TABLE custom_field_value (
  tenant_id   INT           NOT NULL,
  entity_type VARCHAR(15)   NOT NULL,
  entity_id   BIGINT        NOT NULL,
  field_id    BIGINT        NOT NULL,
  value_text  VARCHAR(1000) NULL,
  PRIMARY KEY (tenant_id, entity_type, entity_id, field_id),
  KEY ix_field (tenant_id, field_id),
  CONSTRAINT fk_cfv_def FOREIGN KEY (field_id) REFERENCES custom_field_def(id)
) ENGINE=InnoDB;
```

값 컬럼이 `value_text` 하나뿐인 이유는, **EAV 쪽은 표시와 엑셀 출력만 담당**하기 때문입니다.
타입별 비교 연산이 필요 없으니 타입별 컬럼을 나눌 이유가 없습니다.
타입 검증은 저장 시점에 `data_type`으로 합니다.

## 6. 목록 조회

**슬롯 값은 본 테이블에 있으므로 추가 조회가 없습니다.**

**EAV 값은 페이지 단위로 한 번에 가져와 메모리에서 피벗합니다.**

```sql
-- 1) 본 목록 (슬롯 컬럼 포함, 검색·정렬 적용)
SELECT id, ..., ext_c01, ext_n01 FROM item WHERE ... ORDER BY ... LIMIT 50;

-- 2) 그 50건의 EAV 값을 한 번에
SELECT entity_id, field_id, value_text
  FROM custom_field_value
 WHERE tenant_id = ? AND entity_type = 'ITEM' AND entity_id IN (...50건...);
```

행마다 조회하면 N+1이 됩니다. **반드시 페이지의 id 집합으로 한 번에** 가져옵니다.
50행이면 쿼리 2회로 끝나고, EAV 컬럼이 20개든 50개든 쿼리 수는 그대로입니다.

### 검색·정렬 제약

| 대상 | 검색 | 정렬 |
|---|---|---|
| 슬롯 컬럼 | 일치 · 범위 · 접두 LIKE (인덱스) | 가능 |
| EAV 컬럼 | 통합검색에서만 부분 일치 (느림, 별도 경로) | **불가** |

EAV 컬럼의 정렬 버튼은 **UI에서 비활성**합니다. 눌리는데 안 되는 것보다
처음부터 없는 편이 낫습니다. 툴팁으로 *"검색 가능 컬럼으로 지정하면 정렬할 수 있습니다"* 를 안내합니다.

## 7. 운영

> **커스텀 컬럼 정의는 시스템관리자 고유 권한입니다.**
> 업체 사용자·관리자는 컬럼을 추가·삭제·변경할 수 없습니다. 원문의 `시스템관리(슈퍼관리자) : 커스텀 컬럼관리, 컬럼명 관리`와 일치합니다.
> 업체가 하는 것은 **값 입력**뿐이며, 그것도 해당 엔티티 화면의 **쓰기 권한을 가진 사용자**만 합니다.
> 기능 스위치와 마찬가지로 **사전 협의 후 반영**하며, 업체가 화면에서 요청하는 흐름은 없습니다.
> 슬롯 상한 안내도 시스템관리자 화면에만 노출합니다.

### 컬럼 추가 — 시스템관리자

```
1. is_indexed 여부 선택
2. is_indexed = true  → 빈 슬롯을 data_type에 맞춰 자동 할당
                        빈 슬롯이 없으면 "검색 가능 컬럼 상한 도달" 안내 후 거부
   is_indexed = false → 슬롯 없이 정의만 생성
3. DDL 없음. 정의 한 줄 INSERT로 끝
```

### 컬럼 삭제 — 시스템관리자 · 슬롯을 바로 재사용하지 않는다

슬롯을 즉시 회수해 다른 컬럼에 할당하면 **이전 컬럼의 잔여 데이터가 새 컬럼 값으로 보입니다.**

```
1. 삭제 = is_active = false (soft delete). 슬롯 점유는 유지
2. 슬롯 회수는 관리자의 명시적 "정리" 작업
     → 해당 슬롯 컬럼 전체를 NULL로 UPDATE
     → slot_col 해제, 정의 hard delete
```

정리 전에는 그 슬롯이 상한에 계속 포함됩니다. 시스템관리자 화면에 이 상태를 표시해야
"컬럼을 지웠는데 왜 상한에 걸리느냐"가 됩니다.

### 검색 대상 전환 — 시스템관리자

`is_indexed = false` → `true` 로 바꾸면 슬롯을 할당하고 **EAV 값을 슬롯 컬럼으로 이관**합니다.
행 수가 많으면 배치로 나눠 처리합니다. 반대 방향도 같습니다.

DDL은 여전히 없습니다 — 데이터 이동만 일어납니다.

---

> 해결됨 — *`FUNCTIONAL`(기능형 컬럼)의 정의*: **자재소요 계산식이 값으로 읽는 컬럼**입니다.
> `var_name`을 붙이면 계산식에서 그 이름으로 참조됩니다 — 톱날 손실(`KERF`) · 비중(`DENSITY`) · 로스율(`LOSS`).
> 업체마다 다르고 품목마다 다른 값이라 시스템이 컬럼을 정해 줄 수 없습니다
> ([자재소요-계산-설계.md](./자재소요-계산-설계.md) §3.2).

> 해결됨 — *유니크 제약*: **두지 않습니다.** 슬롯 컬럼에는 일반 인덱스만 겁니다.
> 유니크가 없으므로 **슬롯 회수·재할당이 단순**해지고, 인덱스도 가볍습니다. `is_required`는 유지합니다.

## 부록 · 결정 요약

| 결정 | 값 |
|---|---|
| 운영 중 DDL | **없음** |
| 정의 | `custom_field_def` 단일 테이블 |
| `kind` | `PLAIN` 표시·검색용 / **`FUNCTIONAL` 계산식 변수**(`var_name`, 테넌트 안에서 유일) |
| 검색·정렬 컬럼 | **예비 슬롯 컬럼** — 사전 생성, 인덱스 포함 |
| 표시 전용 컬럼 | **`custom_field_value` (EAV)** — 개수 무제한 |
| 슬롯 수 | 품목 10 · 발주/수주/출하 각 7 |
| 목록 조회 | 슬롯은 본 쿼리에, EAV는 페이지 id 집합으로 1회 조회 후 피벗 |
| 슬롯 삭제 | soft delete → 명시적 정리 작업으로 회수 |
| 편집 권한 | **정의는 시스템관리자 전용.** 업체는 **값 입력만**, 그것도 해당 화면의 쓰기 권한에 따름 |
| 제약 | **유니크 없음.** 슬롯 컬럼에 일반 인덱스만. 필수(`is_required`)는 있음 |

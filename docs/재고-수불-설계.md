## 1. 이 문서가 푸는 문제

요구사항 1차는 재고에 대해 서로 충돌하는 요구를 동시에 걸고 있습니다.

| 요구사항 원문 | 함의 |
|---|---|
| "재고실사 시점에서부터 입출고 계산" | 시점 기준 재계산이 필요 |
| "입고기록보다 재고실사가 이전인데 나중에 등록될 수는 있음(전산처리 늦게)" | **소급 입력 허용** |
| "LOT단위로 몇개있는지" · "LOT추적(정추적/역추적)" | 전 이력 보존 필요 |
| "날짜에 따라 입출고 실시간 계산?" | 조회 성능 요구 |

현재고를 컬럼 하나로 들고 있으면 소급 입력에서 반드시 깨지고, 이력만 남기고 매번 합산하면 데이터가 쌓일수록 느려집니다. **둘 다 필요합니다.**

추가로, 현장 실태가 이렇습니다.

> 오늘 생산건을 처리한 뒤, 1주일 전 생산건을 나중에 전산 입력한다.

즉 **소급 입력은 예외가 아니라 기본 동작**입니다. 이 전제 위에서 설계합니다.

## 2. 3층 구조

| 층 | 테이블 | 역할 | 성격 |
|---|---|---|---|
| ① 원장 | `stock_ledger` | 모든 수불 이력 | **진실의 원본**, append-only |
| ② 잔고 | `stock_balance` | 현재고 | 증분 갱신 캐시, O(1) 조회 |
| ③ 스냅샷 | `stock_snapshot` | 시점 기준고 | 재계산 가능한 캐시 |

```
전표 등록
   ├→ stock_ledger  INSERT       (같은 트랜잭션)
   └→ stock_balance UPSERT       qty = qty + delta

현재고 조회   → stock_balance 단순 SELECT          (합산 없음)
시점 재고 조회 → stock_snapshot + 이후 델타 합산    (범위 제한)
LOT 추적      → stock_ledger 직접 조회             (lot_no 인덱스)
```

### 왜 잔고 테이블이 필요한가

재고 목록 화면 한 번이 품목 5,000 × LOT 평균 3 = **약 15,000행**을 요구합니다. 이걸 원장 `GROUP BY` 집계로 만들면 매번 전체 스캔입니다. 잔고 테이블이면 15,000행 SELECT로 끝나고, 원장이 2,500만 행이든 상관없습니다.

### 절대 규칙

> **`stock_ledger`에 대한 `GROUP BY` 집계는 배치 코드에서만 허용한다.**
> 화면 조회 경로에서 원장을 집계하는 쿼리는 코드 리뷰에서 반려한다.

프루닝이 없으므로(§8) 이 규칙이 유일한 방어선입니다.

## 2-1. 재고 관리 단위 — LOT

> **잔고의 최소 단위는 `품목 × LOT × 창고(·로케이션)` 입니다. 바코드 개체 단위로 관리하지 않습니다.**

원문이 이미 답을 갖고 있습니다 — *"재고관리 : LOT단위로 몇개있는지, **해당 LOT에 발행된 바코드가 있는지 표시**"*.
바코드는 재고의 식별자가 아니라 **LOT에 붙는 라벨**입니다.

### 바코드가 개체가 아니라는 증거

원문 *"**동일한 바코드 번호로 발행 가능** : 자재 사용 및 출하때 한번 찍을때 동일 바코드에서 하나씩 선택"*.

같은 번호를 여러 장 뽑아 붙입니다. 바코드가 개체를 식별한다면 성립할 수 없는 요구입니다.
스캔은 **"어느 LOT인가"** 를 찾는 동작이고, 같은 번호가 여럿이면 그중 하나를 고릅니다.

### 이 결정이 정리하는 것들

| 항목 | LOT 단위이므로 |
|---|---|
| LOT 쪼개기 / 합치기 | 자연스럽게 성립. 쪼개면 **새 LOT 생성** + 원 LOT 차감 |
| 잔재 재입고 | 환봉 1000mm 중 500mm 사용 후 반납 → 반납분을 **새 LOT**으로 재입고하고 바코드 발행 |
| 선입선출 | **LOT의 입고 시점** 기준 |
| 다른 품목으로 변경 | LOT 단위 전환 |
| 재공(WIP) | **LOT 잔고가 아닙니다.** 작업지시 × 공정 단위이므로 별도 테이블(§11) |

### 로케이션

`location_id`는 잔고 키에 남기되 **기본값 `0`(미사용)** 입니다.

**로케이션 사용 여부를 정하는 정책 키는 만들지 않습니다.** 창고 마스터에 로케이션을 등록했는지가
이미 답을 갖고 있습니다 — 등록하지 않으면 모든 잔고가 `location_id = 0`으로 쌓입니다.
정책으로 또 결정하면 두 군데서 같은 것을 정하게 됩니다
([정책-설정-설계.md](./정책-설정-설계.md) §2).

### 자재 LOT — 외부 LOT을 그대로 쓸 것인가

자재를 입고할 때 공급처가 부여한 번호(**Heat No**, **Coil No** 등)를 어떻게 다룰지는
**시스템관리자 설정**입니다 — `lot.material_source` ([정책-설정-설계.md](./정책-설정-설계.md) §6 B-1).

| 모드 | LOT 번호 | 외부 번호 |
|---|---|---|
| `EXTERNAL` | **공급처 번호를 그대로** 사용 | 같은 값 |
| `INTERNAL` *(기본값)* | **LOT규칙으로 자체 발급** | 별도 필드에 보관 · 표시 |

**두 모드가 같은 스키마로 동작합니다.** `external_lot_no`는 어느 모드에서든 채워집니다.

### 같은 외부 LOT이 여러 번 입고된다

동일한 Heat No 자재가 **1일에 한 번, 5일에 한 번** 나뉘어 들어옵니다.

> **입고 시기가 다르므로 DB에서 합치지 않습니다. 입고 건마다 별도 LOT 레코드입니다.**

`EXTERNAL` 모드에서는 그래서 **같은 `lot_no`를 가진 LOT이 여러 개** 존재합니다.
같은 번호라도 언제 들어왔는지가 다르면 다른 물건이고, 선입선출도 각각의 입고일을 따라야 합니다.

| | `EXTERNAL` | `INTERNAL` *(기본값)* |
|---|---|---|
| `lot_no` | **공급처 번호 그대로** | LOT규칙으로 **자체 발급** |
| 레코드 생성 | 입고 건마다 새 LOT | 입고 건마다 새 LOT |
| `lot_no` 중복 | **가능** | 없음 (규칙에 순번 포함) |
| 선입선출 | 각 LOT의 입고일 | 각 LOT의 입고일 |
| Heat No로 묶어 보기 | `lot_no` 검색 | `external_lot_no` 검색 |

**두 모드의 차이는 `lot_no`를 무엇으로 채우느냐 하나뿐입니다.** 레코드를 만드는 규칙은 같습니다.

### `lot_no`에 UNIQUE를 걸지 않는다

`EXTERNAL` 모드가 중복을 허용하므로 DB 제약으로 유일성을 강제할 수 없습니다.

- `INTERNAL` 유일성은 **LOT규칙이 보장**합니다 — 원문의 `품목코드 + 날짜 + 순번`에 순번이 있습니다
- 내부 식별자는 언제나 **`lot.id`** 입니다. `lot_no`는 표시·검색용입니다
- 목록에서는 `lot_no`와 **입고일을 함께** 보여줘야 구분됩니다

**바코드를 스캔했을 때 같은 번호의 LOT이 여럿이면 골라야 합니다.**
이건 원문이 이미 요구한 동작입니다 — *"자재 사용 및 출하때 한번 찍을때 **동일 바코드에서 하나씩 선택**"*.

> **거래처가 다르면 당연히 다른 LOT입니다.** 제강사마다 Heat No 체계가 달라
> 서로 다른 소재가 같은 번호를 가질 수 있습니다. `partner_id`를 LOT에 남깁니다.

### `lot` 테이블

```sql
CREATE TABLE lot (
  id              BIGINT      NOT NULL AUTO_INCREMENT,
  tenant_id       INT         NOT NULL,
  item_id         BIGINT      NOT NULL,
  lot_no          VARCHAR(50) NOT NULL,          -- 화면 · 바코드에 쓰는 번호
  external_lot_no VARCHAR(50) NULL,              -- Heat No / Coil No 등 공급처 번호
  partner_id      BIGINT      NOT NULL DEFAULT 0,-- 공급 거래처 (0 = 자체 생산)
  spec_value      DECIMAL(18,6) NULL,            -- 조각 1개의 규격값 (환봉 1000 / 500)
  spec_value2     DECIMAL(18,6) NULL,            -- 2차원(판재) 세로. Phase 1에서는 항상 NULL
  parent_lot_id   BIGINT      NULL,              -- 잔재가 나온 원 LOT
  pack_qty        DECIMAL(18,6) NULL,            -- 입수. NULL이면 item.pack_qty
  source          VARCHAR(12) NOT NULL,          -- PURCHASE | PRODUCTION | RETURN | LEFTOVER
  in_at           DATETIME(6) NULL,              -- 입고 시각 → 선입선출 기준
  created_at      DATETIME(6) NOT NULL,
  created_by      BIGINT      NOT NULL,
  PRIMARY KEY (id),
  KEY ix_no   (tenant_id, item_id, lot_no),      -- UNIQUE 아님 (EXTERNAL 모드는 중복 허용)
  KEY ix_ext  (tenant_id, external_lot_no),
  KEY ix_fifo (tenant_id, item_id, in_at)
) ENGINE=InnoDB;
```

`in_at`이 선입선출의 기준입니다. 같은 `lot_no`라도 입고 시각이 다르면 **먼저 들어온 LOT이 먼저 나갑니다.**

### 왜 시스템관리자 설정인가

**LOT 번호 체계는 추적의 근간**입니다. 운영 중에 바꾸면 기존 LOT과 새 LOT의 의미가 달라지고
되돌릴 수 없습니다 — [정책-설정-설계.md](./정책-설정-설계.md) §7의 `SYSTEM_ADMIN` 판단 기준
*"구조 · 데이터 무결성 · 추적 전제를 바꾸는 것"* 에 해당합니다.

### 포장 단위 — 완박스와 잔량

한 번에 생산된 제품 하나의 LOT이 이렇게 구성됩니다.

```
5,050개  =  50 box × 100  +  1 box × 50 (잔량)
```

**총 수량 하나로는 실물 구성을 복원할 수 없습니다.** 5,020개가 남았을 때
`50 box + 20` 인지 `49 box + 50 + 70` 인지 구분되지 않습니다.
잔량 박스에서 뺐는지, 완박스를 개봉했는지에 따라 실물이 달라지기 때문입니다.

### 잔량 박스는 항상 최대 1개로 유지한다

박스를 개체로 관리하지 않으면서 이 문제를 없애는 방법은, **현장 관행을 그대로 규칙으로 만드는 것**입니다.

> 완박스는 개봉하지 않는다. 잔량이 필요하면 **잔량 박스에서 먼저 뺀다.**
> 잔량이 모자라면 그때 **완박스 하나를 개봉**해 잔량 박스로 만든다.

이 규칙을 지키면 잔량 박스는 **언제나 0개 또는 1개**입니다. 그러면 두 숫자로 구성이 완전히 정해집니다.

| 필드 | 의미 |
|---|---|
| `stock_balance.qty` | **총 수량** — 원장 합계와 일치 |
| `stock_balance.loose_qty` | **잔량 박스의 수량** (0 ~ `pack_qty - 1`) |
| 완박스 수 | `(qty - loose_qty) / pack_qty` — 계산값 |

### 출고 처리

| 입력 | 처리 |
|---|---|
| **박스 출고** N박스 | `qty -= N × pack_qty`. `loose_qty` 불변 |
| **수량 출고** M개 | `loose_qty`에서 차감. 모자라면 **완박스를 필요한 만큼 자동 개봉**해 `loose_qty`를 채운 뒤 차감 |

예시 — 5,050개 (`50 box + 50 loose`, 입수 100)

```
30개 출고   → loose 50-30=20        →  50 box + 20     = 5,020
30개 출고   → loose 20 < 30
              완박스 1개 개봉 → loose 120, box 49
              loose 120-30=90       →  49 box + 90     = 4,990
3박스 출고  → box 49-3=46           →  46 box + 90     = 4,690
```

**개봉은 별도 전표가 아닙니다.** 출고 처리 안에서 일어나고 원장에는 출고 한 줄만 남습니다.
`loose_qty` 변화는 잔고 테이블에서 관리합니다.

### 박스 구성은 원장에서 파생하지 않는다

`loose_qty`는 **현재 상태만 의미가 있습니다.** 과거 시점의 박스 구성을 조회할 일은 없습니다.

- `stock_ledger` — **수량만** 기록합니다. 참고용으로 `box_qty`(박스 수 입력분)를 함께 남깁니다
- `stock_snapshot` — **총 수량만** 담습니다. 박스 구성은 스냅샷 대상이 아닙니다
- `stock_balance.loose_qty` — 출고·이동 처리에서 직접 갱신합니다

원장 재계산·스냅샷 재계산 로직은 **기존 그대로** 유지됩니다. 박스가 수불 구조를 건드리지 않습니다.

### 재고실사

실사는 **박스 수와 잔량을 따로 셉니다.** 실사 등록 시 두 값을 입력하면
`실사 수량 = 박스 × 입수 + 잔량`으로 장부와 대조하고, `loose_qty`도 함께 확정합니다.

### 입수 값

| 위치 | 필드 | 설명 |
|---|---|---|
| 품목 | `item.pack_qty` | 기본 입수 (예: 100) |
| LOT | `lot.pack_qty` | 실제 입수. `NULL`이면 품목 값을 따름 |

LOT마다 입수가 다를 수 있어 오버라이드를 둡니다 — 포장 공정에서 정해지기 때문입니다.

**박스 라벨은 개체 식별자가 아닙니다.** 같은 LOT의 박스 50개에 **같은 번호**를 붙이고,
사용할 때 그중 하나를 고릅니다 — 원문 *"동일한 바코드 번호로 발행 가능"* 이 그대로 적용됩니다.

### 소재 — 규격별 개수로 기록한다

환봉 · 코일 · 판소재는 **어느 것을 썼는지가 중요합니다.** 500mm를 썼는지 1000mm를 썼는지.

> **품목은 절대 바뀌지 않습니다.** 500mm 잔재도 1000mm 원자재와 **같은 품목**입니다.
> 잔재를 다른 품목으로 만들면 **소재 BOM이 깨집니다.**

1000mm를 입고해 100짜리 5개를 만들면 500mm를 소비합니다. BOM은 *"제품 1개당 환봉 100mm"* 이고,
잔재 500mm도 그 BOM으로 계속 소비될 수 있어야 합니다. 잔재가 별도 품목이 되면
BOM 전개도, 자재소요계산도, 재고 조회도 전부 어긋납니다.

### 재고 기록 — 확정

**규격을 LOT의 속성으로 두고, 수량은 개수로 셉니다.**

```
    1000mm × 5개
        ↓  1개를 꺼내 500mm 사용, 500mm 반납
    1000mm × 4개
     500mm × 1개
```

| | 값 |
|---|---|
| `stock_balance.qty` | **개수** (5 → 4) |
| `lot.spec_value` | 그 LOT 조각 **1개의 규격값** (1000 · 500) |
| 품목 | **동일** — 규격이 달라도 같은 품목 |

한 LOT에 5,000mm를 뭉뚱그리면 **실물 구성이 사라집니다.** 총량이 4,500mm여도
500 조각만 남았다면 600mm 가공을 못 하는데 시스템은 가능하다고 답하게 됩니다.
규격별로 나눠 세면 목록이 곧 실물 구성입니다.

| 위치 | 필드 | 설명 |
|---|---|---|
| 품목 | `item.spec_unit` | 규격 단위 (`mm` · `m` · `kg`). **`NULL`이면 규격 관리 대상이 아님** |
| 품목 | `item.min_usable_spec` | **최소 사용 가능 규격값.** 이 값 이하 잔재는 폐기 |
| LOT | `lot.spec_value` | 조각 1개의 규격값 |
| LOT | `lot.parent_lot_id` | 잔재가 어느 LOT에서 나왔는지 |

`min_usable_spec`은 **품목마다 다릅니다.** 30mm는 예시일 뿐 시스템이 값을 정하지 않습니다.

> **규격 관리 여부를 정하는 정책 키는 만들지 않습니다.** `item.spec_unit`을 등록했는지가
> 이미 답을 갖고 있습니다 ([정책-설정-설계.md](./정책-설정-설계.md) §2).

### 재고 테이블에는 수량 하나뿐

**`stock_balance`에 규격 컬럼을 두지 않습니다.** 규격은 LOT의 속성이고, LOT은 이미 잔고 키에 있으므로
`lot.spec_value`를 JOIN해서 함께 보여주면 됩니다. 잔고에 또 두면 중복이고, 어긋날 수 있습니다.

| 품목 | `item.spec_unit` | `lot.spec_value` | 재고 표시 |
|---|---|---|---|
| 볼트 · 부자재 | `NULL` | `NULL` | **`1,000개`** |
| 환봉 | `mm` | `1000` / `500` | **`1000mm × 4개`** · **`500mm × 1개`** |
| 코일 | `kg` | `3000` | **`3000kg × 2개`** |

**규격이 없는 품목은 그냥 개수입니다.** `1 × 1000개`도 `1000개 × 1`도 아닙니다 —
`spec_value`가 `NULL`이라 곱할 대상 자체가 없습니다.

규격 단위(`mm` · `kg`)가 무엇이든 **수량은 언제나 개수**입니다.
`3000kg × 2개`는 코일 2개이고, 총 중량 6,000kg는 표시할 때 계산합니다.

### 원장

**출고 단위는 조각 하나입니다.** 600mm가 필요해도 1000mm 조각을 쪼개서 가져갈 수 없습니다.
창고에서 나가는 것은 조각 전체입니다. 그래서 원장의 수량은 **개수**입니다.

```
① 출고   OUT_PRODUCTION   LOT-A (1000mm)   −1 개    창고 → 현장
② 반납   IN_LEFTOVER      LOT-B ( 500mm)   +1 개    현장 → 창고 · 새 LOT
                                                     parent_lot_id = LOT-A
```

| 상황 | 재고 원장 | 결과 |
|---|---|---|
| 1000 출고 → 500 사용 → 500 반납 | `OUT −1`(LOT-A) · `IN +1`(LOT-B 500mm) | `1000×4` + `500×1` |
| 1000 출고 → 980 사용 → 20 폐기 | `OUT −1`(LOT-A) **한 줄** | `1000×4` |
| 1000 출고 → 전량 사용 | `OUT −1`(LOT-A) 한 줄 | `1000×4` |

**잔재는 새 LOT입니다.** 규격이 달라져 다른 줄로 세야 하기 때문입니다.
`parent_lot_id`로 원 LOT과 연결해 **어느 소재에서 나온 조각인지** 추적합니다.
새 LOT에는 **바코드를 발행**합니다 — 원문 *"재입고처리 후 바코드 발행"*.

> **새 LOT이지 새 품목이 아닙니다.** 이 구분이 BOM을 지킵니다.

### 재고 원장과 생산 실적의 경계

**재고 원장은 창고 입출고만 기록합니다.** 나간 1000mm 조각이 어떻게 쓰였는지 —
980 사용 + 20 폐기 — 는 **생산 실적(자재 투입)** 의 영역입니다.

| 기록 | 담당 |
|---|---|
| 창고에서 나갔다 · 창고로 들어왔다 | **재고 원장** `stock_ledger` (개수) |
| 얼마를 썼다 · 얼마를 버렸다 | **생산 실적** (작업지시 자재투입, 길이) |

이 경계를 지키지 않으면 이중 차감이 생깁니다. 출고로 이미 빠져나간 20mm를
재고 원장에서 또 빼면 재고가 어긋납니다.

### 출고 후보는 조각 규격으로 걸러진다

**600mm가 필요하면 500mm 조각은 쓸 수 없습니다.** 짧은 것을 이어 붙일 수 없기 때문입니다.

```
출고 후보 = lot.spec_value >= 필요 규격값
```

총 재고 4,500mm가 아니라 **개별 조각의 규격**을 봅니다. 물리적 사실이므로 **차단**합니다 —
소급 입력이나 검사 대기와 달리 판단의 여지가 없습니다.
후보에서 빠진 LOT은 목록에 **"규격 부족"으로 표시**해 왜 못 고르는지 보이게 합니다.

### 판소재 — 잔재를 관리하지 않는다

판소재 잔재는 모양이 불규칙합니다. L자로 남거나 구멍이 뚫린 채 남아서
**실측 · 등록 공수가 잔재 가치보다 큽니다.**

> **Phase 1은 판소재 잔재를 전량 폐기 처리합니다.**

- 부분 사용 후 남은 판재는 **반납하지 않고** `OUT_SCRAP`
- 환봉 · 코일 같은 규격 판정을 하지 않습니다
- 잔재 랙에 보관해 재사용하더라도 **시스템 밖의 일**입니다

### 확장 여지는 열어둔다

나중에 필요해지면 **외접 사각형(bounding box) 근사**로 켤 수 있게 컬럼 자리를 미리 잡습니다.
불규칙 잔재를 감싸는 최대 사각형(예: `700 × 1200`)으로 등록하는 방식입니다.

```sql
item.spec_dim    TINYINT       -- 1 = 길이 · 중량 / 2 = 판재(가로 × 세로). 기본 1
lot.spec_value2  DECIMAL(18,6) -- 2차원일 때 세로. Phase 1에서는 항상 NULL
```

2차원을 켜면 출고 후보 필터가 이렇게 확장됩니다 (회전 허용).

```
(가로 >= W AND 세로 >= H) OR (가로 >= H AND 세로 >= W)
```

외접 사각형은 **실제보다 크게 잡히지 않으므로 보수적**입니다 —
시스템이 "쓸 수 있다"고 한 것을 못 쓰는 일은 생겨도 그 반대는 없습니다.
켤 때는 **"근사 규격" 표시와 작업자 확인**이 함께 필요합니다.

컬럼 자리만 잡아두면 **마이그레이션 없이 전환**됩니다 —
"되돌릴 수 있는 쪽을 고른다"(§11) 원칙 그대로입니다.

### 잔재를 먼저 쓸 것인가 — 업체 설정

같은 품목에 **정상 입고분과 잔재 재입고분**이 섞여 있을 때 무엇부터 쓰는지는 업체마다 다릅니다.
`stock.remnant_consume` — **시스템관리자 설정**입니다 ([정책-설정-설계.md](./정책-설정-설계.md) §6 B-1).

| 모드 | 동작 |
|---|---|
| **`REMNANT_FIRST`** | **잔재부터 자동 차감.** 시스템이 잔재를 우선 소진한 뒤 정상 입고분으로 넘어감 |
| **`FIFO_MANUAL`** *(기본값)* | **선입선출로 자동 차감.** 잔재는 자동으로 잡지 않고 **사용자가 찾아서 선택** |

`FIFO_MANUAL`이 기본인 이유는, 잔재가 규격이 제각각이라 **자동으로 고르면 맞지 않는 경우가 많기 때문**입니다.
600mm가 필요한데 시스템이 잔재 500을 잡아버리면 다시 골라야 합니다.
잔재를 적극적으로 소진하는 업체는 `REMNANT_FIRST`로 켭니다.

어느 모드든 **출고 후보는 규격으로 걸러집니다**(위 절). 잔재를 먼저 쓰더라도 규격이 모자라면 후보에서 빠집니다.

### 쓸 수 없는 잔재는 폐기

잔재가 `item.min_usable_spec` **이하면 창고로 반납하지 않습니다.**

```
1000mm에서 980mm 사용  →  잔재 20mm
20mm <= min_usable_spec(30mm)  →  반납하지 않고 현장에서 폐기
```

- **재고 원장에는 출고 한 줄만** 남습니다. 반납이 없으므로 새 LOT도 만들지 않습니다
- 폐기량 20mm는 **생산 실적의 자재 투입 내역**에 사용 980 / 폐기 20으로 기록합니다
- 잔재 등록 화면의 **기본 선택이 폐기**이며, 반납을 고르면 경고를 표시합니다
- 쓸 수 없는 조각이 재고에 계속 쌓이는 것을 막습니다

### LOT을 쓰지 않는 품목

`lot_id`도 기본값 `0`입니다. 부자재처럼 LOT 추적이 불필요한 품목, 또는 `feature.lot`이 꺼진 업체는
`lot_id = 0`으로 품목 × 창고 단위 잔고가 됩니다. **스키마 변경 없이 같은 구조로 동작합니다.**

## 3. 이중 시간축

`occurred_at`과 `recorded_at`을 **둘 다** 저장합니다.

| | `occurred_at` (발생) | `recorded_at` (등록) |
|---|---|---|
| 의미 | 현장에서 실제 일어난 시각 | 전산에 입력된 시각 |
| 수정 | 가능 (입력 실수 정정) | **불변** |
| 순서 | 뒤죽박죽 | 항상 단조 증가 |
| 담당 | 재고 계산 · FIFO · 기간 집계 · 추적 | 감사 · 입력 확인 · 시스템 상태 재현 |

`recorded_at`이 없으면 "1주일 전 건을 오늘 넣었다"는 사실 자체가 사라져 감사 대응이 불가능합니다.
`occurred_at`이 없으면 재고가 업무 시간순으로 계산되지 않습니다.

## 4. 정렬 규칙

소급 입력 환경에서 정렬은 세 군데서 깨집니다.

### 4.1 AUTO_INCREMENT id는 발생 순서가 아니다

`id`는 `recorded_at` 순서입니다. **`ORDER BY id`는 발생 순서가 아닙니다.**

### 4.2 커서 페이지네이션은 정렬 키와 일치시킨다

```sql
WHERE (occurred_at, id) < (:last_occurred_at, :last_id)
ORDER BY occurred_at DESC, id DESC
LIMIT 50
```

동일 `occurred_at`이 흔하므로(시각을 분 단위로 입력하면 더) **tie-breaker `id`는 필수**입니다. 없으면 페이지마다 순서가 흔들리고 행이 누락됩니다.

### 4.3 화면 목적에 따라 기본 정렬 축이 다르다

| 화면 유형 | 기본 정렬 | 이유 |
|---|---|---|
| 입고/출고 **등록**, 오늘 작업 확인 | `recorded_at DESC` | 방금 넣은 게 맨 위에 있어야 함 |
| 입출고 **이력**, 수주 진행현황, LOT 추적 | `occurred_at DESC` | 업무 시간순이 의미를 가짐 |
| 검사이력, 생산실적 리포트 | `occurred_at` | 기간 집계와 축을 맞춤 |

**두 컬럼 모두 목록에 노출합니다.** 한쪽만 보이면 사용자가 순서를 이해하지 못합니다.

### 4.4 방금 입력한 건이 파묻히는 문제

1주일 전 건을 `occurred_at` 정렬 목록에 넣으면 3페이지 뒤에 나타납니다. 입력자가 저장 여부를 확인할 수 없습니다.

- 등록 직후 해당 행 **상단 고정 + 하이라이트**
- `recorded_at`이 최근 N시간 이내면 **"신규" 배지**

## 5. 소급 입력이 깨뜨리는 업무 규칙

셋 다 **정책 결정**이며, 테넌트 설정으로 노출합니다(§7).

### 5.1 선입선출(FIFO)

> 오늘 LOT A를 FIFO로 골라 출고했다. 내일 "1주일 전 입고" 건이 등록됐고, 사실 그게 LOT A보다 먼저였다.

**기본값: 소급 재배정하지 않는다.** (`fifo_reassign = FALSE`)

재배정하면 이미 발행된 바코드, 라우트시트, LOT 추적 링크가 전부 깨집니다. 대신 소급 입고 등록 시 **"이 시점 이후 출고 N건의 LOT 선택이 FIFO와 불일치"** 경고만 표시합니다.

### 5.2 공정 순서 검증

요구사항: "(e)가 기록되는 순간부터 다음공정 진행 가능"

소급이면 **2공정이 1공정보다 먼저 등록**됩니다.

- 검증은 등록 순서가 아니라 **`occurred_at` 기준**
- 등록 시점에 선행 공정 실적이 없으면 → **차단이 아니라 경고 + 허용**, "선행 공정 미등록" 상태 표시
- 선행 공정이 나중에 등록되면 표시 자동 해제

**기본값: 경고 후 허용** (`process_order_block = FALSE`). 하드 블록하면 현장이 멈춥니다.

**진행 조건은 앞 라인의 유형에 따라 다릅니다.**

| 앞 라인 | 다음 라인 시작 조건 |
|---|---|
| 생산 공정 | **시작(s) 기록** — 수량 0이어도, 완료 불필요 (공정 병행 허용) |
| 검사 공정 | **검사 완료 처리** — 정책과 무관하게 **하드 블록** |

> 검사 대기는 위 `process_order_block`에 해당하지 않습니다. 소급 입력은 "이미 일어난 일을 늦게 넣는 것"이지만
> 검사 대기는 "아직 판정되지 않은 것"이라 성격이 다릅니다.
> 상세는 [정책-설정-설계.md](./정책-설정-설계.md) §6 B-3.

### 5.3 음수 재고

출고를 등록하는데 해당 자재의 입고가 아직 전산에 없는 상황이 정상적으로 발생합니다.

**기본값: 허용 + 경고** (`allow_negative_stock = TRUE`)

음수 상태인 품목×LOT를 모아 보는 **미결 화면**을 둡니다. 대부분 며칠 안에 입고가 들어오며 해소되고, 남는 것이 진짜 문제입니다.

## 6. 마감과 스냅샷은 분리한다

마감 주기는 **업체마다 다르고, 아예 쓰지 않는 업체도 있습니다.** 따라서 마감을 전제로 한 설계를 쓸 수 없습니다.

| | 스냅샷 | 마감 |
|---|---|---|
| 성격 | **성능 캐시** | **업무 잠금** |
| 주기 | 시스템이 정함 (월 또는 주) | 업체가 설정 |
| 생성 | 자동, 무조건 | 사람이 실행 |
| 되돌리기 | 언제든 재계산 | 권한 + 이력 필요 |
| 없으면 | 시점 조회가 느려짐 | 아무 일도 안 일어남 |

**스냅샷은 마감과 무관하게 자동 생성**됩니다. 매월 1일 00:00 기준으로 뜨고, 소급 전표가 들어오면 dirty 마킹 후 야간 배치로 재계산됩니다. 업체는 존재를 몰라도 됩니다.

**마감은 선택 기능**입니다. 쓰지 않아도 재고 조회 성능은 동일합니다.

### 소급 입력 한계 — 마감을 대신하는 안전장치

마감이 없으면 소급이 무한정 열립니다. 이걸 별도 설정이 막습니다.

```
occurred_at이 오늘로부터
  ~ backdate_warn_days 이내   → 그냥 등록
  초과                        → 경고 표시 후 등록
  backdate_block_days 초과    → 지정 권한자만 등록 (또는 차단)
```

**기본값: 경고 30일 / 차단 없음.** 차단을 기본으로 걸면 도입 초기 과거 데이터 이관이 막힙니다.

### 마감 해제

`REOPEN`을 **반드시 구현합니다.** 실무에서 무조건 발생하며, 사유와 이력이 남지 않으면 감사에서 문제가 됩니다.

| 창고 · LOT · 바코드 사용 | 테넌트 | 요구사항 명시 |
| 자재 자동 차감 시점 | 품목 | 요구사항 명시 |
| 재고 차감 기준(수주연동/FIFO) | 품목 | 요구사항 명시 |
| 입고검사(무검사/샘플링/전수) | 거래처 | 요구사항 명시 |
| 검사 필수 여부 | 품목 · 공정 | 요구사항 명시 |

적용 범위가 **계층**이라는 점이 중요합니다.

```
시스템 기본값 → 테넌트 설정 → 거래처/품목별 오버라이드
```

이 계층 조회를 **공통 정책 서비스 하나**로 구현합니다. 각 모듈이 제각각 `if (설정)`을 짜면 정책이 하나 추가될 때마다 전 모듈을 뒤져야 합니다. 요구사항의 `기능옵션관리`가 이 방향을 가리키고 있습니다.

## 8. DB — MariaDB, 파티션 미사용

### 결정

**`stock_ledger`를 파티션하지 않는다.**

### 근거

MariaDB 파티션의 제약이 이 시스템과 충돌합니다.

| 제약 | 영향 |
|---|---|
| 파티션 테이블은 **외래키 불가** | 참조무결성을 DB가 보장하지 못함 |
| **글로벌 인덱스 없음** (파티션마다 로컬) | `recorded_at` 조회 = 전 파티션 스캔. 매일 쓰는 입력 확인 화면이 가장 느려짐 |
| UNIQUE/PK에 **파티션 컬럼 포함 필수** | PK가 `(id, occurred_at)`이 되어 모든 세컨더리 인덱스가 커짐 |
| 파티션 **자동 생성 없음** | EVENT로 `REORGANIZE PARTITION` 직접 운영 |

반면 얻는 것(`DROP PARTITION` 즉시 삭제)은 **이 시스템에서 값어치가 낮습니다.** LOT 추적·클레임 대응 때문에 원장을 삭제할 수 없기 때문입니다.

### 볼륨 근거

행 수가 아니라 **워킹셋이 버퍼풀에 들어가느냐**가 결정합니다. 아래는 실측이 아니라 **감을 잡기 위한 예시 계산**입니다 — 10년 2,500만 행 기준:

| | 크기 |
|---|---|
| 클러스터드 인덱스(데이터) | 약 3.5~4 GB |
| 세컨더리 인덱스 4개 | 약 4~5 GB |
| 합계 | **약 8~9 GB** |

`innodb_buffer_pool_size = 16GB`면 전부 캐시됩니다. 파티션 없이 10년이 갑니다.

### 전환 판단 지표

나중에 감으로 결정하지 않도록 트리거를 정해둡니다. 하나라도 걸리면 재검토:

| 지표 | 임계 |
|---|---|
| `stock_ledger` 행 수 | 3,000만 |
| 테이블 + 인덱스 크기 | `innodb_buffer_pool_size`의 70% |
| 스냅샷 재계산 배치 소요 | 야간 배치 창 초과 |

`information_schema.TABLES`로 월 1회 기록만 남기면 됩니다.

전환은 `pt-online-schema-change` / `gh-ost`로 **다운타임 없이 가능**합니다(디스크 2배, 수 시간 소요). 되돌릴 수 없는 결정이 아닙니다.

### 아카이빙이 필요해지면

파티션이 없으므로 청크 배치로 처리합니다. 느리지만 야간에 나눠 돌리면 됩니다.

```sql
INSERT INTO stock_ledger_archive
  SELECT * FROM stock_ledger WHERE occurred_at < :cut LIMIT 10000;
DELETE FROM stock_ledger WHERE occurred_at < :cut LIMIT 10000;
```

## 9. 스키마

### 9.1 전표 헤더 · 원장 라인

헤더와 라인을 분리합니다. 입고 1건에 품목×LOT N라인이 붙고, 상태·결재·취소가 전표 단위로 움직이기 때문입니다.

```sql
-- 전표 헤더
CREATE TABLE stock_txn (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id     INT          NOT NULL,
  txn_no        VARCHAR(30)  NOT NULL,
  txn_type      VARCHAR(20)  NOT NULL,
  occurred_at   DATETIME(6)  NOT NULL,
  recorded_at   DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  recorded_by   BIGINT       NOT NULL,
  partner_id    BIGINT       NULL,
  warehouse_id  INT          NULL,
  status        VARCHAR(15)  NOT NULL,   -- DRAFT | CONFIRMED | CANCELED
  remark        VARCHAR(500) NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_no  (tenant_id, txn_no),
  KEY ix_rec (tenant_id, recorded_at, id),   -- 등록 확인 화면
  KEY ix_occ (tenant_id, occurred_at, id)    -- 이력 화면
) ENGINE=InnoDB;

-- 수불 라인 (원장)
CREATE TABLE stock_ledger (
  id             BIGINT        NOT NULL AUTO_INCREMENT,
  tenant_id      INT           NOT NULL,
  txn_id         BIGINT        NOT NULL,
  item_id        BIGINT        NOT NULL,
  lot_id         BIGINT        NULL,
  lot_no         VARCHAR(50)   NULL,          -- 번호 기반 추적
  warehouse_id   INT           NOT NULL,
  location_id    INT           NULL,
  txn_type       VARCHAR(20)   NOT NULL,
  qty_delta      DECIMAL(18,6) NOT NULL,      -- 부호 포함
  occurred_at    DATETIME(6)   NOT NULL,
  recorded_at    DATETIME(6)   NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  ref_type       VARCHAR(20)   NULL,          -- ORDER | WORK_ORDER | SHIPMENT ...
  ref_id         BIGINT        NULL,
  reversed_by_id BIGINT        NULL,          -- 취소는 DELETE가 아니라 역분개

  PRIMARY KEY (id),
  KEY ix_bal (tenant_id, item_id, lot_id, warehouse_id, occurred_at),
  KEY ix_lot (tenant_id, lot_no, occurred_at),
  KEY ix_occ (tenant_id, occurred_at, id),
  KEY ix_txn (txn_id),

  CONSTRAINT fk_led_txn  FOREIGN KEY (txn_id)       REFERENCES stock_txn(id),
  CONSTRAINT fk_led_item FOREIGN KEY (item_id)      REFERENCES item(id),
  CONSTRAINT fk_led_wh   FOREIGN KEY (warehouse_id) REFERENCES warehouse(id)
) ENGINE=InnoDB;
```

**인덱스는 이 4개 선에서 끊습니다.** 원장은 쓰기가 많은 테이블이고, 인덱스마다 INSERT 비용과 버퍼풀 점유가 늘어납니다.

### 9.2 현재고

```sql
CREATE TABLE stock_balance (
  tenant_id      INT           NOT NULL,
  item_id        BIGINT        NOT NULL,
  lot_id         BIGINT        NOT NULL DEFAULT 0,   -- 0 = LOT 미관리
  warehouse_id   INT           NOT NULL,
  location_id    INT           NOT NULL DEFAULT 0,
  qty            DECIMAL(18,6) NOT NULL DEFAULT 0,
  loose_qty      DECIMAL(18,6) NOT NULL DEFAULT 0,   -- 잔량 박스 수량 (0 ~ pack_qty-1)
  last_ledger_id BIGINT        NULL,
  updated_at     DATETIME(6)   NOT NULL,
  PRIMARY KEY (tenant_id, item_id, lot_id, warehouse_id, location_id),
  KEY ix_item (tenant_id, item_id),
  KEY ix_wh   (tenant_id, warehouse_id)
) ENGINE=InnoDB;
```

#### 선점 컬럼을 두지 않는다

**출고는 예약이 아니라 실제 차감입니다.** 자재를 출고하면 그 순간 창고 재고에서 빠집니다.
출하도 같습니다 — 출하등록이 곧 차감입니다.

```
가용재고 = stock_balance.qty          ← 뺄 것이 없습니다
```

`reserved_qty` 컬럼을 **자리만이라도 남기지 않습니다.** 남겨 두면
`가용 = qty - reserved_qty` 라는 식이 코드에 스며들고, 언제나 0인 값을 빼는 계산이
전 화면에 퍼집니다. 나중에 예약이 정말 필요해지면 그때 **의미를 정하고** 넣습니다.

### 9.2-1 작업지시가 들고 있는 자재

출고했지만 **아직 사용하지 않은 자재**가 현장에 있습니다.
창고에서는 빠졌고 소비되지도 않은 상태입니다.

```sql
CREATE TABLE wo_stock (
  tenant_id      INT           NOT NULL,
  work_order_id  BIGINT        NOT NULL,
  item_id        BIGINT        NOT NULL,
  lot_id         BIGINT        NOT NULL DEFAULT 0,
  issued_qty     DECIMAL(18,6) NOT NULL DEFAULT 0,   -- 누적 출고
  consumed_qty   DECIMAL(18,6) NOT NULL DEFAULT 0,   -- 누적 사용
  qty            DECIMAL(18,6) NOT NULL DEFAULT 0,   -- 미사용 = issued - consumed
  updated_at     DATETIME(6)   NOT NULL,
  PRIMARY KEY (tenant_id, work_order_id, item_id, lot_id),
  KEY ix_item (tenant_id, item_id, lot_id)
) ENGINE=InnoDB;
```

| 규칙 | 내용 |
|---|---|
| 원장 | **출고 시 한 번만** 기록합니다(`OUT`, `ref_type = WORK_ORDER`). 사용처리는 원장을 남기지 않습니다 |
| 근거 | **원장은 창고 재고의 진실**입니다. 창고 밖으로 나간 뒤의 행방은 `wo_stock`이 답합니다 |
| 재공과의 차이 | `wip_balance`는 **만들어지는 것**(작업지시 × 공정), `wo_stock`은 **투입될 것**(작업지시 × 품목 × LOT) |
| 반납 | **구현 ( 10-29 )** — 출고한 그대로( 같은 LOT )를 `IN_RETURN` 전표로. `wo_stock.returned_qty` 추가 · 보유 = 출고 − 사용 − 반납 ( 50-생산 §15-1 ). 잘라 쓰고 남은 조각의 **잔재 재입고**( 새 LOT · §8 )는 아직 |

**`stock_balance`에 차원을 더하지 않았습니다.** 재공을 별도 테이블로 둔 것과 같은 원칙입니다 —
잔고 키가 커지면 모든 조회가 무거워지고, 창고가 아닌 것이 창고 잔고에 섞입니다.

> 재고현황(`INV-01`)은 이 둘을 **한 화면에서 위치만 다르게** 보여줍니다 —
> `품목 × LOT × 창고`와 `품목 × LOT × 작업지시`. 안전재고 판정은 **창고 가용만** 봅니다.

### 9.3 스냅샷

```sql
CREATE TABLE stock_snapshot (
  tenant_id    INT           NOT NULL,
  snapshot_at  DATETIME(6)   NOT NULL,
```

시점 재고 = `가장 가까운 이전 스냅샷 + 그 이후 ~ 조회시점 델타 합산`

## 10. 처리 흐름

### 10.1 일반 전표 등록

```
1. tenant_stock_policy 조회 → 소급 한계·음수재고 정책 확인
2. occurred_at 검증 (마감 기간 / backdate 한계)
3. 트랜잭션 시작
     stock_txn    INSERT
     stock_ledger INSERT (N라인)
     stock_balance UPSERT  qty = qty + delta
     occurred_at 이후 stock_snapshot → is_dirty = TRUE
   커밋
4. 정책 위반 시 경고 반환 (차단이 아니라 경고)
```

### 10.1-1 입고검사 대기

품질 정책이 `SHEET`이고 입고검사 대상이면, **검사완료 전에는 원장을 쓰지 않습니다.**

```
입고 등록      stock_txn.status = DRAFT       원장 미기록 · 재고 미반영
검사완료       (품질관리에서 검사지 작성)
입고 처리      stock_txn.status = CONFIRMED   stock_ledger INSERT + stock_balance 갱신
```

**검사대기 중인 자재는 재고에 잡히지 않습니다.** 전표 헤더만 존재합니다.
상세는 [정책-설정-설계.md](./정책-설정-설계.md) §6 B-3.

### 10.2 취소

**DELETE하지 않습니다.** 반대 부호의 역분개 라인을 새로 넣고 `reversed_by_id`로 연결합니다. 원장은 append-only를 유지합니다.

### 10.3 재고실사

```
1. 실사 시점(occurred_at) 지정하고 실사 수량 입력
2. 해당 시점 장부 재고 계산 (스냅샷 + 델타)
3. 차이만큼 txn_type = STOCKTAKE 조정 라인 자동 생성
4. 실사 시점 스냅샷을 source = STOCKTAKING 으로 확정
5. 이후 스냅샷 전부 is_dirty = TRUE
```

요구사항의 **"재고실사 등록할 때 재고 재계산하여 현 재고 기록"**이 이 흐름입니다. 실사가 입고보다 이전 시점이어도, 조정 라인이 `occurred_at` 기준으로 들어가므로 최종 잔고는 자동으로 맞습니다.

### 10.4 스냅샷 재계산 배치

**예외 처리가 아니라 매일 도는 정규 배치입니다.** 소급 입력이 일상이기 때문입니다.

```
매일 야간:
  is_dirty = TRUE 인 스냅샷을 snapshot_at 오름차순으로
    → 직전 스냅샷 + 구간 델타 합산 → qty 갱신 → is_dirty = FALSE
```

## 11. 불확실성 처리

### 설계 단계에서 알 수 없는 것

**소급 지연 최대치**와 **일 전표 라인 수**는 설계 단계에서 확보할 수 없습니다.
그래서 **설계 입력에서 제외**하고, 시스템이 스스로 측정하도록 합니다.

| 미지수 | 왜 몰라도 되는가 |
|---|---|
| 일 전표 라인 수 | 파티션을 쓰지 않으므로 사전 추정 불필요. 전환이 필요해지면 `pt-online-schema-change`로 다운타임 없이 가능 |
| 소급 지연 최대치 | 영향받는 건 스냅샷 주기 하나뿐이고, 스냅샷은 순수 캐시라 언제든 주기를 바꿔 재생성 가능. 정책 기본값도 차단 없이 경고만이라 어떤 값이 와도 업무가 막히지 않음 |

두 값 모두 **이미 저장하는 데이터로 계산됩니다.** 소급 지연은 `recorded_at - occurred_at`이고, 라인 수는 세면 됩니다.

### 관측 장치 — Phase 1 포함

이걸 넣지 않으면 6개월 뒤에도 여전히 모릅니다. 야간 배치가 하루 한 줄 기록합니다.

```sql
CREATE TABLE ops_metric_daily (
  metric_date        DATE     NOT NULL,
  tenant_id          INT      NOT NULL,
  txn_count          INT      NULL,   -- 전표 건수
  ledger_line_count  INT      NULL,   -- 라인 수      → 볼륨 지표
  backdate_p50       SMALLINT NULL,   -- 소급 지연 중앙값(일)
  backdate_p95       SMALLINT NULL,
  backdate_max       SMALLINT NULL,   -- 최대 지연
  ledger_total_rows  BIGINT   NULL,   -- 원장 누적 행수
  ledger_size_mb     INT      NULL,   -- 테이블 + 인덱스 크기
  snapshot_dirty_cnt INT      NULL,
  recalc_seconds     INT      NULL,   -- 재계산 배치 소요
  PRIMARY KEY (metric_date, tenant_id)
) ENGINE=InnoDB;
```

1년에 365행이라 비용은 사실상 0입니다. 3개월이면 **소급 한계 기본값 · 파티션 전환 시점 · 스냅샷 주기**를 전부 데이터로 결정할 수 있습니다.
나아가 정책 화면에서 *"최근 90일 P95가 12일입니다 — 경고 기준을 15일로 조정하시겠습니까?"* 같은 제안까지 가능합니다.

### 모르는 상태에서 설계하는 원칙

앞으로도 계속 나올 상황이므로 원칙으로 고정합니다.

1. **차단하지 않는다** — 검증은 경고로. 임계값을 모르는 상태의 하드 블록은 현장을 멈춘다
2. **되돌릴 수 있는 쪽을 고른다** — 비파티션, 캐시형 스냅샷
3. **모르면 측정 장치를 먼저 넣는다** — 추정하지 않는다

본 문서의 모든 결정이 이 원칙을 따릅니다.

### 남은 미결 (합의 필요)

현재 미결 없음.

> 해결됨 — *재고 관리 단위*: **LOT**. `품목 × LOT × 창고(·로케이션)`. 바코드 개체 단위 아님(§2-1).
> 해결됨 — *판소재 잔재*: **Phase 1은 전량 폐기.** 외접 사각형 근사는 `spec_value2` 컬럼 자리만 잡아둠(§2-1).
> 해결됨 — *소재 출고 정렬*: **선입선출 기본.** 잔재를 먼저 쓸지는 `stock.remnant_consume` 업체 설정(§2-1).
> 해결됨 — *재공(WIP)*: **별도 테이블**. `stock_balance`에 차원을 추가하지 않습니다.
> 해결됨 — *정책 항목 최종 목록*: [정책-설정-설계.md](./정책-설정-설계.md)에서 확정(35건).

## 부록 · 결정 요약

| 결정 | 값 |
|---|---|
| 구조 | 원장 + 잔고 + 스냅샷 3층 |
| 재고 관리 단위 | **LOT** — `품목 × LOT × 창고(·로케이션)`. 바코드는 개체 식별자가 아니라 LOT 라벨 |
| 자재 LOT 발급 | `lot.material_source` — `EXTERNAL`(공급처 번호 그대로) / `INTERNAL`(자체 발급, 기본값). **시스템관리자 전용** |
| LOT 레코드 | **입고 건마다 별도 LOT.** 같은 외부 번호라도 입고 시기가 다르면 합치지 않음. `lot_no`에 UNIQUE 없음 |
| 포장 단위 | `qty`(총 수량) + **`loose_qty`(잔량 박스 수량)** 두 값으로 관리. 박스는 개체가 아님 |
| 잔량 박스 | **항상 0 또는 1개.** 수량 출고 시 잔량에서 먼저 빼고, 모자라면 완박스를 자동 개봉 |
| 원장 · 스냅샷 | **수량만.** 박스 구성은 잔고 테이블의 현재 상태로만 관리 — 수불 구조를 건드리지 않음 |
| 소재 재고 | **규격별 개수.** `1000×5` → `1000×4` + `500×1`. 규격은 `lot.spec_value`, 수량은 개수 |
| 잔고 컬럼 | **수량 하나뿐.** 규격 컬럼을 두지 않고 `lot`에서 JOIN. 규격 없는 품목은 그냥 `N개` |
| 판소재 잔재 | **Phase 1은 전량 폐기.** 외접 사각형 근사는 `item.spec_dim` · `lot.spec_value2` **자리만** 잡아둠 |
| 잔재 소진 순서 | `stock.remnant_consume` — `FIFO_MANUAL`(기본, 잔재는 수동 선택) / `REMNANT_FIRST`(잔재부터 자동). **시스템관리자 전용** |
| 재공(WIP) | **별도 테이블.** 작업지시 × 공정 단위이므로 `stock_balance`에 넣지 않음 |
| 선점 | **개념 없음.** 출고 = 실제 차감이므로 `가용 = qty`. `reserved_qty` 컬럼 자체를 두지 않음 |
| 출고 미사용 | `wo_stock` **별도 테이블**(작업지시 × 품목 × LOT). 사용처리는 원장을 남기지 않음 |
| 소재 품목 | **절대 바뀌지 않음.** 잔재는 **새 LOT**이지 새 품목이 아님 — 그래야 **BOM이 안 깨짐** |
| 잔재 추적 | `lot.parent_lot_id`로 원 조각과 연결 + 바코드 발행 |
| 원장 단위 | **개수.** 출고는 조각 전체 −1, 반납은 새 LOT +1 |
| 경계 | 재고 원장은 **창고 입출고만**. 사용량·폐기량은 **생산 실적**에 기록 |
| 출고 후보 | `lot.spec_value >= 필요 규격값` — 물리적 사실이므로 **차단** |
| 폐기 임계 | `item.min_usable_spec` **이하 잔재는 반납하지 않고 폐기.** 값은 품목마다 다름 |
| 시간축 | `occurred_at` / `recorded_at` 이중 |
| 원장 | append-only, 취소는 역분개 |
| DB | MariaDB, **파티션 미사용** |
| 헤더/라인 | 분리 (`stock_txn` / `stock_ledger`) |
| FIFO 소급 재배정 | 안 함 (경고만) |
| 공정 순서 위반 | 경고 후 허용 |
| 음수 재고 | 허용 + 미결 관리 |
| 마감 | **선택 기능**, 스냅샷과 분리 |
| 소급 한계 | 경고 30일 / 차단 없음 (기본값) |
| 볼륨·지연 수치 | 설계 입력에서 제외. `ops_metric_daily`로 운영 중 관측 |

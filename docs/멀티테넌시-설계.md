# 멀티테넌시 설계

> mes-v6 · 업체 데이터 격리 수준
> 작성일: 2026-08-28 · 상태: 확정 (미결은 §9)
> 상위 문서: [개발범위-및-MVP.md](./개발범위-및-MVP.md)

---

## 1. 결정

> **하이브리드 — 공용 DB 1개 + 테넌트마다 DB(스키마) 1개.**

MariaDB에서 `database`는 곧 스키마입니다. 테넌트마다 `mes_t001`, `mes_t002` … 를 두고,
테넌트를 가로지르는 메타데이터만 `mes_common`에 모읍니다.

```
mes_common      테넌트 · 로그인 계정 · 정책 카탈로그 · 메뉴 구조 · 라이선스 · 운영 지표
mes_t001        업체 A의 업무 데이터 전부
mes_t002        업체 B의 업무 데이터 전부
...
```

---

## 2. 왜 스키마 분리인가

| | 행 단위 (`tenant_id` 필터) | **스키마 분리** | DB 서버 분리 |
|---|---|---|---|
| 격리 | 쿼리에 의존 — **필터 누락 시 유출** | DB 경계로 보장 | 완전 격리 |
| **테넌트별 백업 · 복구** | **사실상 불가** | `mysqldump` 한 줄 | 가능 |
| **온프레미스 이관** | 데이터 추출 작업 필요 | **DB 하나만 떼면 끝** | 그대로 |
| 성능 간섭 | 한 업체의 대량 데이터가 전체에 영향 | 테이블 크기 독립 | 없음 |
| 스키마 변경 | **1회** | 테넌트 수만큼 반복 | 〃 |
| 크로스 테넌트 집계 | 쉬움 | 별도 경로 필요 | 어려움 |
| 인프라 비용 | 최소 | 최소 | 높음 |

### 결정적인 두 가지

**① 테넌트별 백업 · 복구**
*"저희 업체 데이터만 어제 시점으로 돌려주세요"* 는 반드시 옵니다.
행 단위에서는 전체를 복원한 뒤 그 테넌트 행만 골라 되돌려야 하는데,
[재고-수불-설계.md](./재고-수불-설계.md)의 원장 · 잔고 · 스냅샷이 얽혀 있어 현실적으로 불가능합니다.

**② 온프레미스 이관**
제조업 MES는 자체 서버 설치 요구가 흔합니다. 스키마 분리면 **그 DB 하나만 떼어** 옮기면 되고,
같은 코드가 테넌트 1개짜리 배포로 그대로 돕니다. 패키지 제품에서 이건 큰 이점입니다.

부수적으로, 도면 · 품번 · 원가는 제조업의 영업기밀입니다.
**경쟁사와 같은 DB에 있는 것을 계약 단계에서 거부**하는 경우가 있습니다.

### DB 서버 분리를 하지 않는 이유

완전 격리는 매력적이지만 인스턴스마다 비용과 운영 부담이 붙습니다.
**대형 고객이 요구하면 그때 그 테넌트만** 별도 서버로 뺍니다 —
스키마 분리는 이 전환이 자연스럽습니다. DB 하나를 다른 서버로 옮기면 끝입니다.

## 3. 무엇이 어디에 있나

### `mes_common` — 공용

| 테이블 | 내용 |
|---|---|
| `tenant` | 업체 · 접속 정보 · 상태 |
| `user_account` | **로그인 계정** + 소속 테넌트 (로그인 시 어느 DB로 갈지 판단) |
| `policy_def` | 정책 **카탈로그** (제품이 정의, 업체가 추가 못 함) |
| `menu` | 메뉴 **구조** (시스템관리자 전용) |
| `custom_field_slot` | 엔티티별 슬롯 정의 (제품 스펙) |
| `ops_metric_daily` | 운영 지표 ([재고-수불-설계.md](./재고-수불-설계.md) §11) |
| `migration_state` | 테넌트별 스키마 버전 |

공통점 — **시스템관리자가 관리하는 것**들입니다.
[정책-설정-설계.md](./정책-설정-설계.md) §7의 *"구조는 시스템관리자, 그 안은 업체의 권한"* 경계와 정확히 겹칩니다.

### `mes_t{id}` — 테넌트

업무 데이터 전부입니다.

- 기준정보 — `item` · `partner` · `process` · `routing` · `warehouse` · `equipment` · `lot_rule` · `label_template`
- 재고 — `stock_txn` · `stock_ledger` · `stock_balance` · `stock_snapshot` · `lot`
- 생산 — `work_order` · `work_order_op` · `work_order_op_run` · `inspection`
- 수주 · 출하 · 품질 · 첨부파일
- `policy_value` · `policy_history` — **값**은 테넌트 것
- `menu_role` — **권한 부여**는 테넌트 것
- `custom_field_def` — 시스템관리자가 편집하지만 **내용은 테넌트 고유**

> `policy_def`(카탈로그)는 공용, `policy_value`(값)는 테넌트.
> `menu`(구조)는 공용, `menu_role`(권한)은 테넌트.
> **구조와 값을 가르는 선이 DB 경계와 같습니다.**

## 4. `tenant_id`는 그대로 둔다

테넌트 DB 안에서 `tenant_id`는 항상 같은 값이라 논리적으로는 불필요합니다.
**그래도 컬럼과 인덱스 선두에 유지합니다.**

| 이유 | 설명 |
|---|---|
| 오배치 탐지 | 잘못된 DB에 쓴 행을 즉시 발견합니다 |
| 이관 · 집계 | 공용 DB로 올리거나 다른 환경으로 옮길 때 출처가 남습니다 |
| 되돌릴 수 있음 | 나중에 행 단위로 합치기로 해도 **그대로 동작**합니다 |

비용은 인덱스 엔트리당 4바이트입니다. 값이 상수라 압축도 잘 됩니다.
**"되돌릴 수 있는 쪽을 고른다"**([재고-수불-설계.md](./재고-수불-설계.md) §11) 원칙을 여기에도 적용합니다.

## 5. 접속 라우팅

```
1. 로그인            mes_common.user_account 조회 → tenant_id 확인
2. 세션에 테넌트 고정  요청마다 다시 판단하지 않음
3. 커넥션 획득        테넌트 DB 풀에서 (또는 공용 풀 + USE database)
4. 업무 처리          해당 DB 안에서만
```

- **커넥션 풀은 테넌트마다 두지 않습니다.** 테넌트가 수백이면 유휴 커넥션만 수천 개가 됩니다.
  공용 풀에서 빌린 뒤 `USE`로 전환하고, 반납 전 원복합니다
- 시스템관리자 세션은 `mes_common`에 붙되, 특정 업체를 볼 때만 그 DB로 전환합니다

## 6. 스키마 마이그레이션 — Phase 0 필수

**스키마 분리의 대가가 전부 여기 있습니다.** 테넌트 100개면 배포마다 100번입니다.

| 요구 | 내용 |
|---|---|
| 자동화 | Flyway · Liquibase 등으로 **테넌트 순회 적용** |
| 상태 추적 | `mes_common.migration_state`에 테넌트별 스키마 버전 |
| **부분 실패 처리** | 60번째에서 실패하면 앞 59개는 새 버전, 뒤는 구 버전. **혼재 상태를 견디는 코드**가 필요 |
| 신규 테넌트 | 최신 스키마로 DB 생성 + 시드(정책 기본값 · 기본 공정 · 코드) |
| 순서 | **공용 DB 먼저**, 그다음 테넌트 순회 |

> **혼재 상태를 견디는 것이 핵심입니다.** 마이그레이션 중에도 서비스는 돌아갑니다.
> 컬럼 추가는 안전하지만 **삭제 · 이름 변경은 2단계로** 나눕니다 — 새 컬럼 추가 → 코드 전환 → 다음 배포에서 제거.

이 도구를 **Phase 0에 만들지 않으면** 테넌트가 늘어난 뒤에는 손댈 수 없습니다.

---

## 7. 크로스 테넌트 집계

시스템관리자가 전체 현황을 보려면 여러 DB를 읽어야 합니다.

- **`ops_metric_daily`가 이미 공용 DB에 있습니다** — 야간 배치가 각 테넌트에서 집계해 올립니다
- 실시간 크로스 조회는 하지 않습니다. 필요하면 배치 주기를 줄입니다
- 업체별 상세는 그 테넌트 DB로 전환해서 봅니다

행 단위 대비 유일하게 불리한 지점인데, **운영 지표 테이블이 이미 그 자리를 메웁니다.**

---

## 8. 배포 형태 — 중앙 관리 / 온프레미스

**공용 DB가 항상 같은 서버에 있는 것은 아닙니다.** 업체 정보를 중앙 관리 서버에서 받아올 수도,
업체 서버 안에서 자체 설정할 수도 있어야 합니다.

| | `CENTRAL` | `ONPREMISE` |
|---|---|---|
| 설치 위치 | 우리 인프라 | **업체 서버** |
| 공용 DB | 중앙 서버의 `mes_common` | **로컬 `mes_common`** |
| 업체 정보 · 기능 스위치 | 중앙에서 직접 조회 | 관리 서버에서 **동기화**하거나 로컬 설정 |
| 관리 서버 | 자기 자신 | **선택** — 없어도 동작 |
| 테넌트 수 | N | 보통 1 |

### 설치 설정

관리 서버 주소를 **설정으로 주입**합니다. 애플리케이션은 공용 DB가 어디 있는지 알 필요가 없습니다.

```
deployment.mode          CENTRAL | ONPREMISE
management.server.url    https://…          ONPREMISE에서는 비워둘 수 있음
management.tenant.key    발급 키 (인증 · 라이선스 식별)
common.datasource        jdbc:mariadb://…/mes_common
tenant.datasource.pattern jdbc:mariadb://…/mes_t{id}
```

### 부팅 흐름

```
CENTRAL
  → 중앙 mes_common 직접 접속 → 테넌트 목록 · 정책 카탈로그 · 기능 스위치 로드

ONPREMISE + 관리 서버 설정됨
  → 관리 서버에서 업체 정보 · 기능 스위치 · 정책 카탈로그 · 라이선스 조회
  → 로컬 mes_common에 동기화
  → 이후 업무는 로컬에서만 읽음. 주기적으로 갱신

ONPREMISE + 관리 서버 없음
  → 로컬 mes_common만 사용 (설치 시 시드된 값)
  → 완전 오프라인 동작
```

### 관리 서버가 끊겨도 멈추지 않는다

**온프레미스에서 관리 서버 접속 실패는 오류가 아닙니다.** 로컬 `mes_common`의 마지막 값으로 계속 돕니다.

관리 서버가 내려주는 것은 전부 **시스템관리자 영역**입니다 — 업체 정보 · 기능 스위치 · 정책 카탈로그 ·
메뉴 구조 · 라이선스. [정책-설정-설계.md](./정책-설정-설계.md) §7 그대로 **자주 바뀌지 않는 값**이라
캐시해도 안전합니다. 업무 데이터는 애초에 관리 서버로 나가지 않습니다.

- 동기화 실패는 **경고 로그와 관리 화면 표시**로만 남깁니다
- 마지막 동기화 시각을 보여줘 언제 것인지 알 수 있게 합니다
- 라이선스 만료 판정도 로컬 값 기준입니다 — 네트워크 문제로 업무가 멈추면 안 됩니다

### 로컬 `mes_common`은 항상 존재한다

`ONPREMISE`에서 관리 서버를 쓰든 안 쓰든 **로컬 공용 DB는 반드시 둡니다.**
관리 서버는 그것을 채우는 경로일 뿐이고, 애플리케이션은 언제나 로컬을 읽습니다.
이 구조라야 오프라인 설치와 온라인 설치가 **같은 코드**로 돕니다.

## 9. 미결

| # | 항목 | 확인 필요 |
|---|---|---|
| 1 | **예상 테넌트 수** | 수십이면 문제없고, 수백을 넘으면 테이블 수(테이블 × 테넌트)가 `innodb_open_files`와 파일 핸들에 걸립니다. 그때는 서버를 나눠야 합니다 |
| 2 | **온프레미스 비중** | 온프레미스가 주력이면 공용 DB도 함께 배포해야 하고, 라이선스·업데이트 경로가 달라집니다 |

둘 다 **지금 몰라도 설계가 흔들리지 않습니다.** 1번은 `ops_metric_daily`로 관측하고,
2번은 영업이 진행되면 드러납니다.

### 추후 결정 — 서명된 라이선스 키

관리 서버 없이 설치하면 시스템관리자가 **로컬에서 기능 스위치를 켤 수 있습니다.**
라이선스 우회가 실제로 문제가 되는지는 사업 모델에 달렸습니다 —
설치 · 유지보수 계약 기반이라면 신경 쓸 필요가 없습니다.

**Phase 1은 이것 없이 진행합니다.** 나중에 필요해지면 이렇게 붙습니다.

| 붙는 곳 | 내용 |
|---|---|
| `management.tenant.key` | 이미 설치 설정에 있는 자리를 **서명 키**로 승격 |
| 기능 스위치 로드 | 부팅 시 서명 검증 후 `mes_common`에 반영 |
| 검증 실패 | 기본 기능 세트로 축소 실행 (**중단하지 않음**) |

검증 지점을 **부팅 시 한 곳**으로 모아두면 나중에 끼워 넣기 쉽습니다.
업무 코드는 기능 스위치를 읽을 뿐 서명을 알 필요가 없습니다.

## 부록 · 결정 요약

| 결정 | 값 |
|---|---|
| 격리 수준 | **하이브리드** — 공용 DB 1개 + **테넌트마다 DB(스키마) 1개** |
| 공용 DB | 테넌트 · 로그인 계정 · 정책 카탈로그 · 메뉴 구조 · 슬롯 정의 · 운영 지표 · 마이그레이션 상태 |
| 테넌트 DB | 업무 데이터 전부 + `policy_value` · `menu_role` · `custom_field_def` |
| 가르는 선 | **구조는 공용, 값은 테넌트** — 정책 문서 §7의 권한 경계와 동일 |
| `tenant_id` | 테넌트 DB에도 **유지** (오배치 탐지 · 이관 · 되돌리기) |
| 커넥션 | 테넌트별 풀을 두지 않음. 공용 풀 + `USE` 전환 |
| 마이그레이션 | **Phase 0 필수.** 테넌트 순회 + 버전 추적 + **혼재 상태 허용** |
| 크로스 집계 | 실시간 조회 없음. `ops_metric_daily` 배치로 공용 DB에 적재 |
| DB 서버 분리 | 하지 않음. 대형 고객이 요구하면 **그 테넌트만** 이전 |
| 배포 형태 | `CENTRAL`(우리 인프라) / `ONPREMISE`(업체 서버). **설정으로 주입** |
| 관리 서버 | 주소를 설정에 넣음. 온프레미스에서는 **선택** — 없어도 동작 |

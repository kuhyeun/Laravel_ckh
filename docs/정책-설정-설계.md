## 1. 왜 필요한가

이 시스템은 **패키지형 MES**입니다. 업체마다 다르게 동작해야 하는 항목이 요구사항 원문에만 20건 이상 흩어져 있고, 설계 과정에서 6건이 더 나왔습니다.

> "특정 메뉴는 **사용여부 설정**으로 자동 추가/삭제" · "거래처별 입고시 무검사, 샘플링, 전수검사 **선택**"
> "품목별로 자재 차감어디서 하는지 **설정**" · "원자재는 생산공정시작전/외주출고전 자동차감 **가능\*설정**"
> "불량만 등록 or 검사완료처리 **옵션선택**" · "업체에서 **필요한만큼** 설정"

각 모듈이 제각각 `if (설정)`을 짜면, 정책이 하나 추가될 때마다 전 모듈을 뒤져야 합니다. **공통 정책 서비스 하나로 모읍니다.**

## 2. 먼저 — 이것들은 한 종류가 아니다

"업체마다 다른 것"을 전부 한 메커니즘으로 처리하려 하면 실패합니다. 성격이 다른 넷이 섞여 있습니다.

| 분류 | 성격 | 값 형태 | 담당 |
|---|---|---|---|
| **A. 기능 스위치** | 모듈을 켜고 끔. 메뉴 노출과 연동 | 참/거짓 1개 | **정책 서비스** |
| **B. 업무 규칙** | 시스템 동작을 바꿈 | 스칼라 1개 | **정책 서비스** |
| **C. 설정 마스터** | 업체가 **N개를 등록** | 레코드 여러 건 | **각자 마스터 테이블** |
| **D. 표현 설정** | 화면 구성을 바꿈 | 구조가 제각각 | **별도 서브시스템** |

### C를 정책 서비스에 넣지 않는 이유

LOT규칙은 "업체에서 필요한만큼 설정"하고 작업지시 때 **골라서** 씁니다. 값이 하나가 아니라 목록이고, 각 항목이 여러 필드를 가집니다. 키-값 정책으로 표현하면 지저분해지고 참조무결성도 잃습니다.

| C에 속하는 것 | 전용 테이블 |
|---|---|
| LOT규칙 (N개, 작업지시 시 선택) | `lot_rule` |
| 라벨 템플릿 (규격 · 분할 · 요소 배치, N개) | `label_template` — 기본 제공 **100 × 70mm**. 업체 보유 프린터에 맞춰 변경 |
| 제조리드타임 (default + 품목별, 5개 구간) | `lead_time` |
| 검사기준서 | `inspection_spec` |
| 공통코드 · 첨부파일 구분 | `code` |
| 거래처 담당자 N · 출고지 N | `partner_contact` / `partner_site` |
| **라우트시트 안내문** (General Information) | `routesheet_notice` — 업체 사용자가 작성 |

### D를 분리하는 이유

커스텀 컬럼은 값이 아니라 **스키마**를 바꿉니다. 컬럼명 관리는 i18n에 가깝고, 메뉴 구성은 트리 구조입니다. 셋 다 정책의 키-값 모델에 맞지 않습니다.

| D에 속하는 것 | 담당 |
|---|---|
| 커스텀 컬럼 정의 (**시스템관리자 전용**) | `custom_field_def` → [커스텀-컬럼-설계.md](./커스텀-컬럼-설계.md) |
| 컬럼명 관리 (**시스템관리자 전용**) | `column_label` |
| 메뉴 구성 (**시스템관리자 전용**) | `menu` |
| 메뉴별 접근 권한 (업체) | `menu_role` |

> **권한(RBAC)도 정책이 아닙니다.** 사용자·역할 기반이고 검사 시점이 완전히 다릅니다. 별도 시스템으로 둡니다.

### 업무 데이터가 이미 답을 갖고 있으면 정책을 만들지 않는다

같은 것을 두 군데서 결정하면 반드시 어긋납니다. 아래는 정책처럼 보이지만 **정책이 아닙니다.**

| 항목 | 실제 결정 주체 | 근거 |
|---|---|---|
| 공정검사를 할 것인가 | **공정라우팅에 검사 공정이 들어 있는가** | 원문 *"공정라우팅 설정시 검사넣기"* |
| 초 · 중 · 종물 검사를 할 것인가 | **라우팅에 초중종 검사 공정을 배치하는가** | 원문 *"공정검사관리(…초중종…)"* |
| 생산 전후 자동 행위 (자동 발주 · 자동 출하) | **공정라우팅의 전후 행위 지정** | 원문 *"공정라우팅에서 ... 생산 전후 행위 미리 지정"* |

둘 다 **전체 테넌트에 일괄 적용되는 값이 아니라 라우팅마다 다른 값**입니다.
정책 키를 만들면 라우팅 데이터와 충돌합니다.

**이 문서가 다루는 것은 A와 B입니다.**

## 3. 스코프 계층

```
SYSTEM   제품 기본값 — 코드/시드에 존재, 업체가 못 바꿈
   └ TENANT   업체 설정
        └ ENTITY   거래처 · 품목 · 공정 · 창고 단위 오버라이드
```

**모든 정책이 모든 스코프를 갖지는 않습니다.** 정책마다 허용 스코프를 정의합니다.

| 예시 | 허용 스코프 | 근거 |
|---|---|---|
| 음수 재고 허용 | `TENANT` | 업체 단위 운영 방침 |
| 입고검사 방식 | `TENANT → ITEM → PARTNER` | 원문 "거래처별 입고시 무검사, 샘플링, 전수검사 선택" **+ "검사필수/무검사 - 품목"** |
| 자재 차감 위치 | `TENANT → ITEM` | 원문 "품목별로 자재 차감어디서 하는지 설정" |
| 공정검사 필수 | `TENANT → PROCESS` | 원문 "공정라우팅 설정시 검사넣기" — 품목 단위 설정은 **입고검사** 쪽 |

허용하지 않은 스코프에 값을 넣으려 하면 **저장 시점에 거부**합니다. 조용히 무시하면 "설정했는데 안 먹는다"가 됩니다.

## 4. 해석 규칙

```
resolve(tenant, policy_key, context) :
  1. policy_def 조회 — 미등록 키면 예외 (오타를 런타임에 잡음)
  2. depends_on 확인 — 선행 정책이 조건값이 아니면 이 정책은 무의미
  3. allowed_scopes 를 구체적인 것부터 탐색
        ENTITY(process → item → partner) → TENANT → default_value
  4. merge_strategy 적용
```

### 스코프 충돌

거래처 A는 `전수검사`인데 품목 X는 `무검사`이면 어떻게 되는가.

| 전략 | 동작 | 적용 |
|---|---|---|
| `OVERRIDE` | 더 구체적인 스코프가 이김 | 대부분의 정책 |
| `EXEMPT_THEN_PRIORITY` | **면제값이 나오면 즉시 확정**, 그 외에는 지정 스코프가 우선 | `quality.incoming_inspection` |

#### `EXEMPT_THEN_PRIORITY` — 입고검사

확정 규칙: **품목이 무검사면 거래처를 무시하고, 그 외에는 거래처가 우선한다.**

품목 특성상 검사가 무의미한 것(포장재·소모품)은 어느 거래처에서 사오든 무검사입니다.
검사 대상 품목이면, 얼마나 볼지는 **거래처 신뢰도**가 결정합니다.

```
1. 면제 스코프(ITEM) 값이 면제값(NONE)이면   → NONE 확정      ← "품목이 무검사이면 업체 무시"
2. 우선 스코프(PARTNER) 에 값이 있으면       → PARTNER        ← "이외 업체 우선"
3. 나머지 스코프를 구체적인 순서로            → ITEM
4. TENANT
5. default_value
```

**2단계는 "값이 있을 때"만 이깁니다.** 거래처에 설정이 없으면 우선할 대상이 없으므로 다음으로 구체적인
스코프(품목)를 따릅니다. 이게 없으면 품목의 `샘플링`·`전수`가 영원히 적용되지 않는 죽은 값이 됩니다.

| 품목 | 거래처 | 결과 | 근거 |
|---|---|---|---|
| `무검사` | `전수` | **`무검사`** | ① 품목 면제가 거래처를 무시 |
| `무검사` | 미설정 | **`무검사`** | ① |
| `전수` | `무검사` | `무검사` | ② 거래처 우선 |
| `전수` | `샘플링` | `샘플링` | ② |
| **`샘플링`** | **미설정** | **`샘플링`** | ③ 거래처 값이 없으면 품목을 따름 |
| 미설정 | `전수` | `전수` | ② |
| 미설정 | 미설정 | 테넌트 → default | ④⑤ 상속 |

> 주의: `전수` 품목이라도 거래처를 `무검사`로 걸면 검사하지 않습니다(②).
> 거래처 무검사는 명시적 판단이므로 존중하되, 화면에서 **"품목 입고검사 설정(전수)을 덮어씁니다"** 를 경고로 표시합니다.

### 캐시

정책은 **읽기가 극단적으로 많고 쓰기는 거의 없습니다.** 전표 등록 한 건에도 여러 번 조회됩니다.

- 테넌트 단위로 **전체 로드 후 인메모리 캐시**
- 값 변경 시 해당 테넌트 캐시 무효화
- DB를 매번 때리면 안 됩니다

## 5. 스키마

```sql
-- 정책 카탈로그 : 제품이 정의. 마이그레이션으로 시드, 업체가 추가 못 함
CREATE TABLE policy_def (
  policy_key     VARCHAR(60)  NOT NULL,      -- 'stock.allow_negative'
  category       VARCHAR(10)  NOT NULL,      -- FEATURE | RULE
  value_type     VARCHAR(10)  NOT NULL,      -- BOOL | INT | ENUM | STRING
  enum_values    VARCHAR(500) NULL,          -- 'NONE,SAMPLING,FULL' (화면 표시 순서)
  default_value  VARCHAR(200) NULL,          -- SYSTEM 기본값
  allowed_scopes VARCHAR(100) NOT NULL,      -- 'TENANT' | 'TENANT,ITEM'
  merge_strategy VARCHAR(25)  NOT NULL DEFAULT 'OVERRIDE',
  exempt_value   VARCHAR(30)  NULL,          -- EXEMPT_THEN_PRIORITY: 면제값 'NONE'
  exempt_scope   VARCHAR(10)  NULL,          -- EXEMPT_THEN_PRIORITY: 면제가 최우선인 스코프 'ITEM'
  priority_scope VARCHAR(10)  NULL,          -- EXEMPT_THEN_PRIORITY: 값이 있으면 이기는 스코프 'PARTNER'
  depends_on_key   VARCHAR(60) NULL,        -- 이 정책이 유효하려면
  depends_on_value VARCHAR(30) NULL,        -- 이 값이어야 함 (NULL이면 truthy)
  label_ko       VARCHAR(100) NOT NULL,
  description_ko VARCHAR(500) NULL,
  editable_by    VARCHAR(15)  NOT NULL DEFAULT 'TENANT',  -- SYSTEM_ADMIN | TENANT
  ui_group       VARCHAR(30)  NULL,          -- 설정 화면 그룹
  ui_order       SMALLINT     NOT NULL DEFAULT 0,
  is_visible     BOOLEAN      NOT NULL DEFAULT TRUE,   -- FALSE = 내부 튜닝값
  PRIMARY KEY (policy_key)
) ENGINE=InnoDB;

-- 정책 값
CREATE TABLE policy_value (
  tenant_id   INT          NOT NULL,
  policy_key  VARCHAR(60)  NOT NULL,
  scope_type  VARCHAR(10)  NOT NULL,   -- TENANT | PARTNER | ITEM | PROCESS | WAREHOUSE
  scope_id    BIGINT       NOT NULL DEFAULT 0,   -- TENANT 스코프면 0
  value       VARCHAR(200) NOT NULL,
  updated_at  DATETIME(6)  NOT NULL,
  updated_by  BIGINT       NOT NULL,
  PRIMARY KEY (tenant_id, policy_key, scope_type, scope_id),
  KEY ix_scope (tenant_id, scope_type, scope_id),
  CONSTRAINT fk_pv_def FOREIGN KEY (policy_key) REFERENCES policy_def(policy_key)
) ENGINE=InnoDB;

-- 변경 이력 (감사 · 소급 판단 근거)
CREATE TABLE policy_history (
  id          BIGINT      NOT NULL AUTO_INCREMENT,
  tenant_id   INT         NOT NULL,
  policy_key  VARCHAR(60) NOT NULL,
  scope_type  VARCHAR(10) NOT NULL,
  scope_id    BIGINT      NOT NULL,
  old_value   VARCHAR(200) NULL,
  new_value   VARCHAR(200) NULL,
  changed_at  DATETIME(6) NOT NULL,
  changed_by  BIGINT      NOT NULL,
  reason      VARCHAR(300) NULL,
  PRIMARY KEY (id),
  KEY ix_key (tenant_id, policy_key, changed_at)
) ENGINE=InnoDB;
```

### 왜 컬럼 방식이 아니라 키-값인가

`tenant_stock_policy` 같은 전용 컬럼 테이블은 타입 안전하고 빠릅니다. 그런데 **패키지 제품이라 정책이 계속 늘어납니다.** 정책 하나 추가할 때마다 DDL + 마이그레이션 + 화면 수정이 반복됩니다.

카탈로그 + 키-값 조합이면 **정책 추가가 시드 데이터 한 줄**이고, 설정 화면도 자동 생성됩니다(§8). 타입 안전성은 코드 쪽 상수와 타입 캐스팅 헬퍼로 확보합니다.

```java
// 문자열 키를 직접 쓰지 않는다
public enum StockPolicy implements PolicyKey {
    ALLOW_NEGATIVE("stock.allow_negative", Boolean.class),
    BACKDATE_WARN_DAYS("stock.backdate_warn_days", Integer.class),
    ...
}

boolean allowNegative = policy.get(StockPolicy.ALLOW_NEGATIVE);
InspectionMode mode = policy.get(QualityPolicy.INCOMING_INSPECTION,
                                 PolicyContext.partner(partnerId));
```

## 6. 정책 카탈로그

### A. 기능 스위치 — `FEATURE` (스코프: TENANT)

메뉴 노출과 직접 연동됩니다. 원문 *"특정 메뉴는 사용여부 설정으로 자동 추가/삭제"*.

> **기능 스위치는 시스템관리자 고유 권한입니다.**
> 업체 사용자·관리자는 켜거나 끌 수 없습니다. 원문의 `시스템관리(슈퍼관리자) : 기능옵션관리`와 일치합니다.
> 상세는 §7.

| 키 | 라벨 | 기본값 | 비고 |
|---|---|---|---|
| `feature.warehouse` | 창고관리 사용 | `true` | 원문 명시 |
| `feature.lot` | LOT관리 사용 | `true` | 원문 명시 |
| `feature.barcode` | 바코드관리 사용 | `true` | 원문 명시 |
| `feature.approval` | 전자결재 사용 | `false` | Phase 2 |
| `feature.subcontract` | 외주관리 사용 | `false` | Phase 2 |
| `feature.equipment` | 설비관리 사용 | `false` | Phase 3 |
| `feature.claim` | 클레임관리 사용 | `false` | Phase 2 |
| `feature.closing` | 재고 마감 사용 | `false` | 업체마다 다름 |
| `feature.bom` | **BOM 메뉴 사용** | `true` | **실 가공만 하는 업체는 끕니다** — 품목의 주 자재로만 관리 |
| `feature.custom_column` | 커스텀 컬럼 사용 | `false` | Phase 2 |
| `feature.production_plan` | 생산계획 시뮬레이션 사용 | `false` | Phase 2 |
| `feature.serial` | **시리얼 번호 사용** | `false` | 켜야 품목에서 고를 수 있습니다. **어느 품목에 붙일지는 `item.serial_use`** |

### B-1. 재고 · 수불 — 스코프 `TENANT`

| 키 | 타입 | 기본값 | 근거 |
|---|---|---|---|
| `stock.allow_negative` | BOOL | `true` | 수불설계 §5.3 |
| `stock.backdate_warn_days` | INT | `30` | 수불설계 §6 |
| `stock.backdate_block_days` | INT | `null` (차단 없음) | 수불설계 §6 |
| `stock.backdate_role` | STRING | `null` | 초과 시 필요 권한 |
| `stock.fifo_reassign` | BOOL | `false` | 수불설계 §5.1 |
| `stock.snapshot_cycle` | ENUM `MONTH,WEEK` | `MONTH` | **내부 튜닝값** (`is_visible=false`) |

### B-3. 품질

#### 검사를 하느냐는 이미 다른 것이 답한다

| 검사 | "한다 / 안 한다"를 정하는 것 |
|---|---|
| 입고 | `quality.incoming_inspection` = `NONE` / `SAMPLING` / `FULL` |
| 공정 | **공정라우팅에 검사 공정을 넣는가** (§2 — 라우팅 데이터) |
| 출하 | `quality.shipping_inspection` = 켜짐 / 꺼짐 |

정책이 여기에 또 개입하면 같은 것을 두 군데서 결정하게 됩니다.

#### 정책이 정하는 것은 "어떻게 완료 처리하는가"

원문: *"모든 품질 처리는 검사완료처리/첨부파일첨부, 필요시 **불량만 등록 or 검사완료처리 옵션선택**"*

| 모드 | 동작 |
|---|---|
| **`SIMPLE`** | **검사완료 버튼**을 누르면 "했음"으로 처리하고 넘어간다. 첨부파일은 붙일 수 있고, **불량이 있으면 그때 불량을 등록**한다 |
| **`SHEET`** | **검사시트를 작성해야** 완료 처리가 된다. 항목별 결과가 기록으로 남는다 |

**입고 · 공정 · 출하가 각각 독립된 키를 가집니다.** 구조는 같고 값은 따로 설정합니다 —
공정은 시트를 쓰고 출하는 버튼만 누르는 운영이 실제로 있습니다. 하나로 묶으면 안 됩니다.

| 키 | 타입 | 스코프 | 기본값 |
|---|---|---|---|
| `quality.mode.incoming` | ENUM `SIMPLE,SHEET` | `TENANT` | `SIMPLE` |
| `quality.mode.process` | ENUM `SIMPLE,SHEET` | `TENANT` | `SIMPLE` |
| `quality.mode.shipping` | ENUM `SIMPLE,SHEET` | `TENANT` | `SIMPLE` |

#### 모드가 바꾸는 것은 기록 깊이만이 아니다 — 처리 주체와 화면이 바뀐다

| | `SIMPLE` | `SHEET` |
|---|---|---|
| 처리 화면 | **업무 화면**에서 검사완료 버튼 | **품질관리 메뉴**에서 검사지 작성 후 완료처리 |
| 담당 | 현장 · 업무 담당자 | **품질 담당자** |
| 업무 화면의 검사완료 버튼 | 활성 | **누를 수 없음 (비활성)** |
| 해당 순서의 상태 | 즉시 완료 | **검사 대기중** |

`SHEET`에서 현장이 검사완료를 누를 수 없는 이유는, **검사지 작성이 완료의 전제조건**이고
그 작업이 품질관리 메뉴에 있기 때문입니다. 업무 화면은 대기 상태만 보여줍니다.

입고 · 공정 · 출하가 같은 구조입니다.

| 검사 | `SIMPLE` 처리 화면 | `SHEET` 처리 화면 |
|---|---|---|
| 입고 | 입고 등록 | 품질관리 · 입고검사 |
| 공정 | **공정실적관리** | 품질관리 · 공정검사 |
| 출하 | 출하 | 품질관리 · 출하검사 |

#### `SHEET`는 업무 진행을 막는다

버튼만 비활성되는 게 아니라 **그 다음 업무가 진행되지 않습니다.**

| 검사 | 정책 키 | 그 키가 `SHEET`일 때 |
|---|---|---|
| **입고** | `quality.mode.incoming` | 입고 등록 후 **검사대기**. 품질관리에서 검사완료 처리해야 **입고할 수 있음** |
| **공정** | `quality.mode.process` | 해당 순서 **대기중**. 현장에서 스캔으로 넘길 수 없음 |
| **출하** | `quality.mode.shipping` | **출하대기**. 검사완료 처리해야 출하할 수 있음 |

**세 키는 완전히 독립입니다.** 한쪽이 `SHEET`라고 다른 쪽이 따라가지 않습니다 —
`공정만 SHEET, 입고·출하는 SIMPLE` 같은 조합이 정상적인 설정입니다.

입고가 가장 분명합니다 — 원문 *"입고검사관리(자재입고전 검사/입고처리)"* 대로 **검사가 입고보다 선행**합니다.

```
SHEET 모드 · 입고검사 대상 자재

  1. 자재 도착 → 입고 등록          stock_txn.status = DRAFT   (검사대기)
                                     원장 미기록 · 재고 미반영
  2. 품질관리에서 검사지 작성 + 완료
  3. (incoming_confirm_required = true 면 자재팀 확인)
  4. 입고 처리                       stock_txn.status = CONFIRMED
                                     stock_ledger INSERT + stock_balance 갱신
```

**검사대기 중인 자재는 재고에 잡히지 않습니다.** 전표 헤더만 존재하고 원장은 아직 쓰이지 않습니다
([재고-수불-설계.md](./재고-수불-설계.md) §9.1의 `stock_txn.status`가 이 상태를 담습니다).

`SIMPLE`이면 입고 화면에서 검사완료 버튼을 누르고 그 자리에서 입고 처리까지 끝납니다.
검사 대상이 아니면(입고검사 `NONE`) 검사 단계 없이 바로 입고합니다.

#### 검사 대기는 정책이 아니라 불변 규칙이다

**대기중인 검사 공정을 건너뛰고 다음 공정을 진행할 수 없습니다.** 설정으로 열 수 없는 하드 블록입니다.

`production.process_order_block`(기본: 경고 후 허용)과 혼동하면 안 됩니다. 원인이 다릅니다.

| 상황 | 원인 | 처리 |
|---|---|---|
| 선행 공정 실적이 아직 등록 안 됨 | **소급 입력** — 현장에서는 이미 했고 전산이 늦은 것 | `production.process_order_block`<br>기본: 경고 후 허용 |
| 선행 검사 공정이 **검사 대기** | **아직 검사가 안 끝난 것** | **항상 차단 · 정책 없음** |

소급 입력은 이미 일어난 일을 늦게 넣는 것이라 막으면 현장이 멈춥니다.
검사 대기는 품질 담당자가 **아직 판정하지 않은** 상태이므로, 통과시키면 불량품이 다음 공정으로 흘러갑니다.

입고 · 출하도 같습니다 — 검사대기 자재는 입고되지 않고, 출하대기 건은 출하되지 않습니다.
**세 곳 모두 하드 블록**입니다.

> **라우트시트에 반영할 것**
> 검사 공정이 대기중일 때 다음 공정을 스캔하면 **거부**하고, 이유를 명확히 보여줍니다 —
> *"○공정 검사 대기중 · 품질관리에서 검사완료 후 진행"*.
> 스캔이 조용히 실패하면 현장은 바코드가 안 읽힌 줄 알고 계속 찍습니다.

> **`SHEET`는 Phase 2입니다.** 검사시트를 어떤 방식으로 작성할지가 아직 미결이기 때문입니다
> ([개발범위-및-MVP.md](./개발범위-및-MVP.md) §4-7 · §5 미확정 #5).
> **Phase 1은 `SIMPLE`만** 구현합니다 — 검사완료 버튼 + 첨부파일 + 불량 등록.

#### 검사 대상 · 강도

| 키 | 타입 | 스코프 | 전략 | 기본값 |
|---|---|---|---|---|
| `quality.incoming_inspection` | ENUM `NONE,SAMPLING,FULL` | `TENANT → ITEM → PARTNER` | **`EXEMPT_THEN_PRIORITY`**<br>면제 `NONE`@`ITEM` · 우선 `PARTNER` | `NONE` |
| `quality.incoming_confirm_required` | BOOL | `TENANT` | OVERRIDE | `false` |
| `quality.shipping_inspection` | BOOL | `TENANT → ITEM` | OVERRIDE | `false` |

**공정검사에는 대응하는 설정 키가 없습니다.** 공정라우팅에 검사 공정을 넣는 것이 곧 설정입니다 —
원문 *"라우팅에서 검사를 설정하여 검사진행 및 완료처리"*.

#### 공정검사 4가지 시점을 어디에 넣는가

원문: *"공정검사관리(**공정시작전 / 초중종 / 공정진행후 / 직접의뢰**)"*

넷을 한 방식으로 표현할 수 없습니다. **초중종만 성격이 다릅니다** —
나머지 셋은 한 시점이지만 초중종은 **한 공정 안에서 3번** 일어납니다.

| 시점 | 표현 방법 | 라우트시트에서 |
|---|---|---|
| **공정 시작 전** | 라우팅에 검사 공정을 대상 공정 **앞**에 배치 | 별도 순서 |
| **초 · 중 · 종물** | 라우팅에 **초중종 검사 공정**을 대상 공정 **바로 뒤**에 배치 | 별도 순서 **1줄** (초/중/종은 그 안의 체크포인트) |
| **공정 진행 후** | 라우팅에 검사 공정을 대상 공정 **뒤**에 배치 | 별도 순서 |
| **직접 의뢰** | 라우팅과 무관. 사용자가 언제든 검사 의뢰를 생성 | 표시하지 않음 (별건) |

초 · 중 · 종을 각각 라인으로 쪼개지 않습니다. **초중종 검사는 라우팅에서 한 줄**이고,
초물 · 중물 · 종물은 그 줄 안의 체크포인트 3개이고, **각각 켜고 끕니다** —
초물과 종물만 하는 현장이 있습니다(`routing_line.insp_first` · `insp_middle` · `insp_last`).
**검사 공정 완료는 켜진 것 중 마지막**을 기준으로 합니다.

검사 공정의 종류는 공정 마스터가 구분합니다.

```sql
process (
  ..., process_type = 'INSPECTION',
  inspection_kind   -- NORMAL | IFL(초중종)
)
```

검사 기록은 `inspection.type`으로 구분합니다 — `BEFORE` / `IFL_FIRST` / `IFL_MIDDLE` / `IFL_LAST` / `AFTER` / `ADHOC`.

#### 공정 진행 조건 — 앞 라인의 유형에 따라 다르다

**초중종 검사는 앞 생산 공정과 병행합니다.** 생산이 끝날 때까지 기다리지 않습니다.

| 앞 라인 | 다음 라인이 시작 가능한 조건 |
|---|---|
| **생산 공정** | **시작(s)이 기록되면** — 수량 0이어도, 완료되지 않아도 열립니다 |
| **검사 공정** | **검사 완료 처리되면** |

```
  [생산공정 A] ─────────────────────────────▶ (아직 진행 중일 수 있음)
        │ 시작(s) 기록 — 수량 0이어도
        ▼
  [초중종 검사] ── 초물 ── 중물 ── 종물 ──▶ 검사 완료
                                              │
                                              ▼
                                        [다음공정 B] 시작 가능
```

- 생산공정 A가 **시작되면 초중종 검사를 바로 시작**할 수 있습니다 — 수량이 찍히기를 기다리지 않습니다
- **종물 검사가 완료되면 검사 공정이 완료**됩니다. 이때 **생산공정 A는 끝났을 수도, 아직 진행 중일 수도 있습니다**
- 검사 완료 전에 막히는 것은 **다음 공정 B의 시작뿐**입니다. 생산공정 A는 계속 진행됩니다

초물이 본 생산을 막지 않는다는 점이 중요합니다 — 검사와 생산은 **동시에 굴러갑니다.**

#### 초물은 원칙이지 강제가 아니다

**초물검사를 해야 본 생산이 진행되는 것이 원칙**이지만, 시스템이 완전히 차단하지 않습니다.
현장의 생산 흐름에 따라 **사용자가 조정할 수 있는 부분**입니다.

| 상황 | 처리 |
|---|---|
| 초물 미완료 상태에서 본 생산 수량 누적 | **경고 후 허용** — 현장이 판단 |
| 중물 미실시 | 경고만 — **종물을 완료해 검사 공정을 닫으려 할 때** 표시 |
| **켜진 것 중 마지막이 미완료 = 검사 공정 미완료** + 다음 공정 시작 | **차단** |

**중물은 작업자가 임의 시점에 진행합니다.** 시스템이 수량 비율이나 주기로 시점을 계산하지 않습니다.
그래서 "중물 미실시" 경고는 진행 중에 띄우지 않고, **종물을 완료해 검사 공정을 닫는 시점**에 한 번 표시합니다.
그 전에는 언제 해야 하는지 시스템이 알 수 없기 때문입니다.

정책 키를 새로 만들지 않습니다. 초물 경고는 시스템이 항상 표시하고, 진행 여부는 현장이 정합니다.
막아야 할 유일한 지점은 **검사 완료 전 다음 공정 시작**이며, 이건 앞서 정한 하드 블록 그대로입니다.

#### 초중종에도 `quality.mode.process`가 그대로 적용된다

체크포인트마다 다른 방식을 쓰지 않습니다.

- `SIMPLE` — 초 · 중 · 종 각각 **검사완료 버튼**으로 처리
- `SHEET` — 초 · 중 · 종 각각 **품질관리에서 검사지 작성** 후 완료. 공정실적관리 버튼은 비활성, 해당 순서 **대기중**

`SHEET`이면 종물 검사지가 완료되어야 검사 공정이 완료되고, 그때 다음 공정이 열립니다.

#### 스코프 근거

- **품목 단위 검사 설정은 입고검사의 것입니다.** 원문 *"검사필수/무검사 - 품목"* 이 여기 붙습니다. 공정과는 무관합니다.
- `shipping_inspection`은 **품목에 출하검사 사용여부를 설정**합니다. 켜짐/꺼짐 둘뿐이라 `BOOL`입니다.
  거래처(고객사) 스코프는 없습니다 — 출하검사 여부는 무엇을 만들었는지로 정해지지 누구에게 보내는지로 정해지지 않습니다.
- `incoming_confirm_required`는 원문 *"자재입고전 검사/입고처리(자재팀 확인후\*옵션)"*.

#### 불량 등록

**두 모드 모두 불량을 등록합니다.** `SIMPLE`은 검사완료 화면에서 "필요시" 등록하고,
`SHEET`는 시트의 항목별 결과에서 불량이 파생됩니다.
불량관리·불량이슈관리는 모드와 무관하게 동작하며, 데이터는 같은 테이블에 쌓입니다.

검사 자체가 없는 경로(입고 `NONE`, 라우팅에 검사 공정 없음, 출하검사 꺼짐)에서는
**업무 화면에서 직접** 불량을 등록합니다 — 입고 등록, 생산실적, 출하 화면.

### B-4. 생산 — 스코프 `TENANT`

| 키 | 타입 | 기본값 | 근거 |
|---|---|---|---|
| `production.process_order_block` | BOOL | `false` | 수불설계 §5.2 — 경고 후 허용 |
| `production.scan_qty_presets` | STRING | `5,10,50,100,150,200` | 원문 수량 바코드 |
| `production.equipment_manual_qty` | BOOL | `true` | 원문 *"수동으로 처리 가능해야 함"* |

### B-5. 바코드 · 라벨 — 스코프 `TENANT`, `feature.barcode` 의존

| 키 | 타입 | 기본값 | 근거 |
|---|---|---|---|
| `barcode.allow_duplicate_no` | BOOL | `true` | 원문 *"동일한 바코드 번호로 발행 가능"* |
| `barcode.allow_pre_issue` | BOOL | `true` | 원문 *"미리 선발행"* |
| `barcode.print_count_default` | INT | `1` | 원문 *"몇장씩 프린트할지"* |

### B-6. 화면 · 조회 기본값 — 스코프 `TENANT`

목록 화면의 기본 검색 기간처럼, 업무 로직을 바꾸지 않고 **사용 편의만 조정**하는 값입니다.

| 키 | 타입 | 기본값 | 의미 |
|---|---|---|---|
| `auth.qr_login` | ENUM `OFF,QR_ONLY,QR_PIN` | `QR_ONLY` | **현장 QR 로그인.** 관리자 계정은 언제나 불가. **시스템관리자 전용** |
| `auth.qr_idle_minutes` | INT | `10` | **공용 단말 유휴 자동 로그아웃.** 남의 이름으로 실적이 남는 것을 막습니다 |
| `ui.search_range_from_days` | INT | `-10` | 기본 검색 시작일 = 오늘 + N일 |
| `ui.search_range_to_days` | INT | `10` | 기본 검색 종료일 = 오늘 + N일 |

원문 공통 요구 *"검색, 기간, 검색어"* 의 기본값입니다. 업무 관행에 따라 과거만 보는 곳도,
납기 예정까지 보는 곳도 있어서 고정할 수 없습니다.

**합계: FEATURE 12건 + RULE 33건 = 45건.**

> 출하 자동화(`생산완료 → 자동 출하`)는 정책이 아닙니다. **공정라우팅의 전후 행위 지정**으로 갑니다(§2).
> 테넌트 전체에 일괄 적용될 값이 아니기 때문입니다.

## 7. 편집 권한

**기능을 넣고 빼는 옵션은 시스템관리자의 고유 권한입니다.** 업체 사용자·관리자는 설정할 수 없습니다.

### `editable_by`는 정책마다 개별 지정한다

**카테고리로 결정되지 않습니다.** `RULE` 안에도 시스템관리자만 만져야 하는 것이 섞여 있고,
"업무 규칙이니까 전부 업체" 같은 고정 분류는 성립하지 않습니다. `policy_def.editable_by`를
정책 하나하나에 붙이는 이유가 이것입니다.

| | `SYSTEM_ADMIN` | `TENANT` |
|---|---|---|
| 성격 | 구조 · 데이터 무결성 · 추적 전제를 바꾸는 것 | 업무 운영 방식과 화면 편의 |
| 되돌리기 | 어렵거나 불가 | 언제든 가능 |
| 잘못 설정하면 | 데이터가 깨지거나 이력이 끊김 | 불편하지만 복구 가능 |
| 예 | 커스텀 컬럼을 추가할지 말지 | 기본 검색 기간을 −10일 ~ +10일로 |

#### 현재 할당

`FEATURE` 12건은 전부 `SYSTEM_ADMIN`입니다. `RULE` 33건 중 아래 **8건만** `SYSTEM_ADMIN`이고 나머지 25건은 `TENANT`입니다.

| 키 | `SYSTEM_ADMIN`인 이유 |
|---|---|
| `stock.fifo_reassign` | 켜면 **이미 발행된 바코드·LOT 추적 링크가 깨집니다.** 되돌릴 수 없습니다 |
| `auth.qr_login` | **인증 강도를 바꾸는 설정**입니다. 업체가 켜고 끄게 두면 보안 경계가 업체마다 달라집니다 |
| `material.issue_calc` | 계산식은 **잘못 등록하면 현장 출고 수량이 통째로 틀립니다** ([자재소요-계산-설계.md](./자재소요-계산-설계.md) §8) |
| `stock.snapshot_cycle` | 내부 튜닝값. 업무 의미가 없고 잘못 잡으면 배치가 무너집니다 |
| `barcode.allow_duplicate_no` | 바코드 번호의 유일성 전제를 바꿉니다. 추적 로직 전체가 여기에 의존합니다 |
| `production.equipment_manual_qty` | 설비 연동 구성과 짝입니다. 연동 없이 끄면 실적을 아예 못 넣습니다 |
| `lot.material_source` | **LOT 번호 체계는 추적의 근간**입니다. 운영 중 바꾸면 기존 LOT과 새 LOT의 의미가 달라지고 되돌릴 수 없습니다 |
| `stock.remnant_consume` | 자동 차감 대상이 바뀌면 **어느 조각이 나갔는지의 의미가 달라집니다.** 운영 중 전환하면 이전 출고 이력과 해석이 어긋납니다 |

나머지 20건 — 음수재고 허용, 소급 한계, 마감 주기, 자재·출하 차감 방식, 검사 정책, 공정 순서 차단,
수량 바코드 값, 선발행 허용, 인쇄 매수, 검색 기간 기본값 — 은 **업체가 자기 업무에 맞춰 정합니다.**

> 이 할당은 고정이 아닙니다. 정책을 추가할 때마다 위 기준으로 **개별 판단**합니다.
> 애매하면 `SYSTEM_ADMIN`으로 시작해서 필요할 때 여는 편이 안전합니다. 반대 방향은 사고를 부릅니다.

#### 노출 위치

| `editable_by` | 노출 |
|---|---|
| `SYSTEM_ADMIN` + `FEATURE` | 슈퍼관리자 **기능옵션관리** |
| `SYSTEM_ADMIN` + `RULE` | 슈퍼관리자 **업체 설정** (`is_visible=false`면 운영 도구로만) |
| `TENANT` | 업체 설정 화면 + 품목/거래처 마스터의 오버라이드 |

### 원칙 — 구조는 시스템관리자, 그 안은 업체의 권한

정책 밖의 항목까지 놓고 보면 경계가 하나로 정리됩니다.

| 시스템관리자 전용 | 업체 |
|---|---|
| 기능 스위치 `feature.*` | 업무 규칙 `RULE` (ENTITY 오버라이드 포함) |
| 메뉴 구성 `menu` | 메뉴별 접근 권한 `menu_role` |
| **커스텀 컬럼 정의** `custom_field_def` | **커스텀 컬럼 값** |
| **컬럼명 관리** `column_label` | **마스터 데이터** (품목·거래처·공정·LOT규칙·라벨규격…) |
| 내부 튜닝값 (`is_visible=false`) | 업무 데이터 (수주·발주·작업지시·실적·출하…) |

**업체는 시스템의 구조를 바꾸지 못하고, 그 안을 채웁니다.**
시스템관리자 쪽은 전부 **온보딩 전 협의로 확정**하며, 운영 중 화면에서 요청하는 흐름은 없습니다.
원문의 `시스템관리(슈퍼관리자) : 기능옵션관리, 메뉴관리, 커스텀 컬럼관리, 컬럼명 관리`가 이 경계 그대로입니다.

#### 오른쪽 열 안에서는 권한이 결정한다

오른쪽은 "테넌트 관리자"라는 고정 역할의 몫이 아닙니다. **업체 사용자의 권한에 따릅니다.**

| 무엇을 | 누가 |
|---|---|
| 정책 값 변경 | **설정 메뉴** 쓰기 권한을 가진 사용자 |
| 마스터 데이터 등록·수정 | **해당 마스터 메뉴** 쓰기 권한을 가진 사용자 |
| 품목/거래처의 정책 오버라이드 | **그 마스터 메뉴** 쓰기 권한을 가진 사용자 |
| 커스텀 컬럼 값 입력 | 그 엔티티 화면의 쓰기 권한을 가진 사용자 |
| 메뉴별 접근 권한 부여 | **권한관리 메뉴** 쓰기 권한을 가진 사용자 |

`editable_by = TENANT`는 특정 역할 이름이 아니라 **"업체 쪽에서 편집 가능"** 이라는 뜻이고,
업체 안에서 실제로 누가 하는지는 `menu_role`이 정합니다.

품목의 자재 차감 방식이나 거래처의 입고검사 방식이 그 마스터 화면 안에 들어 있는 것도 같은 이유입니다 —
**정책 오버라이드는 마스터를 등록하는 사람이 그 자리에서 정하는 값**이지, 별도 관리자가 개입할 일이 아닙니다.
원문에서도 거래처 등록 화면 안에 검사 선택이 들어 있습니다.

### 화면에서 숨기는 것으로는 부족하다

`PolicyService.set()`이 **호출자 권한을 검사**합니다. 업체 사용자가 `feature.*` 키를 설정하려 하면 **거부**합니다.
`editable_by='TENANT'` 항목이라도 해당 화면의 쓰기 권한이 없으면 역시 거부합니다.
조용히 무시하면 "설정했는데 안 먹는다"가 되고, UI만 막으면 API로 뚫립니다.

선행 조건을 만족하지 않는 정책은 설정 화면에서 숨깁니다.
`feature.closing = false` → `closing.cycle` · `closing.grace_days` 비노출.

### 기능 세트는 온보딩 전에 정해진다

업체의 기능 사용여부는 **사전 협의로 확정한 뒤 반영**합니다. 운영 중에 업체가 화면에서 요청하는 흐름은 없습니다.

**계약 플랜별 템플릿은 두지 않습니다. 업체마다 개별 지정합니다.**
신규 테넌트는 `policy_def.default_value`에서 출발하고(창고·LOT·바코드는 켜짐, 나머지는 꺼짐),
온보딩 화면에서 협의 내용대로 10건을 개별 조정합니다. 플랜 테이블은 필요 없습니다.

따라서 꺼진 기능은 **메뉴에서 그냥 사라집니다.** "담당자에게 문의" 같은 안내를 두지 않습니다 —
협의된 범위 밖의 기능이 존재한다는 사실 자체를 화면에 노출할 이유가 없습니다.

누가 언제 어느 업체의 기능을 켰는지는 `policy_history`가 남깁니다.

### 메뉴 노출은 3단계로 결정된다

**메뉴 설정도 업체가 할 수 없습니다.** 업체가 하는 것은 메뉴별 접근 권한 부여뿐입니다.

| 단계 | 대상 | 결정 주체 | 통과 못 하면 |
|---|---|---|---|
| ① 기능 스위치 | `feature.*` | **시스템관리자** (온보딩 전 협의) | 테넌트 전체에 메뉴 없음 |
| ② 메뉴 구성 | `menu` | **시스템관리자** | 〃 |
| ③ 메뉴별 접근 권한 | `menu_role` | **업체** (권한관리 권한 보유자) | 해당 역할 사용자에게만 미표시 |

- 업체는 메뉴를 **만들거나 지우거나 순서를 바꿀 수 없습니다.** 구조·명칭은 제품이 정합니다.
- 업체가 정하는 것은 **"어느 역할이 어느 메뉴에 접근하는가"** 뿐입니다.
- **읽기 권한이 없으면 메뉴에 아예 표시되지 않습니다.** 비활성 처리나 "권한 없음" 페이지가 아니라 **미표시**입니다.

읽기 권한이 노출을 결정합니다. 쓰기 권한은 그 안에서의 동작만 제어합니다 — 읽기 없이 쓰기만 있는 조합은 만들 수 없습니다.

```
menu_role (tenant_id, menu_id, role_id, can_read, can_write, ...)
   can_read = false  →  그 역할의 사용자 메뉴 트리에서 제외
```

**여기서도 화면에서 숨기는 것만으로는 부족합니다.** 메뉴에 없어도 URL을 직접 치면 들어가집니다.
라우트와 API 양쪽에서 같은 권한을 검사해야 합니다.

꺼진 기능의 메뉴는 **권한 설정 화면에서도 보이지 않습니다.** 존재하지 않는 메뉴에 권한을 부여할 수는 없습니다.

시스템관리자가 신규 메뉴를 추가하면 기존 테넌트에는 **권한 미부여가 기본**입니다.
관리자가 명시적으로 부여해야 노출됩니다 — 새 메뉴가 갑자기 전 사용자에게 열리는 사고를 막습니다.

## 8. 설정 화면은 카탈로그에서 자동 생성한다

`policy_def`의 `ui_group` / `ui_order` / `label_ko` / `value_type` / `enum_values` / `editable_by`만 있으면 화면을 그릴 수 있습니다.

- 슈퍼관리자 **기능옵션관리** = `category='FEATURE'`
- 업체 **설정** = `category='RULE' AND is_visible=true AND editable_by='TENANT'`, `ui_group` 별 묶음 (+ 설정 메뉴 쓰기 권한)
- 거래처 상세의 검사 정책 = `allowed_scopes`에 `PARTNER`가 있는 항목
- 품목 상세의 차감·검사 정책 = `allowed_scopes`에 `ITEM`이 있는 항목

**정책을 추가할 때 화면 코드를 고치지 않습니다.** 시드 한 줄이면 설정 화면에 항목이 생깁니다. 이게 키-값 방식을 택한 가장 큰 이유입니다.

오버라이드된 항목은 화면에서 **"상위 설정과 다름"** 을 표시하고, 상속 상태로 되돌리는 버튼을 둡니다.

## 9. 운영 규칙

**① 정책 변경은 소급 적용되지 않는다**
음수 재고를 나중에 금지로 바꿔도 과거 데이터는 그대로입니다. 정책은 "지금부터"의 규칙입니다. 언제 바뀌었는지는 `policy_history`가 답합니다.

**② 미등록 키는 런타임 예외**
`resolve()`가 `policy_def`에 없는 키를 받으면 기본값을 반환하지 말고 예외를 던집니다. 오타가 조용히 기본값으로 흘러가면 몇 달 뒤에 발견됩니다.

**③ 정책 증식을 경계한다**
설정 가능한 제품의 고질병입니다. 새 정책을 추가하기 전에 확인합니다.

- 이게 **정말 업체마다 다른가**, 아니면 우리가 결정을 미루는 것인가
- 기본값으로 90%가 커버되는가
- 이 정책의 두 값이 **둘 다 테스트되는가**

세 번째가 핵심입니다. 정책 하나는 테스트 경로를 두 배로 만듭니다. 33건이면 이미 적지 않습니다.

**④ 기능 스위치는 데이터를 지우지 않는다**
`feature.lot`을 껐다가 다시 켜면 기존 LOT 데이터가 그대로 보여야 합니다. 스위치는 **노출과 동작만** 제어합니다.

## 10. 서비스 인터페이스

```
PolicyService
  get(key)                          → 테넌트 스코프 값
  get(key, context)                 → 컨텍스트 반영 해석
  getAll(category)                  → 설정 화면용
  set(key, scope, value, reason)    → 검증 + 이력 + 캐시 무효화
  isEnabled(featureKey)             → 기능 스위치 단축

PolicyContext
  .partner(id) / .item(id) / .process(id) / .warehouse(id)
  체이닝 가능 — resolve 시 구체적인 것부터 탐색
```

`set()`은 저장 전에 검증합니다 — **호출자가 `editable_by`를 만족하는지**, 허용 스코프인지, `value_type`에 맞는지, ENUM 후보에 있는지, 의존 기능이 켜져 있는지.

## 11. Phase 배치

| Phase | 내용 |
|---|---|
| **Phase 0** | `policy_def` / `policy_value` / `policy_history`, 해석 서비스, 캐시, **기능 스위치 10건 + 메뉴 연동** |
| **Phase 1** | RULE — 재고·수불(8) · 자재차감(3) · 품질(5) · 생산(3) · 바코드(3). 설정 화면 자동 생성 |
| **Phase 2** | 전자결재·외주·커스텀 컬럼 관련 정책 활성화. 오버라이드 UI 고도화 |
| **Phase 3** | 공정라우팅의 **생산 전후 행위** 지정 (자동 발주 · 자동 출하) — 정책이 아니라 라우팅 데이터 |

**Phase 0에 반드시 들어가야 합니다.** 뒤로 미루면 각 모듈이 자기 방식으로 설정을 읽기 시작하고, 나중에 통합하는 비용이 처음 만드는 비용보다 큽니다.

## 12. 미결

| # | 항목 | 확인 필요 |
|---|---|---|

> 해결됨 — *초중종 배치*: 라우팅에 **초중종 검사 공정을 생산 공정 바로 뒤에** 배치. 병행 진행(§6 B-3).
> 해결됨 — *진행 차단*: 앞이 생산 공정이면 **시작(s) 기록**(수량 0이어도), 검사 공정이면 **검사 완료**. 검사 완료 전 막히는 것은 **다음 공정 시작뿐**.
> 해결됨 — *초물 차단*: 하드 블록이 아니라 **경고 후 허용**. 현장이 생산 흐름에 따라 판단(§6 B-3).
> 해결됨 — *초중종의 완료 방식*: `quality.mode.process`를 **그대로 적용**. 체크포인트별로 다르게 두지 않음(§6 B-3).
> 해결됨 — *중물 시점*: **작업자 임의**. 시스템이 시점을 계산하지 않고, 미실시 경고는 검사 공정을 닫을 때 표시(§6 B-3).

> 해결됨 — *기능 스위치와 라이선스*: 기능 스위치는 **시스템관리자 고유 권한**. 업체는 설정 불가(§7).
> 해결됨 — *정책 오버라이드 권한*: `RULE`의 ENTITY 오버라이드는 **해당 마스터 메뉴의 쓰기 권한을 가진 업체 사용자**가 수행(§7).
> 해결됨 — *출하검사 품목 스코프*: 품목에 **출하검사 사용여부**를 설정(`BOOL`, `TENANT → ITEM`).
> 해결됨 — *기능 프리셋*: 플랜 템플릿 없음. **업체마다 개별 지정**(§7).
> 해결됨 — *`quality.process_inspection` 정책 필요성*: 키 삭제. **라우팅 데이터**가 검사 유무를 결정(§6 B-3).

> 해결됨 — *입고검사 스코프에 품목 추가*: 추가. 품목은 전체 값 설정 가능하며, `무검사`일 때만 거래처를 무시합니다(§4).
> 해결됨 — *STRICTEST 적용 범위*: 사용하지 않음. `OVERRIDE` + `EXEMPT_THEN_PRIORITY` 두 전략으로 충분.

| 캐시 | 테넌트 단위 전체 로드, 변경 시 무효화 |
